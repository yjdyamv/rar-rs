# 官方 RAR 7.23 解析器决策规则（反汇编，2026-11-16）

目标函数：`Rar.exe`（7.23）`FUN_140044794`（每子块驱动）+ `FUN_1400468d4`（哈希链搜索）。
这张表把我们和官方的差别定位到了具体规则，而不是"实现好坏"。

## 子块划分

`FUN_140044794` 循环 `uVar19 = 0x1000`（**4096 字节**），每子块写
`param_2+0x300ac = 子块剩余长度`（`max_length`）、`+0x30098 = 当前位置`、
`+0x300b0 = 最大距离`（`min(pos, 字典大小)`）。位置是全局的，子块只是
"决策批"边界，不是历史边界。

## 每位置只有 4 类候选

| 类 | 来源 | 接受条件 |
| -- | ---- | -------- |
| 1 | `prev1[pos]`（`param_1+0xb1e8`，1 字节步长链） | 首字节 + 第二字节相同 |
| 2 | `prev2[pos]`（`+0xb1f0`，2 字节步长链） | 距离 ≤ `0x2000`（8 KiB）、len ≥ 3、`best_len < 2 \|\| dist < best_dist << 7` |
| 3 | `prev4[pos]`（`+0xb1f8`，4 字节步长链） | 距离 ≤ `0x40000`（256 KiB）、len ≥ 4、`best_len < 3 \|\| dist < best_dist << 6` |
| 4 | 5 字节哈希链（`FUN_1400468d4`） | 见下 |

即：`prev1` / `prev2` / `prev4` 三张"逐位置前驱表"直接给出 3 个候选，
只有它们都不够长时才进哈希链。这正是我们一次次想用"每位置前驱链"
替代 CSR 却只看到变慢的原因——我们把它当**全部**候选来源，官方只当
**前 3 个**，第 4 类还是靠哈希桶。

## 哈希与链走

`FUN_1400468d4`：

- 哈希（5 字节参与）：`w = *(u32*)p; h = ((w * 0x2773) >> 12 ^ p[4] ^ (w * 0x2773)) & mask`。
- 链头表 `param_1+0x120` 按 `pos % param_1[0x10]` 寻址（**环形**），
  候选必须同时满足首字节与哈希相同，否则直接 `return`。
- 深度：`uVar25 = param_1[0x184]`；当 `param_1[0x18d] != 0 && counters[0x300b8] < counters[0x300bc]`
  且 `pos > 0x1fffff` 时取 `>> 2`（MT/远距离时深度降为 1/4）。
- 计数器 `0x300b8 / 0x300bc` 初值为 `0x96 = 150`（`0x300bc` 在 `-m1` 之外为 150，
  否则 0），是"最近 N 次没提升"的节流器。

## 规则式接受（没有 DP）

- 候选长度 `iVar22 > best_len` 时，先在 `iVar22 - 4` 个后续位置上扫描同哈希，
  选**距离最小**的那个作为该长度的代表（`uVar8 = min(dist_i)`），再更新 `best`。
- 早停：`best_len > 2 && new_dist > best_dist * 0x4000 && iVar22 < best_len + 5` → `return`。
- 接受新最优：`iVar22 > 4 && (iVar22 > best_len + 1 || new_dist >> 5 <= best_dist)`。
- 记录：16 字节/条 `{u32 len, u32 类别, u64 dist}`，写进 `param_2+0x20048`
  的环形缓冲（`0x1000 = 4096` 条上限），供 `FUN_140044600` 串行裁决。
- 懒匹配：`iVar13 = best_len; if (iVar13 != 2) local_res8 -= 1;`（`local_res8` 是
  逐位置的"上次是否赢"历史计数）。

**没有任何价格表、没有逐长度松弛、没有 OPTIMAL 递归。** 全部是整数比较，
每条候选 O(1) 决策。

## 与我们的差距（量化）

| | 官方 | 我们 |
| -- | ---- | ---- |
| 候选来源 | 3 类前驱 + 哈希链（深度 `0x184`，MT 时 `>>2`） | CSR 哈希链，深度 64 |
| 决策 | 规则（`dist >> 5/6` 比较 + 早停） | 定价 DP（32 字节/位置 × 长度步） |
| 决策批 | 4096 字节 | 48 KiB |
| 距离/rep 裁决 | 串行 `FUN_140044600`（全局一致） | 每切片重启 rep/价格 |
| 每字节 CPU | ~108 ns（274 ms 墙体 / 16 核 / 13.9 MB） | ~360 ns（547 ms / 16 核） |

结论：2× 差距是**决策模型**的差距，不是常数因子。要么按上表重写解析
（比例上会明显变差：我们 DP 的 0.05% 优势会消失，还要再退），要么接受现状。
`-m1` 上更能说明问题：我们的固定开销（filter 扫描 47 + 索引 102）已经接近
官方整个 `-m1` 的 170 ms，而官方根本没有这两步。
