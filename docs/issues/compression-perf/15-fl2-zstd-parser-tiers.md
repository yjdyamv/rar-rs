# issue 15 — 借 Fast LZMA2 / zstd 的价格驱动解析思路提速

状态：开放（2026-09-18 立项，有意做）。目标：**压缩速度**；比率按
[`PLAN.md`](../../../PLAN.md)「性能」段的契约守住（默认档 packed 不得变大）。

## 参照物（上游事实）

Fast LZMA2（`conor42/fast-lzma2`，README 原文）基于 Igor Pavlov 的
LZMA2（7-Zip），用**并行缓冲的 radix match-finder** 加一部分 zstd
的优化，目标是相对 7-Zip 默认 LZMA2 "a 20% to 100% speed gain at the higher
levels"，代价是 "a small loss in compression ratio"。

它的匹配器是 _block_ 算法：要拿到与 7-Zip
相当的比率需要约双倍字典（抬高解压内存），同字典下产物大约大 1%–5%；另有一个
high-compression
选项在较小字典上换回比率。好处是匹配器能用简单线程模型多线程、不把输入切成需要复制表/链的大块，每线程额外内存
"typically no more than a few megabytes"。v0.9.1 还加了 incompressibility
checker，对高熵数据约快 2x。

zstd 侧（`zstd_opt.c`）：最优解析的价格每次从频次数组重算（`ZSTD_getMatchPrice`
/ `ZSTD_litLengthPrice`），上游有把价格分量制表缓存的提议；`optLevel`
用于分级（低档偏好小 offset，利于解压时的缓存局部性）。FL2 对外提供 fast / opt /
ultra 三档策略。**实现前先读上游源码核对**档位命名与价格表公式。

## 我们的现状（已核对源码）

- 顺序/未过滤（`codec/modern/lzss_huff/encoder/chunked.rs`、`codec/modern/lzss_huff/encoder/parse/`）：`-m1`
  = 哈希链 greedy+lazy（`find_matches_with_tail`）；`-m2`–`-m5` = 一次 DP 加
  `OPTIMAL_PARSE_PASSES`（0/2/2/3/4）次重定价，匹配用 BT4 风格
  `TreeMatchFinder`（`son` 树），长程靠采样表 `LongRange`。

- 过滤成员（x86/delta 等，`codec/modern/lzss_huff/encoder/filter.rs`）：level ≥
  2 走 `find_matches_optimal`，level 1 走哈希链。

- MT：所有档位都由 `mt_slice_symbols_low_step` 以哈希链 greedy+lazy（链预算常量
  16）解析切片——即 map 里「文档化接受的分歧」，也是低步数档位的落点。

- 价格：`TokenPrices::match_cost` 对每个候选调 `EncoderMatchState::encode_match`
  现场算 slot/extra，再查码长。

## 杠杆

### A. 不改产物字节（先做；验收 = 逐字节相同）

1. **价格分量制表**：把 `len_slot` / `dist_slot` / `ldc`
   相关分量按当前价格表缓存成表，内循环只做查表与加法；对应上游那个制表提议。

2. **可压性预检更便宜**（已落地 2026-09-18）：预检本身要按成员自己的档重编 512
   KiB + 3×256 KiB 样本，在 4 MiB 成员上占**编码时间的
   18–28%**；现在先用一个廉价结构筛（步长 16 的 4 字节窗口重复率，共用
   `distinct_window_percent`）——所有采样区都有重复窗口就跳过采样编码。跳过只可能去掉一个原本会强制
   STORE 的判决，所以归档产物只会不变或更小，代价仅是时间；实测 8 MiB 语料：m3
   文本 180→155 ms、m5 288→256 ms（−13%/−11%），随机数据不变
   （筛不会放行）。数据与边界见 [`PLAN.md`](../../../PLAN.md)「性能」段。

### B. 改产物字节（只能是新档或 MT 档，须文档化并过比率门）

3. **价格驱动的中间档**：填 `-m1` 与 `-m2` 之间的断崖——「有界候选 +
   一次定价的便宜 DP」。优先级最高的是装进 MT 低步数层：同速换比率，把 map
   记录的 ~0.6–2.9pp 收回来（MT 偏离 seq 已是接受的分歧，seq 不受影响）。

   **已试（2026-11-01）：MT 那半边早在「杠杆 3 顺延价格表」里落地了**
   （`mt_slice_symbols_row_index` + `windowed_priced_parse` 已是 m1–m5 的默认
   解析器），本条的净剩余是 seq 侧；实测结论见下「已试：seq 断崖的真实旋钮
   是收集器预算，不是定价器」。

4. **匹配器行化**：给快档加「按哈希分行的有界深度 finder」（RAR15
   已用同形状的扁平 CSR 行索引），BT4
   继续留给默认比率档；不得为速度改默认档的下降语义（issue 09）。

## 已试（2026-09-18）：一正一负

### 成立：窗口内有界 DP（原型开关 `RAR_RS_MT_WINDOW_DP`，未落地——当前树中无此环境变量）

把链式 finder 的「每位置单一候选」喂给 seq 自己那条已验证的 DP （原型
`windowed_chain_parse` → `optimal_parse_tokens` +
`convert_tokens`，不新增决策逻辑），
加上共享长程探测与首次估计价格。`ntoskrnl.exe` 12.5 MiB、mt8、同二进制 A/B：

| mt8         | 贪心（现状）     | 窗口 DP             |
| ----------- | ---------------- | ------------------- |
| m1（链 4）  | 438 ms / 53.77%  | 754 ms / 49.98%     |
| m3（链 16） | 1117 ms / 52.05% | ~2.8–3.1 s / 48.48% |

收益：回收 MT 与 seq 差距（~5.4pp）中的 ~3.6–3.8pp，MT 可到 48.48%（seq 46.67%）
而只花 seq m3 的 2.3x 时间；对速度更值的是 **m1 + 窗口 DP 在两个轴上都胜过现在的
m3 贪心**（754 ms/49.98% vs 1117 ms/52.05%）。代价是同一档下时间换比率（m1
1.7x、 m3 ~2.5x），所以它留在开关后：改现有 `-m` 档的 MT
时间/产物是产品决策，不是白送的优化。产物可解（`collectbench` 自带 decode
断言）。

### 成立（2026-10-28，已落地）：DP 块之间顺延价格表

杠杆 3 的最后一个便宜件。`windowed_priced_parse` 的每个 DP 块本来只用首次估计价
（`estimated_match_cost`）算一遍；现在把上一块 `convert_tokens` 得到的码长表
（`TokenPrices`，全 `Copy`）交给下一块的第一次定价。同一成员内块顺序固定（一个
worker
一次只跑一个切片），所以顺延的那张表就是解析自己会重建的那张；切片第一块没
有前驱，仍用估计价——切片独立性（并行的前提）不受影响。

此前已实测「真正多跑一遍重定价」能换回多少：`RAR_RS_MT_PASSES` 扫
`ntoskrnl.exe`(12.5 MiB, mt16) m3 44.68%→44.44%、m5 44.31%→44.08%，但耗时
+10~20%（DP 才是热点，finder 很便宜——把 `RAR_RS_MT_ROW_DEPTH` 从 64 提到 1024
几乎不花时间），标准语料上更是 +22~69%（text l3 2479→4214 ms）。顺延拿到的是同一
笔收益，成本是一次码长表构建：

| ratiocheck（mt16） | 顺延前       | 顺延后       | 差      | 耗时 |
| ------------------ | ------------ | ------------ | ------- | ---- |
| text l3            | 18.19%       | 17.68%       | −0.51pp | 持平 |
| text l5            | 17.27%       | 16.83%       | −0.44pp | 持平 |
| xml l3             | 11.85%       | 11.45%       | −0.40pp | 持平 |
| xml l5             | 11.15%       | 10.76%       | −0.39pp | 持平 |
| mixed l3/l5        | 48.32/48.17% | 48.22/48.09% | −0.10pp | 持平 |
| sparse-copies      | 88.55%       | 88.54%       | −0.01pp | 持平 |

CLI 端到端（mt16，`-ma5`）同样全档变小：`ntoskrnl.exe` m1–m5 −0.06~−0.13pp、
`ntdll.dll` −0.06~−0.11pp、30 MB 文本 **−0.58~−0.77pp**；`unrar t` 全通过。
产物字节变了，但 MT 偏离 seq 本来就是已文档化的接受项，且 packed
在每档每语料上都 **只变小**，符合「比率是契约」。

确定性：`mt4`/`mt8`/`mt16` 与重复运行字节完全一致（切片边界不影响块内顺延）。
守卫：`mt_tests::carried_prices_beat_starting_from_the_flat_estimate` 用测试缝
`set_price_carry_enabled` 关掉顺延，断言产物必须变大且两臂都能解码。

## 已试（2026-11-01）：seq 断崖的真实旋钮是收集器预算，不是定价器

`ntoskrnl.exe`（12.5 MiB）、`src.rs`（5.1 MiB，本仓源码拼接）、`text`/`mixed`/
`xml`/`sparse-copies`（`ratiocheck` 语料），dict 16 MiB，`rar_rs::encode` （seq
路径，不可压预检关闭），min-of-2，重复运行字节完全一致。

先量基线断崖：m1（贪心，链 4）747 ms / 54.40%，m2（BT4 cut 16 + 两 pass） 6621
ms / 46.87%——**8.9x 时间、7.5pp 比率**。

阶段分解（临时插桩，per chunk 的 collect / dp / passes）：

| 配置                | collect    | dp     | passes | wall    | 比率   |
| ------------------- | ---------- | ------ | ------ | ------- | ------ |
| m2 默认（16/2/256） | **4.41 s** | 1.46 s | 1.46 s | 8028 ms | 46.87% |
| cut 4，1 pass       | 2.18 s     | 1.02 s | —      | 3797 ms | 48.87% |
| cut 64，1 pass      | 4.74 s     | 1.35 s | —      | 6760 ms | 46.76% |

**collect 占 55–60%，且随尾部窗口增长而恶化**（每 chunk 吞吐 cut4 8.06 → 5.69 →
4.32 MiB/s，cut64 7.65 → 2.74 → 1.52 MiB/s，即 166 ns/位置 → 362 ns/位置）——
正是 issue 09 的结论（BT4 ~5.5 步/查询、每步一次 DRAM 随机读）。而**DP
在各预算下 成本恒定**，多跑一遍重定价只值 ~0.2pp、代价 20%：

| ntoskrnl | passes 0/1       | passes 2         |
| -------- | ---------------- | ---------------- |
| cut 4    | 3797 ms / 48.87% | 4676 ms / 48.65% |
| cut 16   | 5405 ms / 47.08% | 6676 ms / 46.87% |
| cut 64   | 5738 ms / 46.87% | 7461 ms / 46.66% |

所以这个档的旋钮就是**收集器预算**，而且梯度是光滑的（这正是 B.3 想要的东西）：

| 语料     | m1        | cut 4      | cut 8      | cut 16     | m2（16 + 2 pass） |
| -------- | --------- | ---------- | ---------- | ---------- | ----------------- |
| ntoskrnl | 54.40/747 | 48.87/3472 | 47.82/4575 | 47.08/5680 | 46.87/6621        |
| src.rs   | 22.99/101 | 19.86/1118 | 18.62/1455 | 17.75/1861 | 17.64/2407        |
| text     | 23.19/99  | 21.38/1028 | 18.74/1595 | 16.56/2674 | 16.22/3750        |
| mixed    | 53.41/407 | 49.33/1563 | 48.59/1481 | 48.05/1844 | 47.99/2632        |
| xml      | 14.63/16  | 13.45/330  | 12.19/424  | 10.93/555  | 10.51/831         |

（`比率% / 耗时ms`；sparse-copies 各档一致，在 dict 16 MiB 下走不可压探针直接
STORE，对这个实验没有信息量。）

**已落地的样子**：开关 `RAR_RS_SEQ_PRICE_TIER=<cut>` 把 level ≥ 2 的 seq 解析
换成「该 cut + 一次定价」（`encoder::price_tier_cut`，默认关闭；level 1 不受
影响——贪心路径没有可重配的预算）。默认档字节一字未动（m1 指纹
`49b1916ea94dd6c0`、m2 指纹 `a1a2ac5200a11c5b` 与改动前逐字节相同； `ratiocheck`
的 MT 12 组 size+指纹全部不变）。守卫： `lzss_huff::price_tier_tests` 用测试缝
`set_price_tier_cut` 断言开关确实到达
解析器（不改字节就说明开关是空转）、两次运行逐字节相同、四候选预算不比默认档
更小，以及 level 1 完全不受影响。

**要不要提升为文档化档，待定——这是产品决策**：cut 4 在每个语料上都落在 m1 与 m2
之间，而这两点之间原来什么都没有；但它的产物字节与 m1/m2 都不相同，按「比率是
契约」只能作为新档（例如 `-m1.5`）或 MT 侧选项出现，不能改现有档。

### 否决（同批实测）：三条更「聪明」的省时间路线

- **行索引替掉 BT4**（杠杆 4 的形状）：`RowIndex` 的 `build` 计入后单测全位置
  `collect`，实测 depth 4 = 139.9 ns/位置、16 = 437.4、64 = 622.5、256 = 903.9
  （runs/位置 0.89–1.33），而树 cut4 = 166、cut64 = 362——**depth ≥ 16 时
  行索引比树更慢**（没有长度-距离剪枝、每个候选都要 `match_length_at`、位置靠
  `partition_point` 二分）。它在 MT 里成立的前提是切片刻意短、预算特意小，
  不是普适的提速手段。
- **砍 `MAX_PARSE_STEPS_PER_POSITION`**：12 → 8 → 6 → 4 在 `ntoskrnl` 上是
  7283/7362/7223/7386 ms、46.76/46.78/46.80/46.83%——**步数预算在二进制语料上
  根本不是瓶颈**。
- **砍近窗上限**（issue 09 的老实验，复测）：`ntoskrnl` cut16 w4 47.49%/5337
  ms、 w2 47.92%、w1 48.51%；`mixed` cut16 w4 **50.70% 且更慢**（3318 ms 对基线
  6446 ms/46.87% 是另一侧）；`text` 三个窗口都是 16.2x%。比率代价与 issue 09
  记录的 4 MiB/−27%、2 MiB/−37% 同向，仍然不值得。

结论：**seq 的 `-m1`→`-m2` 断崖填不平在「更便宜的定价」或「更聪明的 finder
结构」上，只能靠「更小的收集预算 + 放弃重定价」**——也就是上面那张表。

### 否决：静态价格的 cheap tier

把 MT 低步数层的「比长度」换成「比价格」——候选取 finder 最优、最近两个距离与重复
长度，按估计 bit/字节比较，再加一步价格前视（zstd 的 `opt0` 形状）。藏在
`RAR_RS_MT_PRICED` 后面测 `ntoskrnl.exe` m3/mt8：无开关 52.05%，有开关 54.45%，
速度相同；把模型的字面量价格从 3 扫到 14 bit 只在 53.07%–54.45%
之间游走，从未低于
基线。原因：静态预块估计看不到「多一个符号」的表代价（逐字节比较会把长匹配打碎成短
而便宜的匹配），所以「取最长、次位置更长就
lazy」反而是更好的代理。已回退，不留开关（同 issue 14 的负例处理），判决在
[`PLAN.md`](../../../PLAN.md)「性能」段。

## 硬约束与验收

- 默认 `-m` 各级产物字节不动（map：「比率是契约」）；改字节的档位先以
  `RAR_RS_FAR_BAND` 这类 env 开关做实验，再决定是否提升为文档化档。

- 验收：`examples/mtprobe.rs`、`examples/ratiocheck.rs`、`examples/perfbench.rs`
  加 map 的对拍语料；默认档 packed
  不得变大；新档必须给出成对的「同速下比率」或「同比率下速度」数字；MT
  的跨线程确定性不变。

- **不搬** FL2/zstd 的熵编码器与格式：RAR 的流是 LZSS+Huffman
  表、价格按码长而非频次分布，能搬的只有解析器/匹配器/线程模型与预检这类工程手法。FL2
  的「1%–5% 比率损失换速度」只允许出现在新档，默认档不接受。
