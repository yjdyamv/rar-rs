## 根因一：行索引报不出短匹配

`RowIndex::collect`（`parse/optimal.rs`）只把 `length >= 4` 的候选写进
`runs`——因为它按 4 字节哈希分桶。于是 MT 走法在 13.9 MB 内核镜像上**只发出
1 条** 2/3 字节匹配，MT 的 DP 也只有 ~13.5 K，而我们自己的顺序路径有 ~155 K，
官方有 ~275 K（`analyze_stream` 的 `short_dist` 行）：

| 流 | len2 | len3 |
| -- | ---- | ---- |
| 官方 m3 | 113,693 | 161,206 |
| 我们 m3（顺序） | 75,908 | 79,320 |
| 我们 m3（MT/DP） | 1,904 | 11,580 |
| 我们 m1（走法，改前） | **0** | **1** |
| 我们 m1（走法，改后） | 57,538 | 68,549 |

短匹配便宜是因为**长度加成**把距离卡得很死（`length_bonus`）：raw length 2 只能
距离 ≤ 0x100，raw length 3 只能 ≤ 0x2000。也就是它们永远在 8 KiB 内，顺手的
直映射表就能找。

## 修法一：`ShortHeads`

新增 `ShortHeads`（`parse/optimal.rs`），两张直映射表：

- `head1[256]`：每个字节值最近出现的位置 → 官方 `prev1` 的 2 字节候选；
- `head2[65536]`：每个 2 字节前缀最近出现的位置 → 官方 `prev2` 的 3 字节候选。

在 `windowed_walk_parse` 里按位置增量维护（每位置 2 次随机写，表 256 B + 256 KB
常驻 L1/L2），并从 `span.start - 0x2000` 起播种前瞻（raw length 3 的上限就是
0x2000）。≥4 的匹配仍归行索引。

**关键：短候选只能是「兜底」，不能参与竞争。** 让它们和长候选一起进「取最近的
接近最长者」，会把一条距离 10 的 2 字节匹配顶掉真正的 4 字节匹配（`length + 3 >=
longest` 那条容差本是为 rep 距离留的），实测反而变差：46.11% 对 45.75%。

## 根因二：走法的「近者优先」是错的

`walk_best` 原来取最长候选，再在「够得着」（`length*4 >= longest*3` 或
`length+3 >= longest`）的范围里改取**最近**的。官方不这么做——它的链规则是
**只把 best 变长**（`len > best+1 || dist>>5 <= best_dist`），从不为了更近而变短。
把这条对齐（`RAR_RS_WALK_NEAR=0`，现为默认）在三个语料上都是纯收益，且基本免费。

## 修法三：DP 也接上短匹配

`windowed_priced_parse` 的候选同样只来自行索引，所以 MT 的 DP 也缺 2/3 字节
候选（~13.5 K 对顺序的 ~155 K）。把同一份 `ShortHeads` 接进去：在块循环里按位置
增量维护（位置是顺序访问的，一趟前向就够），并把短候选**插到该位置的 run 段首**
（`matches.runs.insert(before, ..)`），保持它「长度递增」的次序——DP 就是按这个
次序理解「候选逐步变长」的。

结果见上表：`-m3` 5,878,581 → 5,801,341（−0.56 pp，+4% 时间），四档一致，
MT 与顺序的缺口从 100 KB 收到 23 KB。计数器顺手把 `walk_short_enabled` 改名
`short_sources_enabled`（两处共用）。

## 官方形状的逆向（ghlab，本轮补的）

- `FUN_140044600(job, pos, len, ...)` 不是决策者，是**记录 → token 的转写器**：
  遍历 job+0x1a0 的 32 字节记录（`{+0x1a0 pos, +0x1a8 len, +0x190 class}`），只处理
  落在 `[pos, pos+len)` 的记录，把 class 0/1/2/3 映射成「新距离 / rep1 / rep2 /
  rep3」的 token（`0x30007` + 槽号；新距离走 `FUN_140047d20`）。**决策在并行段**。
- `FUN_140044794(job, sub)` 是并行 worker：一次处理 `job+0x10` 字节，按 **0x1000
  (4096)** 切子块；每次调用把四个 rep 距离（`+0x300e0…f8`）清零；每位置依次取
  `prev1`(2 字节) / `prev2`(3 字节) / `prev4`(4 字节) / `FUN_1400468d4`(5 字节哈希链)
  的候选，然后用一步惰性（`FUN_14004600c` / `FUN_140045b7c`）决定是否发出；
  发出后 `local_res10 += best_length`（**跳过被覆盖的字节**）。
- 候选的接受规则带强烈的距离偏好：`prev2` 要 `dist <= 0x2000` 且
  `best < 2 || dist < best_dist<<7`；`prev4` 要 `dist <= 0x40000` 且
  `best < 3 || dist < best_dist<<6`；链上要 `len > 4 && (len > best+1 || dist>>5 <=
  best_dist)`，并在 `best_dist*0x4000 < dist && len < best+5` 时提前 return。
- `FUN_140047698` 是四槽 rep 裁决器（`len > 1`、`len >= best-3 || len*4 >= best*3`、
  以及 best-1/-2/-3 的 0xff/0x7ff/0x7fff 边界），与我们的走法一致。

结论：官方**就是**「受限候选 + 一步惰性 + 跳过」的贪心，没有任何 DP。它的
42.30% 说明贪心**能做到**；我们仍差 1.74 pp，缺的是候选类（5 字节链 + 环形/长程
两条附加源）、`FUN_140044794` 里那条「同一长度取最近」的后续扫描、以及一步**延迟**
裁决（当前只做了一步前瞻）。

## 速度：固定开销就是全部差距（2026-11-17 下半场）

同一份 ntoskrnl、`-md32m -mt24`，交错测（各 2 次取最小）。「WALK」= 强制走法
解析（`RAR_RS_MT_WALK=1`，即把走法放到该档）：

| who | -m1 | -m2 | -m3 | -m4 | -m5 |
| --- | --- | --- | --- | --- | --- |
| 我们 DP | 326 / 44.04% | 508 / 42.08% | 546 / 41.68% | 591 / 41.49% | 747 / 41.29% |
| 我们 WALK | — | 309 / 44.43% | 329 / 44.04% | 335 / 43.85% | 363 / 43.61% |
| 官方 | 124 / 54.34% | 192 / 46.59% | 240 / 42.30% | 384 / 42.14% | 373 / 42.10% |

阶段账（`RAR_RS_MTTIME=1`，m3）：

| 阶段 | m1 | m3 | 官方 |
| ---- | -- | -- | ---- |
| 启动 + 读 + CRC + 写 | ~52 ms | ~52 ms | ~56 ms |
| `best_combined_specs`（滤镜扫描） | 57 | 49 | **0** |
| 预表（`LongRange::push` + 行索引） | 109 | 96 | **0** |
| 换能（`forward_transform`） | ~21 | ~21 | 含在内 |
| waves（解析 + emit） | **99** | 329 (DP) / ~180 (走法) | ~176（整包） |

三条能落到纸上的事实：

1. **IO/启动与官方持平**（52 vs 56 ms），不是问题。
2. **走法的解析（99 ms）比官方整次 `-m3`（240 ms）还快**。走法慢是因为它多付
   ~166 ms 的预表 + 滤镜扫描，官方一次流式通过里顺手做完。
3. **我们的墙钟地板 ≈ 310 ms**（最快配置），而官方 `-m3` 是 240 ms。在官方
   `-m3` 及以下，我们的固定开销单独就超过对方整次运行，**不可能追上**；官方
   `-m4`/`-m5`（384 / 373 ms）我们可以持平甚至更快。

速度对齐点（等速比比率）：

| 对齐 | 我们 | 官方 | Δratio |
| ---- | ---- | ---- | ------ |
| 官方 -m4（384 ms） | WALK -m5 363 ms / 43.61% | 384 ms / 42.14% | +1.47 pp |
| 官方 -m5（373 ms） | WALK -m5 363 ms / 43.61% | 373 ms / 42.10% | +1.51 pp |

所以「速度达到官方」在 `-m4`/`-m5` 已经成立（还略快），代价约 1.5 pp；`-m1`–`-m3`
做不到，瓶颈是那 166 ms 固定开销，**不是解析**。

### 本轮为本轮加的两个旋钮

- `RAR_RS_MT_WALK=1`：把走法解析放到任意档（速度优先映射用）。
- `RAR_RS_RI_BITS`：行索引桶位数（12–26，默认 20）。桶数是**构建局部性**的旋钮：
  桶越少散写越集中、构建越快（14/16/18/20 bit 的 prelude 实测 51/64/82/138，
  waves 246/217/176/131），但桶内哈希碰撞变多、解析要多比较（waves 反涨），
  **净和基本持平**，故默认仍是 20。规模表（walk -m3）：14 bit 448 ms/44.96%、
  16 bit 421/44.23%、18 bit 409/44.07%、20 bit 413/44.04%、22 bit 563/44.04%。

结论方向不变：要追官方 `-m3` 及以下，必须让滤镜扫描与行索引不再是「读之外
的独立两趟」——官方没有成员级索引、没有成员级滤镜扫描，它用 128 KiB 子块 +
增量哈希链一次流式做完。这是结构改动，不是调参。

### 换能（`forward_transform`）已并行

`forward_transform` 原来把 187 条记录串行地一条条换能（`data.to_vec()` 之后再
逐区域 `apply_filter_encode`）。区域互不相干，所以现在先验证 records 是**有序、
不相交、在界内**，再切成不相交的 `&mut [u8]`，用 `par_iter_mut` 各换各的；任何
一条不满足（强制单区域、手工拼的 spec 列表）就退回原来的串行循环，字节不变。
实测归档大小逐字节相同（6,129,621 / 5,801,341），`UnRAR t` 通过；m1 的 wall
在 6 次交错里平均 422 → 407 ms（最小 328/332 在噪声内），即省 ~8–15 ms。
开关 `RAR_RS_PT=0` 退回串行，用于 A/B。

顺带试过、**实测无收益故已回退**：把 `build_split` 里那次串行 merge（八张计数表
逐桶求和）并行化。归档字节相同，但 prelude 在 107–112 ms 之间不动——本机上
prelude 的地板是那 140 MB 索引数组的首次写入（页错误 + 带宽），不是这 18 ms。

### 预表砍不掉：它被查询赚回来了（2026-11-17，本轮的决定性实验）

按「速度优先」去砍那 ~107 ms 的 prelude：加 `RAR_RS_NOINDEX=1`，跳过
`RowIndex::build`，退回每切片链（`mt_slice_symbols_low_step`，尾长由
`RAR_RS_NEAR` 控）。ntoskrnl、`-m1 -md32m -mt24 -mc-`（`-mc-` 把滤镜扫描也去掉，
纯比 prelude ↔ waves）：

| 候选源 | prelude | waves | wall | size |
| ------ | ------- | ----- | ---- | ---- |
| 行索引（现状） | 113 ms | **109 ms** | **308 ms** | 6,590,352 |
| 每切片链，8 MB 尾 | **32 ms** | 270 ms | 449 ms | 7,367,607 |
| 每切片链，2 MB 尾 | 31 ms | 309 ms | 431 ms | 7,367,607 |
| 每切片链，512 KB 尾 | 33 ms | 272 ms | 405 ms | 7,367,607 |
| 每切片链，128 KB 尾 | 33 ms | 273 ms | 438 ms | 7,367,607 |

**链省下 81 ms 的 prelude，却要赔 161 ms 的 waves 和 11.8% 的体积**（链尾长短
几乎不影响体积——瓶颈不是可达距离）。所以**成员级索引的构建费是被它自己的查询
赚回来的**。

### 链不是被可达距离限制的：与「同可达距离的行索引」对照

为公平起见，加 `RAR_RS_WALK_REACH`（把行索引候选裁到任意距离）做对照，并给
`MatchFinder` 补一个多候选探针（`collect_candidates`：把链上每一跳里改善的
`(len, dist)` 都推出去，形状与 `RowIndex::collect` 相同——原来的 `find_match`
只给一个候选）。`-m1 -md32m -mt24 -mc-`：

| 可达 | 行索引 | 链 |
| ---- | ------ | -- |
| 8 MB | 6,590,706 (47.36%) | 7,200,745 (51.74%) |
| 2 MB | 6,645,663 (47.75%) | 7,254,612 (52.13%) |
| 512 KB | 6,767,408 (48.62%) | 7,331,093 (52.68%) |
| 128 KB | 6,923,418 (49.75%) | 7,385,344 (53.06%) |

**同一可达距离下链一律差 ~4 pp**，而且链的深度几乎无用（探针深度 16/64/256/1024
→ 52.71/52.68/52.67/52.67%），所以不是碰撞、也不是走得太浅。速度上链也不赢：
512 KB 尾的链 wall 296 ms，而 512 KB 可达的**行索引**只要 241 ms。

结论：**「每切片链」这条架构路被「把行索引的可达距离裁短」严格支配**——后者
更快、更好，而且不需要新结构。链的代码留在 `RAR_RS_NOINDEX` 下作复现用。

### 可达距离是个真旋钮（走法，默认滤镜）

`RAR_RS_WALK_REACH`（字节）：

| ---- | ---- | ---- | ---- | ---- | ---- | ------ |
| wall | 331 | 323 | 321 | 304 | 312 | 305 |

即：**裁到 8 MB 几乎白送 8 ms，裁到 512 KB 换 ~26 ms 要赔 1.55 pp**。它有真
收益但很小——因为墙钟被固定开销压着（见下）。

### 走法的深度旋钮几乎不花时间

`RAR_RS_MT_WALK=1` + `RAR_RS_MT_DEPTH`（m1，ntoskrnl）：

| depth | 4 | 8 | 16 | 32 | 64 |
| ----- | - | - | -- | -- | -- |
| wall | 311 | 311 | 304 | 324 | 324 |
| size | 6,361,746 | 6,276,100 | 6,212,324 | 6,165,011 | 6,129,621 |

深度 4→64 只值 13 ms —— 走法的墙钟由固定开销决定，不由候选深度决定。所以
**「用比率换速度」在本架构里几乎换不到速度**。

即：**目前能达到的最快是官方 `-m3` 的 ~1.2×**，代价约 +5 pp。要再往下只剩

### 官方的形状：位置索引的 prev4（做通了，但被行索引支配）

逆完 `FUN_14004264c`（官方顶层 MT 驱动）后，结构定死了：一波 = 线程 × 128 KiB，
每 worker 一个 128 KiB 子块，worker 内部按 4096 字节决策；**它的 prev1/prev2/prev4
和 5 字节链是在解析的同时就地插入的（先查后插）**，所以官方**没有单独的建索引趟**。
这才是我们那 ~107 ms prelude 的对手：不是"换个结构"，而是"表按位置写、边解析边写"。

按这个形状做了 `Prev4Index`（`RAR_RS_PREV4=1`，配合 `RAR_RS_MT_WALK=1`）：
`prev[pos]` = 到上一个同 4 字节哈希位置的距离，**写在位置自己的下标上**，所以构建
是一趟线性、顺序写的 pass（分片并行，各写各的区间）。

**先记一个真 bug（本轮抓到并修好）**：`prev` 存的是**相对步长**，第一版却每次都从
`pos` 出发算 `candidate = pos - prev[candidate]`——一跳之后就落到 `pos - step` 这个
错误且通常很近的位置。表现是"远距离匹配几乎全部消失"（`dist_hist` 的 4M+ 从 92,131
掉到 12,086），而在它上面量出来的"248 ms"是假象：链几乎什么都没找到，所以快。
修法是记住 `candidate`、每跳 `candidate -= prev[candidate]`。

抓它的工具是**仓库自己的测试缝**：`prev4_candidates_match_the_row_index`
（`#[ignore]`，`RAR_RS_PREV4_CMP_FILE=<corpus>` 指向语料）把两种索引建在同一份数据上，
逐位置对比 `collect` 的 `runs`。修前 13,917,564 个位置里 5,351,705 个不一致，修后 **0**。
这个测试留下来当护栏，命令就在函数文档里。

修好后的实测（ntoskrnl 13,917,568 B，`-m1 -md32m -mt24`）：

| 候选源 | prelude | waves | wall | size |
| ------ | ------- | ----- | ---- | ---- |
| 行索引（现状） | 100 ms | 109 ms | **362 ms** | **6,129,621 (44.04%)** |
| prev4，1 片（精确） | 51 ms | 319–337 ms | 536 ms | 6,129,621 (44.04%) |
| prev4，2 片 | 35–41 ms | 233 ms | 412 ms | 6,185,728 (44.45%) |
| prev4，4 片 | 35–36 ms | 177–182 ms | 354 ms | 6,271,612 (45.06%) |
| prev4，8 片 | 39–40 ms | 134–147 ms | 334 ms | 6,331,047 (45.49%) |
| prev4，16 片 | 53 ms | 106 ms | 295 ms | 6,431,294 (46.21%) |

**结论：链的查询比桶的查询贵约 3 倍**（同等候选下 waves 319 vs 109），所以构建省下的

断掉，比率就往下走。最优点（4 片：354 ms / 45.06%）仍然**被行索引（362 ms / 44.04%）
支配**。这和 PITFALLS 里"查询必须连续、构建必须散写"那条旧结论一致，本轮第一次用
修正后的链和精确数字把它钉死。

### 重要修正：可达距离不能裁到 `-md` 以下（2026-11-17 晚）

本轮早些时候把可达距离当档位旋钮（128 K / 256 K / 512 K），在 ntoskrnl 上看起来
几乎免费（512 K 只比整窗差 1.27 pp）。**换到长距冗余占比高的数据上它是灾难**：
同一份 9.25 MB markdown，32 KiB 前瞻 → **3,246,179 B**、256 KiB 可达 →
**3,070,349 B**，而整窗只要 244,295 B（官方 318,089）。也就是说把可达距离压到
`-md` 以下**不是"有损"，而是悄悄违背字典的承诺**——匹配确实存在、就在窗口里，
只是我们不去看。

所以现在 `walk_reach` **默认等于 `dict_size`**（`RAR_RS_WALK_REACH` 只留作测量）。

### 官方形状的位置索引：浅档净赚，深档必须用排序桶（2026-11-17 晚）

用 ghlab 读 `Rar723.exe` 之后确认了官方的候选结构（`FUN_1400468d4`）：
`param_1[0x120]` 是一张**按位置索引的环表**（`ring[pos % param_1[0x10]]` 存位置），
哈希是**五字节**（`word4 * 0x2773 >> 0xc ^ byte[4] ^ word4`，与本地
`collect.rs::word5` 同形），**没有链、没有计数排序**，一趟顺序填。搜索是
"取最近同哈希位置 → 算匹配长度 → 把锚点右移 `1..len-4` 再取最近候选 → 重锚"
的贪心（`uVar15 = uVar13+1 … iVar22-4` 那段），预算在 `param_1[0x184]`
（远距离时 `>> 2`）。也就是说官方**没有我们那个 ~100 ms 预表**，它的预表就是这一趟。

本地复刻（`Prev4Index`）的实测：

- **单趟串行填充确实便宜**：内核镜像 13.9 MB 只要 **49 ms** 预表，计数排序要 120 ms。
- **链不能分片建**：每片头表从空开始，walk 走到"该片内首次出现"就断，而断的正是
  长距匹配。markdown：精确 244,419 B、2 片 393,459、4 片 679,614、8 片 1,231,478、
  16 片 1,725,608（内核镜像同口径 6,215,127 → 6,520,590，敏感度差 30 倍）。
  所以默认 `RAR_RS_PREV4_PARTS=1`。
- **深桶时链输给桶**：候选要得多时指针追踪输给连续内存——内核镜像 depth 16 的
  waves 204（链）vs 107（桶），depth 64 是 367 vs 110。
- **结论**：浅深度用链是净赚（内核镜像内部 149 vs 200 ms，**比率相同**），
  深深度必须用桶。所以 **`-m1`~`-m3` 用位置索引（深度 2 / 4 / 8），`-m4`/`-m5` 用行索引**。

修正后的五档（`-md32m -mt24`，我们和官方在同一轮里交替取三次最小）：

| 档 | 我们（内核镜像） | 官方 | dRatio | 时间 |
| -- | ---------------- | ---- | ------ | ---- |
| m1 | 190 ms / 47.14% | 134 / 54.34% | −7.19 pp | 1.42x |
| m2 | 220 ms / 46.32% | 199 / 46.59% | −0.26 pp | 1.11x |
| m3 | 237 ms / 45.71% | 237 / 42.30% | +3.41 pp | **1.00x** |
| m4 | 337 ms / 43.85% | 362 / 42.14% | +1.70 pp | 0.93x |
| m5 | 359 ms / 43.61% | 371 / 42.10% | +1.52 pp | 0.97x |

markdown 时间比 0.98 / 0.87 / 0.79 / 0.89 / 0.88x，Rust 源码 0.99 / 0.90 / 0.81 / 0.89 /
0.85x。**除内核镜像的 `-m1` 外每档都达到或快过官方同档**，`-m1`/`-m2` 的比率还好于官方。

### 推迟 `LongRange::push`（2026-11-17 深夜）

上一条把"预表 = push"记成结论，这一条把它做掉：独立成员根本不查那张表（`lr_q` 为
None），所以 push 现在**推迟到确实还有下一个成员时**才做 —— 状态里留住上一成员的字节
（超过 `max_hist` 的部分只记数量，用 `LongRange::skip` 推进绝对位置），下一个成员开始时
再索引。**单成员归档因此完全不再付这笔钱**，多成员只多留一个成员。

输出**逐字节不变**，两个方向都核对过：单成员三档大小与改前一致；两成员 solid（各 6.9 MB）
在改前/改后都是 6,504,697 B（m3）与 6,236,710 B（m5），UnRAR 校验通过、解出的字节一致。
预表的变化：m1 52→41、m2 52→47、m3 47→43、m4 112→96、m5 114→103 ms（`-m4`/`-m5` 也受益，
因为 push 与计数排序在同一 pool 上互相争内存）。

**顺带修正上一轮的说法**：`max(链, push)` 的分解比"push ≈ 50 ms"更乱——链的构建只有首波
在关键路径上（24 ms）之后预表仍有 41 ms，其中包含 56 MB `prev` 数组的分配与清零
（~12 ms）以及 pool 的首次唤醒。所以准确的说法是"链与 push 互相遮挡，push 对单成员
完全无用"，而不是某个精确的数值。

剩下的 `-m1` 1.42x 与 `push` 无关：它只在 13.9 MB 成员上出现（另两份 0.98 / 0.99x），
是每位置的解析开销（短匹配源 16 ms、惰性 16 ms、链深度 20 ms，占 103 ms 的 waves）。

### 波序构建，以及"预表其实不是链"（2026-11-17 深夜）

按官方的形状把链改成**按波序增量构建**：`Prev4Index` → `Prev4Builder`，头表就是全部
状态，所以第 w 波读 `prev[..end_w]` 的同时，同一个 `pool.scope` 里另开一个任务填
`prev[end_w..end_{w+1}]`。两段不重叠（worker 不会越过自己的位置，而位置低于 `built`），
所以这个 pass 不花墙钟；输出**逐字节不变**（三份语料大小与改前一致，UnRAR 校验通过）。
`RAR_RS_PREV4_PARTS` 和它测的分片构建一起删掉了。收益 11–19 ms。

**但它同时暴露了我之前记错的一件事**：预表不是链的构建，而是 **`LongRange::push`**。
`prelude = max(链, push)`：链要 48 ms 时量到 53 ms，链只剩首波（24 ms）在关键路径上
之后仍是 52 ms —— 说明 push ≈ 50 ms，链一直在它后面藏着。而**独立成员根本不查那张表**
（`lr_q` 为 None），所以这 ~50 ms 对单成员归档是完全白付的。这是最快几档剩下的最大
一块固定成本，也是下一步该动的地方（把 push 推迟到"确实还有下一个成员"时再做）。

### 比率侧：证据、逆向，以及唯一有效的一档（2026-11-18 凌晨）

**证据**（`cargo run --release --features parallel --example analyze_stream -- <rar>`，
解我们与官方对同一份 9,251,209 B markdown 的 `-m3` 归档）：

| | 我们 | 官方 |
| -- | ---- | ---- |
| packed | 265,242 | **230,825** |
| literals | 45,096 | **32,800** |
| len-2 | 1,407 | **3,555** |
| len-3 | 2,554 | **8,321** |
| len 4-15 | 72,729 | 56,870 |
| 距离 ≥4K 的匹配 | 52,083 | 42,056 |

即：我们的匹配**更多更长，但落在更远的距离上**，literal 反而多 12K。

**逆向**（`FUN_140044794` 的内层按位置循环）：
1. 从 prev1 / prev2 / prev4 三张直接表各取一个候选，按距离闸门记成 2/3/4 字节的 record
   （2 字节档另有 credit：每命中一次 +0x80，其余位置每位置 −1，作用是给短匹配设上限）；
2. 再跑链（`FUN_1400468d4`，只在"严格更长"时升级）和两个长程环形表；
3. 只有拿到匹配才进惰性判决 `FUN_14004600c`（best < 12）或 `FUN_140045b7c` ——
   它会**在 pos+1 用自己的预算再搜一遍**，可以否决当前匹配、退回 literal 或"延迟匹配"。

**试过且为负的三样**（都在新档位上重测）：官方接受闸门（`RAR_RS_WALK_GATES`：内核
6,361,369 → 6,420,608、markdown 265,403 → 276,983）；收紧距离闸门（`RAR_RS_LEN_BONUS`
三档：内核与 markdown 都变差，只有源码略好）；比特定价（旧记录）。同一份证据还说明：
我们的定价 DP（`RAR_RS_MT_DP=1`，m5 41.29%）比官方（42.10%）**低 0.81 pp** ——
**差距全在"贪心 vs 最优"的判决质量上**，不在候选集或闸门。

**有效的那一档**：一步惰性阈值 `WALK_LAZY_MAX` 从 8 提到 64（曲线见 `PLAN.md`）。
它把 `-m1`~`-m5` 的比率各压低 0.1–0.25 pp，代价是 `-m3`/`-m5` 各 +12/+23 ms ——
这两档本来就与官方同档，这点时间花得值。曲线拐点在 32，64 距平台只差 400–700 B。

### 关键发现：比率差距全在 MT walk 的候选深度（2026-11-18 凌晨）

把三条解析路径放在一起量（内核镜像 13,917,568 B，`-md32m`）：

| | 大小 | 比例 | 时间 |
| -- | ---- | ---- | ---- |
| `-mt24` walk（发布） | 6,345,598 | 45.59% | 258 ms |
| `-mt24` 定价 DP（d32） | 5,837,651 | 41.94% | 537 ms |
| `-mt24` 定价 DP（d384） | 5,745,915 | 41.29% | 937 ms |
| `-mt1` 顺序（BT4 树） | 5,848,227 | 42.02% | 3804 ms |
| 官方 | 5,886,560 | 42.30% | 239 ms |

**结论：同一条流水线的定价 DP 与顺序解析器都比官方小**（m5：我们 41.29% vs 官方
42.10%，低 0.81 pp），**唯一比官方大的是 MT walk**，而它慢的原因不是判决规则、也不是
候选结构，而是**候选深度**：`-m1`~`-m3` 只有 2/4/8，`-m4`/`-m5` 是 128/384，而顺序解析器
用的是 BT4 树（等价于很深的搜索）。所以比率差距 = "贪心 + 浅"对"定价 + 深"。

DP 的深度/时间前沿（内核镜像，m4/m5 同配置时结果相同）：d16 42.31%/484 ms、
d32 **41.94%/537**、d64 41.68%/734、d128 41.49%/653、d384 41.29%/937。
**d32 就已经比官方好 0.20 pp**，代价 1.49x；d384 好 0.81 pp，代价 ~2x。
（所以 DP 真正的成本大头是 `collect`，占 38%，它随深度增长；这解释了 d64 比 d128 还慢
的噪声。）

**判决规则本身不是杠杆**（三样都重测）：官方惰性判决 `FUN_14004600c` 的规则单独移植
到 walk 上更差（内核 m3 6,345,598 → **6,427,665**）——因为它和"延迟匹配"机制（顺序解析器
里的 `lazy2`/`pending`，能保留被推迟的匹配）是一对，缺了后者，推迟就等于白丢一个匹配。
官方接受闸门与收紧距离闸门同样为负。**唯一有效的仍是惰性阈值 8 → 64。**

要"达到比率目的"只有两条路，都是策略选择：
1. **把 `-m4`/`-m5` 换成定价 DP**（d32 / d128）：比率比官方低 0.20 / 0.49 pp，时间
   1.49x / 1.79x。
2. **把 DP 做快 ~1.6x**：它的 `collect` 占 38%，而那部分和 walk 共用同一个行索引，
   所以真正的优化面和 walk 的一样（候选查询），不是 DP 本身。

### walk 有一条硬天花板（2026-11-18 凌晨，穷举确认）

"为什么参考了官方还是不如"——把 walk 的每个旋钮都推到极限（内核镜像 `-m3`/`-m5`）：

| 改动 | `-m3` | `-m5` |
| ---- | ----- | ----- |
| 基线（d8, bits20） | 6,345,598 (45.59%) | 6,045,537 (43.44%) |
| 哈希表 20→26 位 | 6,336,042 (45.53%) −0.07 pp | 6,045,359 (43.44%) ±0 |
| 深度 8→384 | 6,133,426 (44.07%)，**1124 ms** | 6,045,537 (43.44%) |
| rep 优先（`FUN_140047698` 的规则） | −486 B | +26 B |

**结论：walk 的天花板就是 ~45.6% / ~43.4%**，与哈希宽度无关、与深度基本无关（深度 384
只换来 1.5 pp，代价 4.6x），rep 规则在这里中性。而**同一批候选**交给定价 DP 就是
41.94% / 41.29% —— 所以差距不是"候选太少"也不是"没照官方做"，而是**贪心本身**：
官方是"贪心 + 很深的候选 + 重锚 + 惰性判决"的组合，其判决质量落在我们的 walk 与我们的
DP 之间。三样判决侧移植（官方闸门、官方惰性判决、rep 优先）在本代码库上都测不出收益。

- **每档的固定成本**：进程启动 48 ms（1 字节成员也一样）、13.9 MB 读+CRC+写 ~15 ms，
  两边一样（官方 50 / 56 ms），所以差距都在编码内部。
- **`-m1` 为什么慢**：不在索引结构——官方 `FUN_140043670` 把链按 `window * 4` 分配、
  `FUN_1400468d4` 按"位置模窗口"走链，与我们一样是每位置 4 字节，另外还有 prev1/2/4
  距离表（1+2+4 字节）——而在**每位置的解析开销**（短匹配源、惰性探针、距离缓存排序
  各占一段，`waves` 里没有一项超过 20%）。
- **`-m1` 的深度不是单调的**：depth 1 反而比 2 慢（主源常常什么都搜不到，于是
  短匹配兜底源在每个位置都跑）。best of five：depth 1 198 ms / 48.21%、
  2 **183** / 47.14%、3 206 / 46.64%、4 220 / 46.32%、6 224 / 45.94%。
- **惰性探针**（`RAR_RS_WALK_LAZY`）：关掉在内核镜像上省 13–21 ms、比率差 0.75 pp。
  默认**保留**——位置索引档已经达到或快过官方同档，剩下的预算换成比率更值。
- **修了两个真 bug**：`mt_slice_symbols_prev4` 原来**没有**长程表探针（solid 链会丢
  跨成员匹配，`solid_members_share_the_window_through_mt` 抓到），而且硬编码
  `WALK_LAZY_MAX`，所以按档设的惰性根本没生效。两处都改成与行索引档同形。
- **测量噪声很大**：同一台机上官方自己的 `-m5` 在 366–435 ms 之间漂。所以选档用
  `RAR_RS_MTTIME` 的 prelude/waves 内部计时，wall 只做参考，且每轮与官方交替跑。

**"预览档"（不建索引 + 短前瞻）的两种形态都试过、都已删除**：

| 形态 | ntoskrnl | markdown | 判定 |
| ---- | -------- | -------- | ---- |
| 不建索引 + 32 KiB 前瞻 | 178 ms / 49.45% | **3,246,179 B**（整窗 244,295） | 文本塌 13 倍 |
| 不建索引 + 整窗前瞻 | 409 ms / 48.25% | 321,420 B | 比索引版更慢且更大 |

第二行是关键：短前瞻省下的只是构建，却要用每片 8 MB 的链播种补回来，净亏。
"按数据自适应前瞻"也不可行——ntoskrnl 自己就有 7.8 万条 4 MB 以上的匹配
（全窗 vs 8 MB 只差 492 B），任何"看起来没有长距冗余"的判据都会判错。

`-m3` 的旧前沿（**可达距离那两行现在只作测量记录**，默认已改回整窗）：

| 配置 | wall | 比例 | 对官方 |
| ---- | ---- | ---- | ------ |
| 无扫描 + 512 K 可达 | 253 ms | 46.23% | 1.04x / +3.93 pp |
| 无扫描 + 8 M 可达 | 282 ms | 44.68% | 1.20x / +2.38 pp |
| 扫描 + 8 M 可达 | 330 ms | 44.05% | 1.40x / +1.75 pp |
| 定价 DP（`RAR_RS_MT_DP=1`） | 617 ms | 41.49% | 1.61x / −0.65 pp |

顺带修了一处**功能回归**：走法原来不查长程表，solid 链因此丢掉跨成员匹配
（`solid_members_share_the_window_through_mt` 直接抓到）。现在走法的候选闭包也
probe `lr_q`，与 DP 同源；独立成员 `lr_q = None`，行为不变。

两个测试因此改为用 `-m4`（它们测的是逐块滤镜决策和 DP 的价格携带，不是快档）。

**注意**：`PLAN.md` 里那张"现有五档到底差什么"的表还是旧档位，待刷新。

下一步（在保持这个速度的前提下继续降比率）：

1. **判决侧**：把官方的自适应价格回喂搬进走法。官方每次只走 2–3 个候选就到
   42.30%，我们要 64 个才 44%——差距在**判决**，不在候选数量。这是最大的一块。
2. **滤镜侧**：用一次廉价探测（成员级"二值 vs 文本"判定）决定发不发 E8E9，
   替掉"整成员盲目套用"，把 0.64 pp 拿回来而几乎不花时间。

### 那 +2.38 pp 到底在哪（`analyze_stream` 对拍，`-m3`）

| 量 | 我们 | 官方 |
| -- | ---- | ---- |
| packed | 6,217,732 | 5,886,390 |
| 字面量 | 2,056,448 | **1,915,966** |
| 匹配数 | 1,320,366 | 1,330,161 |
| len2 | 75,179 | **134,868** |
| len3 | 126,668 | **187,720** |
| dist <4 K | 522,383 | **676,742** |
| 滤镜记录 | 54（全 type 2 E8E9，覆盖 100%） | 220（110 E8E9 + 70 E8 + 40 delta，覆盖 87%） |

也就是说：**官方的匹配更多、更短、更近**——多出 ~6 万个 len2、~6.1 万个 len3、
~15 万个 4 K 内距离，对应少 14 万个字面量。这不是"rep 传播"的形状，而是
**短/近匹配的覆盖**加上**逐块滤镜**。

**这推翻了本轮早先"差距在判决模型/rep 传播"的推断**（那个 1.95% 是 DP 内部做消融
得到的，不等于我们能从走法里把它抠出来）。按这个证据，下一步的性价比排序变成：

1. **短/近匹配覆盖**（最大一块）：走法在"有 ≥4 字节候选"时完全忽略短候选，
   而官方大量用 len2/len3 的近匹配去替代字面量。要把短候选按"省下的比特"参与
   选择，而不是只当兜底。
2. **逐块滤镜**（0.64 pp，已知代价 44–58 ms）：或者做一次更便宜的逐块判据。
3. rep 传播：优先级下调——没有数据支持它是这里的主因。

### 按第 1 条做的尝试：按比特节省选候选（已做，实测为负）

`RAR_RS_WALK_PRICED=1` 让短候选与长候选一起按 `8*length - 槽位估算成本` 竞争
（成本 = 长度槽号 + 额外位 + 距离槽号 + 额外位，缓存距离记 2 bit）。

结果 **更差**：`-m3` 6,217,902 (44.68%) → **6,291,522 (45.21%)**。

原因：**槽号不是码长**，而且一条"省 8 bit"的 2 字节匹配同时挤掉了原本 4 字节
匹配覆盖的那两个字节。这和 `non-dp-plan.md` 里"短视界 DP 输给走法"是同一个结论：
**贪心没有真实熵模型可定价**，能定价的是定价 DP——也就是我们留在 `-m4`/`-m5`
的那两档。

所以走法要再降比率，只剩"把真实价格表搬进走法"这一条（走法现在完全没有价格表，
要先按块 `convert_tokens` 回喂）——但那正是被 `RAR_RS_MT_RULE` 量过只值 0.5%、
并且会吃掉 1/3 速度的东西。**在"速度优先"的前提下，44.68% / 1.19× 已经接近这条
架构的实用前沿。**

### 又两个按诊断做的尝试（都实测为负）

1. **官方的接受闸门**（`RAR_RS_WALK_GATES=1`）：把 `FUN_140044794` 的距离加权规则
   原样搬进 `walk_best`——`prev2`（3 字节）要 `dist ≤ 0x2000` 且
   `best < 2 || dist < best_dist<<7`，`prev4`（4 字节）要 `dist ≤ 0x40000` 且
   `best < 3 || dist < best_dist<<6`，链上要 `len > 4 && (len > best+1 ||
   dist>>5 ≤ best_dist)`。
   **更差：6,217,902 (44.68%) → 6,252,827 (44.93%)。** 它的闸门是围绕官方自己的
   候选类（prev1/prev2/prev4 + 5 字节链）和自适应价格调的；对"4 字节桶 + 两张
   head 表"来说，距离偏好只是把本来能用的长度丢掉了。
2. **发射块缩小**（`RAR_RS_EMIT_BLOCK`）：官方 219 块（均 27 KB），我们 119 块。
   32 K → 6,218,421（略差），16 K/8 K → 6,248,572（更差）。成帧不是我们的问题。

（过程中还抓到自己的一处 bug：闸门里的 2/3 字节候选没按剩余 span 截断，会越过
块尾让整条距离流错位——`UnRAR t` 报 checksum error。已按 `max_length` 截断。）

因此**本轮的三个"判决侧"尝试全部为负**，走法的最优解仍然是"取最长"。剩下能动的
只有实测有效的两个旋钮：可达距离（约 20 ms/点）和逐块滤镜（0.63 pp / 28 ms）。
