## 根因一：行索引报不出短匹配

`RowIndex::collect`（`parse/optimal.rs`）只把 `length >= 4` 的候选写进
`runs`——因为它按 4 字节哈希分桶。于是 MT 走法在 13.9 MB 内核镜像上**只发出
1 条** 2/3 字节匹配，MT 的 DP 也只有 ~13.5 K，而我们自己的顺序路径有 ~155 K，
官方有 ~275 K（`analyze_stream` 的 `short_dist` 行）：

| 流 | len2 | len3 |
| -- | ---- | ---- |
| 官方 m3 | 113,693 | 161,206 |
| 我们 m3（顺序） | 75,908 | 79,320 |
| 我们 m3（MT/DP） | 1,904 | 11,580 |
| 我们 m1（走法，改前） | **0** | **1** |
| 我们 m1（走法，改后） | 57,538 | 68,549 |

短匹配便宜是因为**长度加成**把距离卡得很死（`length_bonus`）：raw length 2 只能
距离 ≤ 0x100，raw length 3 只能 ≤ 0x2000。也就是它们永远在 8 KiB 内，顺手的
直映射表就能找。

## 修法一：`ShortHeads`

新增 `ShortHeads`（`parse/optimal.rs`），两张直映射表：

- `head1[256]`：每个字节值最近出现的位置 → 官方 `prev1` 的 2 字节候选；
- `head2[65536]`：每个 2 字节前缀最近出现的位置 → 官方 `prev2` 的 3 字节候选。

在 `windowed_walk_parse` 里按位置增量维护（每位置 2 次随机写，表 256 B + 256 KB
常驻 L1/L2），并从 `span.start - 0x2000` 起播种前瞻（raw length 3 的上限就是
0x2000）。≥4 的匹配仍归行索引。

**关键：短候选只能是「兜底」，不能参与竞争。** 让它们和长候选一起进「取最近的
接近最长者」，会把一条距离 10 的 2 字节匹配顶掉真正的 4 字节匹配（`length + 3 >=
longest` 那条容差本是为 rep 距离留的），实测反而变差：46.11% 对 45.75%。

## 根因二：走法的「近者优先」是错的

`walk_best` 原来取最长候选，再在「够得着」（`length*4 >= longest*3` 或
`length+3 >= longest`）的范围里改取**最近**的。官方不这么做——它的链规则是
**只把 best 变长**（`len > best+1 || dist>>5 <= best_dist`），从不为了更近而变短。
把这条对齐（`RAR_RS_WALK_NEAR=0`，现为默认）在三个语料上都是纯收益，且基本免费。

## 修法三：DP 也接上短匹配

`windowed_priced_parse` 的候选同样只来自行索引，所以 MT 的 DP 也缺 2/3 字节
候选（~13.5 K 对顺序的 ~155 K）。把同一份 `ShortHeads` 接进去：在块循环里按位置
增量维护（位置是顺序访问的，一趟前向就够），并把短候选**插到该位置的 run 段首**
（`matches.runs.insert(before, ..)`），保持它「长度递增」的次序——DP 就是按这个
次序理解「候选逐步变长」的。

结果见上表：`-m3` 5,878,581 → 5,801,341（−0.56 pp，+4% 时间），四档一致，
MT 与顺序的缺口从 100 KB 收到 23 KB。计数器顺手把 `walk_short_enabled` 改名
`short_sources_enabled`（两处共用）。

## 官方形状的逆向（ghlab，本轮补的）

- `FUN_140044600(job, pos, len, ...)` 不是决策者，是**记录 → token 的转写器**：
  遍历 job+0x1a0 的 32 字节记录（`{+0x1a0 pos, +0x1a8 len, +0x190 class}`），只处理
  落在 `[pos, pos+len)` 的记录，把 class 0/1/2/3 映射成「新距离 / rep1 / rep2 /
  rep3」的 token（`0x30007` + 槽号；新距离走 `FUN_140047d20`）。**决策在并行段**。
- `FUN_140044794(job, sub)` 是并行 worker：一次处理 `job+0x10` 字节，按 **0x1000
  (4096)** 切子块；每次调用把四个 rep 距离（`+0x300e0…f8`）清零；每位置依次取
  `prev1`(2 字节) / `prev2`(3 字节) / `prev4`(4 字节) / `FUN_1400468d4`(5 字节哈希链)
  的候选，然后用一步惰性（`FUN_14004600c` / `FUN_140045b7c`）决定是否发出；
  发出后 `local_res10 += best_length`（**跳过被覆盖的字节**）。
- 候选的接受规则带强烈的距离偏好：`prev2` 要 `dist <= 0x2000` 且
  `best < 2 || dist < best_dist<<7`；`prev4` 要 `dist <= 0x40000` 且
  `best < 3 || dist < best_dist<<6`；链上要 `len > 4 && (len > best+1 || dist>>5 <=
  best_dist)`，并在 `best_dist*0x4000 < dist && len < best+5` 时提前 return。
- `FUN_140047698` 是四槽 rep 裁决器（`len > 1`、`len >= best-3 || len*4 >= best*3`、
  以及 best-1/-2/-3 的 0xff/0x7ff/0x7fff 边界），与我们的走法一致。

结论：官方**就是**「受限候选 + 一步惰性 + 跳过」的贪心，没有任何 DP。它的
42.30% 说明贪心**能做到**；我们仍差 1.74 pp，缺的是候选类（5 字节链 + 环形/长程
两条附加源）、`FUN_140044794` 里那条「同一长度取最近」的后续扫描、以及一步**延迟**
裁决（当前只做了一步前瞻）。

## 速度：固定开销就是全部差距（2026-11-17 下半场）

同一份 ntoskrnl、`-md32m -mt24`，交错测（各 2 次取最小）。「WALK」= 强制走法
解析（`RAR_RS_MT_WALK=1`，即把走法放到该档）：

| who | -m1 | -m2 | -m3 | -m4 | -m5 |
| --- | --- | --- | --- | --- | --- |
| 我们 DP | 326 / 44.04% | 508 / 42.08% | 546 / 41.68% | 591 / 41.49% | 747 / 41.29% |
| 我们 WALK | — | 309 / 44.43% | 329 / 44.04% | 335 / 43.85% | 363 / 43.61% |
| 官方 | 124 / 54.34% | 192 / 46.59% | 240 / 42.30% | 384 / 42.14% | 373 / 42.10% |

阶段账（`RAR_RS_MTTIME=1`，m3）：

| 阶段 | m1 | m3 | 官方 |
| ---- | -- | -- | ---- |
| 启动 + 读 + CRC + 写 | ~52 ms | ~52 ms | ~56 ms |
| `best_combined_specs`（滤镜扫描） | 57 | 49 | **0** |
| 预表（`LongRange::push` + 行索引） | 109 | 96 | **0** |
| 换能（`forward_transform`） | ~21 | ~21 | 含在内 |
| waves（解析 + emit） | **99** | 329 (DP) / ~180 (走法) | ~176（整包） |

三条能落到纸上的事实：

1. **IO/启动与官方持平**（52 vs 56 ms），不是问题。
2. **走法的解析（99 ms）比官方整次 `-m3`（240 ms）还快**。走法慢是因为它多付
   ~166 ms 的预表 + 滤镜扫描，官方一次流式通过里顺手做完。
3. **我们的墙钟地板 ≈ 310 ms**（最快配置），而官方 `-m3` 是 240 ms。在官方
   `-m3` 及以下，我们的固定开销单独就超过对方整次运行，**不可能追上**；官方
   `-m4`/`-m5`（384 / 373 ms）我们可以持平甚至更快。

速度对齐点（等速比比率）：

| 对齐 | 我们 | 官方 | Δratio |
| ---- | ---- | ---- | ------ |
| 官方 -m4（384 ms） | WALK -m5 363 ms / 43.61% | 384 ms / 42.14% | +1.47 pp |
| 官方 -m5（373 ms） | WALK -m5 363 ms / 43.61% | 373 ms / 42.10% | +1.51 pp |

所以「速度达到官方」在 `-m4`/`-m5` 已经成立（还略快），代价约 1.5 pp；`-m1`–`-m3`
做不到，瓶颈是那 166 ms 固定开销，**不是解析**。

### 本轮为本轮加的两个旋钮

- `RAR_RS_MT_WALK=1`：把走法解析放到任意档（速度优先映射用）。
- `RAR_RS_RI_BITS`：行索引桶位数（12–26，默认 20）。桶数是**构建局部性**的旋钮：
  桶越少散写越集中、构建越快（14/16/18/20 bit 的 prelude 实测 51/64/82/138，
  waves 246/217/176/131），但桶内哈希碰撞变多、解析要多比较（waves 反涨），
  **净和基本持平**，故默认仍是 20。规模表（walk -m3）：14 bit 448 ms/44.96%、
  16 bit 421/44.23%、18 bit 409/44.07%、20 bit 413/44.04%、22 bit 563/44.04%。

结论方向不变：要追官方 `-m3` 及以下，必须让滤镜扫描与行索引不再是「读之外
的独立两趟」——官方没有成员级索引、没有成员级滤镜扫描，它用 128 KiB 子块 +
增量哈希链一次流式做完。这是结构改动，不是调参。

### 换能（`forward_transform`）已并行

`forward_transform` 原来把 187 条记录串行地一条条换能（`data.to_vec()` 之后再
逐区域 `apply_filter_encode`）。区域互不相干，所以现在先验证 records 是**有序、
不相交、在界内**，再切成不相交的 `&mut [u8]`，用 `par_iter_mut` 各换各的；任何
一条不满足（强制单区域、手工拼的 spec 列表）就退回原来的串行循环，字节不变。
实测归档大小逐字节相同（6,129,621 / 5,801,341），`UnRAR t` 通过；m1 的 wall
在 6 次交错里平均 422 → 407 ms（最小 328/332 在噪声内），即省 ~8–15 ms。
开关 `RAR_RS_PT=0` 退回串行，用于 A/B。

顺带试过、**实测无收益故已回退**：把 `build_split` 里那次串行 merge（八张计数表
逐桶求和）并行化。归档字节相同，但 prelude 在 107–112 ms 之间不动——本机上
prelude 的地板是那 140 MB 索引数组的首次写入（页错误 + 带宽），不是这 18 ms。

### 预表砍不掉：它被查询赚回来了（2026-11-17，本轮的决定性实验）

按「速度优先」去砍那 ~107 ms 的 prelude：加 `RAR_RS_NOINDEX=1`，跳过
`RowIndex::build`，退回每切片链（`mt_slice_symbols_low_step`，尾长由
`RAR_RS_NEAR` 控）。ntoskrnl、`-m1 -md32m -mt24 -mc-`（`-mc-` 把滤镜扫描也去掉，
纯比 prelude ↔ waves）：

| 候选源 | prelude | waves | wall | size |
| ------ | ------- | ----- | ---- | ---- |
| 行索引（现状） | 113 ms | **109 ms** | **308 ms** | 6,590,352 |
| 每切片链，8 MB 尾 | **32 ms** | 270 ms | 449 ms | 7,367,607 |
| 每切片链，2 MB 尾 | 31 ms | 309 ms | 431 ms | 7,367,607 |
| 每切片链，512 KB 尾 | 33 ms | 272 ms | 405 ms | 7,367,607 |
| 每切片链，128 KB 尾 | 33 ms | 273 ms | 438 ms | 7,367,607 |

**链省下 81 ms 的 prelude，却要赔 161 ms 的 waves 和 11.8% 的体积**（链尾长短
几乎不影响体积——瓶颈不是可达距离）。所以**成员级索引的构建费是被它自己的查询
赚回来的**。

### 链不是被可达距离限制的：与「同可达距离的行索引」对照

为公平起见，加 `RAR_RS_WALK_REACH`（把行索引候选裁到任意距离）做对照，并给
`MatchFinder` 补一个多候选探针（`collect_candidates`：把链上每一跳里改善的
`(len, dist)` 都推出去，形状与 `RowIndex::collect` 相同——原来的 `find_match`
只给一个候选）。`-m1 -md32m -mt24 -mc-`：

| 可达 | 行索引 | 链 |
| ---- | ------ | -- |
| 8 MB | 6,590,706 (47.36%) | 7,200,745 (51.74%) |
| 2 MB | 6,645,663 (47.75%) | 7,254,612 (52.13%) |
| 512 KB | 6,767,408 (48.62%) | 7,331,093 (52.68%) |
| 128 KB | 6,923,418 (49.75%) | 7,385,344 (53.06%) |

**同一可达距离下链一律差 ~4 pp**，而且链的深度几乎无用（探针深度 16/64/256/1024
→ 52.71/52.68/52.67/52.67%），所以不是碰撞、也不是走得太浅。速度上链也不赢：
512 KB 尾的链 wall 296 ms，而 512 KB 可达的**行索引**只要 241 ms。

结论：**「每切片链」这条架构路被「把行索引的可达距离裁短」严格支配**——后者
更快、更好，而且不需要新结构。链的代码留在 `RAR_RS_NOINDEX` 下作复现用。

### 可达距离是个真旋钮（走法，默认滤镜）

`RAR_RS_WALK_REACH`（字节）：

| ---- | ---- | ---- | ---- | ---- | ---- | ------ |
| wall | 331 | 323 | 321 | 304 | 312 | 305 |

即：**裁到 8 MB 几乎白送 8 ms，裁到 512 KB 换 ~26 ms 要赔 1.55 pp**。它有真
收益但很小——因为墙钟被固定开销压着（见下）。

### 走法的深度旋钮几乎不花时间

`RAR_RS_MT_WALK=1` + `RAR_RS_MT_DEPTH`（m1，ntoskrnl）：

| depth | 4 | 8 | 16 | 32 | 64 |
| ----- | - | - | -- | -- | -- |
| wall | 311 | 311 | 304 | 324 | 324 |
| size | 6,361,746 | 6,276,100 | 6,212,324 | 6,165,011 | 6,129,621 |

深度 4→64 只值 13 ms —— 走法的墙钟由固定开销决定，不由候选深度决定。所以
**「用比率换速度」在本架构里几乎换不到速度**。

即：**目前能达到的最快是官方 `-m3` 的 ~1.2×**，代价约 +5 pp。要再往下只剩

### 官方的形状：位置索引的 prev4（做通了，但被行索引支配）

逆完 `FUN_14004264c`（官方顶层 MT 驱动）后，结构定死了：一波 = 线程 × 128 KiB，
每 worker 一个 128 KiB 子块，worker 内部按 4096 字节决策；**它的 prev1/prev2/prev4
和 5 字节链是在解析的同时就地插入的（先查后插）**，所以官方**没有单独的建索引趟**。
这才是我们那 ~107 ms prelude 的对手：不是"换个结构"，而是"表按位置写、边解析边写"。

按这个形状做了 `Prev4Index`（`RAR_RS_PREV4=1`，配合 `RAR_RS_MT_WALK=1`）：
`prev[pos]` = 到上一个同 4 字节哈希位置的距离，**写在位置自己的下标上**，所以构建
是一趟线性、顺序写的 pass（分片并行，各写各的区间）。

**先记一个真 bug（本轮抓到并修好）**：`prev` 存的是**相对步长**，第一版却每次都从
`pos` 出发算 `candidate = pos - prev[candidate]`——一跳之后就落到 `pos - step` 这个
错误且通常很近的位置。表现是"远距离匹配几乎全部消失"（`dist_hist` 的 4M+ 从 92,131
掉到 12,086），而在它上面量出来的"248 ms"是假象：链几乎什么都没找到，所以快。
修法是记住 `candidate`、每跳 `candidate -= prev[candidate]`。

抓它的工具是**仓库自己的测试缝**：`prev4_candidates_match_the_row_index`
（`#[ignore]`，`RAR_RS_PREV4_CMP_FILE=<corpus>` 指向语料）把两种索引建在同一份数据上，
逐位置对比 `collect` 的 `runs`。修前 13,917,564 个位置里 5,351,705 个不一致，修后 **0**。
这个测试留下来当护栏，命令就在函数文档里。

修好后的实测（ntoskrnl 13,917,568 B，`-m1 -md32m -mt24`）：

| 候选源 | prelude | waves | wall | size |
| ------ | ------- | ----- | ---- | ---- |
| 行索引（现状） | 100 ms | 109 ms | **362 ms** | **6,129,621 (44.04%)** |
| prev4，1 片（精确） | 51 ms | 319–337 ms | 536 ms | 6,129,621 (44.04%) |
| prev4，2 片 | 35–41 ms | 233 ms | 412 ms | 6,185,728 (44.45%) |
| prev4，4 片 | 35–36 ms | 177–182 ms | 354 ms | 6,271,612 (45.06%) |
| prev4，8 片 | 39–40 ms | 134–147 ms | 334 ms | 6,331,047 (45.49%) |
| prev4，16 片 | 53 ms | 106 ms | 295 ms | 6,431,294 (46.21%) |
| prev4，24 片 | 51 ms | 75–82 ms | 292 ms | 6,486,839 (46.61%) |

**1 片时 prev4 与行索引逐字节相同**（6,129,621 / 44.04%）——说明修好之后两者候选
完全等价，这条对照是可信的。

**结论：链的查询比桶的查询贵约 3 倍**（同等候选下 waves 319 vs 109），所以构建省下的
（107 → 35–51）正好被查询吃掉。分片能换速度，但每片各自播种空 head 表、链在片边界
断掉，比率就往下走。最优点（4 片：354 ms / 45.06%）仍然**被行索引（362 ms / 44.04%）
支配**。这和 PITFALLS 里"查询必须连续、构建必须散写"那条旧结论一致，本轮第一次用
修正后的链和精确数字把它钉死。

### 速度优先的默认档位（已落地，用户批准）

三处改动：

1. **`-m1`..`-m3` 走 walk 解析**（`WALK_MAX_LEVEL = 3`），`-m4`/`-m5` 保留定价 DP
   ——顶档仍是最好的比率，档位阶梯才有意义。
2. **走法的可达距离按档递增**（`WALK_REACH` = 512 K / 2 M / 8 M），DP 档仍用整个
   窗口。这是走法档唯一还剩下的速度/比率分离旋钮，而且很划算：同一档下 512 KB
   6,434,014 B / 252 ms、2 MB 6,287,387 / 266 ms、8 MB 6,217,902 / 283 ms
   （约 20 ms 换一个点），而 8 MB 距全窗 32 MB 只差 492 B。
3. **滤镜**：`-m1`..`-m3` 不再做逐块扫描，改发**一条整成员 E8E9 记录**；
   `-m4`/`-m5` 保留扫描。`RAR_RS_FILTER_SCAN=0/1` 可强制。
   依据：逐块扫描（213 块 × 13 条通道）要 44–58 ms，但在内核镜像上只买到 0.64 pp，
   在 Rust 源码和 Markdown 上是 **0 字节**（文本 186 → 127 ms，体积不变）。

实测（ntoskrnl 13,917,568 B，`-md32m -mt24`，两次取最小）：

| 档 | 我们 | 官方 | dRatio | 时间 |
| -- | ---- | ---- | ------ | ---- |
| m1 | 258 ms / 46.23% | 138 / 54.34% | −8.11 pp | 1.87x |
| m2 | 282 ms / 45.49% | 189 / 46.59% | −1.09 pp | 1.49x |
| m3 | 286 ms / 44.68% | 240 / 42.30% | **+2.38 pp** | **1.19x** |
| m4 | 658 ms / 41.49% | 364 / 42.14% | −0.65 pp | 1.81x |
| m5 | 910 ms / 41.29% | 408 / 42.10% | −0.81 pp | 2.23x |

**`-m3` 现在是 1.19× 官方、+2.38 pp**（可达距离加宽之前是 1.10× / +3.93 pp，即用
24 ms 换了 1.55 pp）。`-m4`/`-m5` 仍是比率档，比官方小 0.65–0.81 pp。

剩下 +2.38 pp 的分解：整成员 E8E9 而不逐块 ≈ 0.64 pp（只能靠更便宜的逐块判决拿回，
采样类做法已被否），其余 ≈ 1.7 pp 是**走法判决模型与定价 DP 的差**——DP 的优势是
块内整段最优路径 + 逐节点 rep 传播，而那正是我们为速度放弃的东西。

顺带修了一处**功能回归**：走法原来不查长程表，solid 链因此丢掉跨成员匹配
（`solid_members_share_the_window_through_mt` 直接抓到）。现在走法的候选闭包也
probe `lr_q`，与 DP 同源；独立成员 `lr_q = None`，行为不变。

两个测试因此改为用 `-m4`（它们测的是逐块滤镜决策和 DP 的价格携带，不是快档）。

**注意**：`PLAN.md` 里那张"现有五档到底差什么"的表还是旧档位，待刷新。

下一步（在保持这个速度的前提下继续降比率）：

1. **判决侧**：把官方的自适应价格回喂搬进走法。官方每次只走 2–3 个候选就到
   42.30%，我们要 64 个才 44%——差距在**判决**，不在候选数量。这是最大的一块。
2. **滤镜侧**：用一次廉价探测（成员级"二值 vs 文本"判定）决定发不发 E8E9，
   替掉"整成员盲目套用"，把 0.64 pp 拿回来而几乎不花时间。
