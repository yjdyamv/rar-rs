## 结论：官方快在哪（已用采样器实测，不是猜）

自建采样剖析（无管理员权限、无 ETW）给出的官方 m3 函数占比：
搜索 `FUN_1400468d4` **57.7%**、字节直方图 `FUN_1400413dc` 10.5%、rep/最佳裁决
`FUN_14004600c` 9.9%、每位置包装 `FUN_140044794` 5.1%、Huffman 2.2%、解析 2.3%。

- 官方搜的是**哈希链**（每位置 1 个 u32 后继，5 字节哈希），不是二叉树；
- 一次搜索只走 2–3 步（预算 100，`budget>>2`=25 的远预算，>11 字节立刻收工）；
- 三张**全窗口**短表（2/3/4 字节）+ 8 个按**哈希域**分的类表（不是距离类，早先文档写错过已更正）；
- 主循环是**真贪心**：找到匹配就 `pos += best_len`，因此搜索位置数只有 3.45 M；
- 解析极便宜（2 ns/位置）：候选数组 + 一步惰性 + `FUN_140047698` 的 rep 判价，**没有代价 DP**；
- 成帧更碎（块均 26.9 KB / 219 块 vs 我们 55 KB / 106 块）、滤镜 220 条（类型 0 带通道/1/2）vs 我们 52 条（全类型 1）。

我们的对应量：`walkbench` 拟合每步 **15.8 ns**、每位置固定 **36.5 ns**；默认路径 13.1 M 次搜索、
5.2 步/次；融合路径 5.8 M 次（惰性）/ 4.2 M（贪心）。

## 已被实测否掉的方向（别再试）

1. **8 个距离类（8 棵独立树）**：collect +18%、比例 +0.56 pp。见 ADR「P2 结果」。
2. **共享 son + 8 份类表头（官方形态之一）**：+193% 时间、比例持平。见 ADR「P2'」。
3. **照官方写哈希链（近者优先）**：17.1 步/位置 vs 树 5.2，collect 4593 ms、45.39%。见 ADR「官方形态的哈希链」。
4. **按距离类产出候选**：比例不动、时间 +6–9%（树的一次下降只进一个内容子树，沿途节点几乎同属一类）。
5. **官方 look-ahead（跳过 len-5 个链节点）**：steps 变多、比例更差（我们的命中只有 27–33 字节）。
6. **信用计数节流**（官方 `+0x300b8/+0x300bc`）：融合路径上实测惰性，比例差 0.01 pp。
7. **桶表位宽**（`HASH_BITS` 20…26）：比例完全不变，只影响步数；21/23/24 都在同一噪声带。
8. **块粒度**（`RAR_RS_EMIT_BLOCK` 32/64 KiB）：只值 0.04 pp。
9. **免越界检查的裸指针 descent**：LLVM 早已消掉那些检查，无收益。
10. **`FUN_14004600c` 的判价移植（`RAR_RS_LAZY2`）**：0.16 pp。官方最后一个未逆函数也只值这么多。

## 逆向定案与链式实验（2026-11-16）

`Rar723.exe` 反编译定案：m3 的匹配器是 `FUN_1400413dc`（一次顺序插入 2/3/4/5 字节链，
`prev` 在 `+0xb1e8`…`+0xb200`），解析是 `FUN_140044794`（短链各取最近一个 + 5 字节链走
≤ `DAT_1400baf58[m]` 步 + 一步懒匹配 + **跳过匹配覆盖的字节**），**没有树、没有 DP、没有
价格表**。搜索预算 m3 = 100（失配快模式 25）。

在本仓库照搬「链 + 保留 DP」（`RAR_RS_CHAIN`，见 ADR 0011 同名一节）：

| 形态 | 体积 | 比例 | 时间 |
|---|---|---|---|
| 树 + DP（默认） | 5,780,209 | 41.53 % | 3,985–5,805 ms |
| 链 18 + 距离闸门 | 6,395,029 | 45.94 % | 2,630 ms |
| 链 100 无闸门 | 5,914,173 | 42.49 % | 6,233 ms |
| 链 100 SPAN=8 | 5,938,227 | 42.66 % | 5,611 ms |
| 官方 `-mt1` | 5,886,469 | 42.30 % | 1,422 ms |

结论：链喂不饱 DP（3 个候选达不到代价最优），这条路的比例要 6.2 s 才追平，比树还慢。
官方 42.30 % / 1.42 s 来自**贪婪决策 + 跳步**，不是候选更多。下一步把
`RAR_RS_INTERLEAVE` 的融合路径按 `FUN_140044794` 的规则重写（懒匹配阈值、
`dist < bestdist<<7/<<6` 闸门、`best < 0xc` 与否则两套懒检查、发匹配后 `pos += len`），
再用工程工具复算 2200 ms 那条线。

## 下一步：时间线的 1.8 s 在搜索次数，不在滤镜

`RAR_RS_PROFILE=1`（ntoskrnl m3，默认构建）：collect 2,313 ms（66 %）、dp 935 ms（27 %）、
prep 116、emit 101、convert 31；墙外还有 ~0.5 s 是滤镜（0.43 s）与 CRC/IO。
计数 positions 13.92 M / searches 12.62 M / steps 75.4 M（6.0 步/次）。官方是 3.45 M 个
搜索位置、2–3 步/次。

- 比例线已经满足（41.53 % < 42.5 %）；`RAR_RS_COMMIT=16` 用 0.64 pp 换 0.6 s，
  仍在线上（42.17 % / 3.35 s）。
- 时间线要的是**搜索次数**：DP 要求每个位置都有候选。融合路径（2.7 s / 45.74 %）用
  跳过定价买到时间，赔 4.2 pp。要么让 DP 在「确定不需要候选」的位置跳过（不只是
  COMMIT 的「已覆盖」），要么让融合路径的判价便宜到接近 DP 的质量。
- 别再调常数：步数与时延线性（STALL(2,2) 步数 −14.5 % → collect −12.5 %），每步
  15.8 ns 是 64 MB `son` 数组的随机访问；覆盖抽样（`RAR_RS_HEUR_SAMPLE`）只省
  0.1 s 却赔 KB。
- 两条曲线没有交点（2026-11-15 夜补测）：DP 路径在 ≤42.5 % 内的地板是
  COMMIT=12/16 的 3.18–3.35 s；到 2.2 s 要 COMMIT≈5，比例 45–46 %。融合路径地板
  2.19 s / 47.4 %。STOP（搜索够长即停）在两者之间画出同一条线（STOP=24 → 42.21 % /
  3.53 s），也不是出路。
- 结构差异：官方主匹配器是 2/3/4 字节哈希表（O(1) 候选，3.45 M 位置、2–3 步），BT4
  只是补充；我们是树独占（6.0 步/次），`ShortFinder`（`collect.rs:194`）只补 2/3 字节。
- **「哈希表做主候选、树做下沉」已经试过（`RAR_RS_HASH4`，05d5ad5）**：四字节表全开
  时 5,756,583 B / 41.36 %（比默认小 0.17 pp）但要 4.5 s；只开表 6,425,256 B /
  46.17 % / 1.9 s。结论：表能买比例、买不到时间——单候选喂不饱代价 DP，它要同一
  位置上的多个距离与长度档。**真正的瓶颈是「每个位置都要候选」这件事本身**：官方
  3.45 M 次搜索拿到 42.30 %，说明它的定价循环在多数位置上根本不问候选。
  下一步的方向因此是改定价策略（哪些位置值得问、问几档），而不是候选来源。
