# 非 DP 走法分支：目标、证据与实验清单

> **状态（2026-11-18）：本文件是开分支时的计划，保留作出发点。**
> 目标里的「比率损失控制在 1% 以内」**没有达到**（最终内核镜像 `-m3` 差 +3.17 pp
> / 体积 +7.5%）。最终状态、实测与 被排除的方案见
> [`handoff-2026-11-17.md`](./handoff-2026-11-17.md) 的
> 「最终状态」与「现状与剩下的路」。

分支：`exp/non-dp-official-shape`（从 `6839ec3` 开出）

目标：用 WinRAR 7.23 的候选类 + 自己的优化，做到官方速度（ntoskrnl 13.9 MB、
`-m3 -md32m -mt24` 约 295 ms / 5,886,560），比率损失控制在 1% 以内。

## 已经把路走死的事实（不必重试）

| 实验                             | 结果                                          | 结论                        |
| -------------------------------- | --------------------------------------------- | --------------------------- |
| 规则走法 + 行索引链，depth 64    | 6,291,756（+7.0%），波次 73 ms                | 提交即跳过的走法丢 7%       |
| 上述 + 官方四类候选（prev1/2/4） | 6,393,561（+8.8%）                            | 短候选反而更差              |
| 上述 + 一位置延迟裁决            | 无变化                                        | 缺的不是 lazy               |
| 上述 + 真实价格排序              | 6,323,060（+7.5%）                            | 规则只值 0.5%，砍在跳过上   |
| prev 表替代行索引（7–12 B/位置） | 预表 152–163 ms（比 85 ms 更慢），波次 291 ms | 串行 head 依赖 + 依赖随机跳 |
| 每位置计价步数 12→6              | 时间不变，比值 +0.15%                         | 不是 DP 的开销来源          |

**核心结论**：走法的 7% 损失不是"决策规则不够好"，而是"提交后跳过 L−1 个位置"
本身——被跳过的位置里藏着 rep/cache 链，DP
在那里能选一条局部更差但全局更好的路径。
官方能扛住这一点，是因为它的判决对着自适应 Huffman 价格做，且子块只有 4096 字节
（`FUN_140044600`
在每个子块边界重做裁决）。要逼近它，必须在跳过与计价之间取中间态。

## 已确认的固定开销账（ntoskrnl，`-m3 -md32m -mt24`）

| 项                                      | 耗时       | 备注                           |
| --------------------------------------- | ---------- | ------------------------------ |
| 进程启动                                | 67 ms      | 官方 90 ms                     |
| 读入 + CRC + 写出                       | 68 ms      | 1 MiB `BufReader` + SIMD crc32 |
| 筛选（`best_combined_specs`）           | 48 ms      | 187 个 spec                    |
| 预表（LongRange + RowIndex，并行 join） | 106–113 ms | RowIndex 占 85 ms              |
| 波次（DP，depth 64）                    | 293 ms     |                                |
| 合计                                    | 585 ms     | 官方整次 295 ms                |

**波浪外固定开销 ≈ 296 ms 已经等于官方整次运行的 295 ms。** 任何走法路线都必须
同时砍掉预表，否则即便解析归零也到不了官方速度。

## 分支上的候选方向（按预期收益/风险排序）

1. **短视界 DP（推荐首试）**：在走法的每个提交点，用 DP 只评估"当前匹配 + 后面 H
   字节"（H ≈ 24–64），取第一步后跳过。跳过的位置里有 rep 链时能选对，成本是 每
   H/avg_len 次小 DP。目标是拿回 7% 里的 4–5%，波次控制在 150 ms 内。
2. **rep/cache 链优先的走法**：提交前先问"这个位置若用 rep 距离能延伸多长"，
   若能延伸 ≥ 当前最长匹配的 3/4 就走 rep 而不是新距离。官方 `FUN_140047698`
   就是这个形状；我们的走法已实现裁决器但只在**已经选出** best 之后才问，
   顺序反了，先问 rep 能省掉新距离的整段计价。
3. **预表与筛选合并**：筛选已经顺序扫一遍成员（`block_stats`），行索引构建也是
   顺序扫一遍。两者在同一趟里做，预表可以摊到筛选的 48 ms 里，省掉一部分墙钟。
4. **子块级重裁决**：官方子块 4096 字节。我们的 DP 块 48 KiB。把走法按 4096 字节
   分段，每段结束时用 `convert_tokens` 后的频率回喂价格，让走法的判决逐步逼近
   自适应价格——这是"自己的优化"里最贴近官方机理的一条。

## 度量协议（必须遵守）

- 每次重建后第一次运行是冷缓存，丢弃，取第二次。
- 机器会漂（已见 ±35%），基线/改动/基线必须交错测量。
- `rar a` 是追加语义，每次计时用新的归档路径。
- 不要用 `cmd | head`，SIGPIPE 会杀掉写入进程并留下不存在的归档。
- 参考值：DP 基线 585 ms / 5,878,519；官方 295 ms / 5,886,560。

## 实验 1：短视界 DP（已做，否定）

在走法的每个提交点对 `[pos, pos+H)` 跑一次小 DP（代价模型：字面量 8 bit/字节，
匹配 ≈ `2*log2(dist) + log2(len) + 4` bit），取路径最后一个被窗口截断的 step
之前 全部提交，剩余一位仍由走法决定。

| 配置                 | 波次       | 大小          |
| -------------------- | ---------- | ------------- |
| 短视界 DP h=64 d=64  | 201–205 ms | 6,376,220     |
| 短视界 DP h=128 d=64 | 196–199 ms | 6,333,114     |
| 短视界 DP h=256 d=64 | 193–207 ms | 6,309,570     |
| 短视界 DP h=64 d=4   | 108 ms     | 6,650,726     |
| 短视界 DP h=1024 d=4 | 98 ms      | 6,577,427     |
| 参考：纯走法 d=64    | **73 ms**  | **6,291,756** |
| 参考：DP             | 293 ms     | 5,878,519     |

结论：**每一个短视界配置都被纯走法同时击败（更慢且更大）**。窗口内的 DP 拿不到
额外信息——候选还是同一个行索引给的，路径最优只是把同一批候选重排了一遍，没有引入
走法看不到的候选。真正的 7% 来自"候选集本身不够"，而不是"候选没排好"。

调试过程中确认的两个实现陷阱（后续再做类似结构必须注意）：

- 提交点不能是"路径前缀截止在窗口一半"：路径最后一步一定是那条把价格压下去的匹配，
  若因跨窗口边界而丢弃，就永远只提交字面量，产物退化到比 STORE 还差（实测 10.6
  MB）。 正确做法是提交整条路径，最后一位用走法重判。
- 终点选择必须按"相对纯字面量的收益"而不是"绝对价格"：否则不可达节点/偏远节点会把
  提交长度压到 1 字节，窗口成本摊不出去（实测波次随 H 线性涨到 34 s）。

## 走法的瓶颈已经不在解析

走法 73 ms 就做到 6.29 MB。分支上真正剩下的是**波浪外 296 ms 固定开销**（启动
67 + IO 68 + 筛选 48 + 预表 106），它等于官方整次运行。方向 2/3/4
都应改成围绕这个来做： 若能在 73 ms 解析之上把固定开销压到 150 ms 以内，总墙钟 ≈
225 ms，比官方还快， 代价只是比率 +7%。那时再用方向 2（先问 rep）把 7% 往下压到
3–4% 就是可交付的配置。

## 机制分解：完整 DP 的 7.3% 到底来自哪里

短视界 DP（6,309,570）与完整 DP（5,878,519）用的是**同一批行索引候选**，却差
7.3%。 为定位机制，改为在**完整 DP
上逐个摘除机制**再测（ntoskrnl，`-m3 -md32m -mt24`， UnRAR
`All OK`），每次只改一处、测完即还原：

| 摘除的机制                                                       | 大小      | 相对默认   | 波次       |
| ---------------------------------------------------------------- | --------- | ---------- | ---------- |
| （默认）                                                         | 5,878,519 | —          | 289–304 ms |
| 每段长度只给上限定价（不逐 slot 展开中间长度）                   | 5,897,073 | **+0.32%** | 290–304    |
| 不传播逐节点 rep 状态（`arrive_reps`/`arrive_last_length` 不写） | 5,993,067 | **+1.95%** | 282–289    |

结论：

- **中间长度只值 0.32%**——"按 slot 逐级定价"主要是个省时的写法，不是比率的来源。
  这同时说明短视界 DP 的亏损不能归因于"只取最长匹配"。
- **逐节点 rep 传播值 1.95%**——这是完整 DP
  真正独有的机制：它知道哪条路径会把哪个 距离留在缓存槽里，于是愿意为"保住某个
  rep"付一点代价。走法和短视界 DP 都只有 一个固定的 rep 视图。
- 剩下约 5% 不在上述两项里，指向**自适应价格表**（`prices_from_frequencies` 逐块
  继承的真实符号代价，而非 `2*log2(dist)+log2(len)+4` 的估算）与**48 KiB
  的规划视界** （视界 256 字节时，位于 pos+300 长度 1000 的匹配根本不可见）。

给后续实验的排序建议：

1. 短视界 DP 若要可用，必须同时补上 rep 传播与真实价格表，且视界提到 1–4 KiB；
   按上面的分解，光补 rep 传播与价格表就可能拿回 2–5%，但每节点的状态拷贝会抵消
   一部分它省下的时间。
2. 若目标是"比官方快、比率只差 3–4%"，不如走另一条：保留走法的 73 ms 解析，把
   296 ms 固定开销压到 150 ms 以内（总墙钟 ≈ 225 ms），再用 rep 优先把 7%
   往下压。

## 预表 99 ms 的内部账与固定开销的硬地板

在 `RowIndex::build_split` 内临时加 `MTTIME ri_count= / ri_merge=` 打印后测得
（ntoskrnl，`-m3 -md32m -mt24`，8 个 part）：

| 段                                                | 耗时      | 性质                 |
| ------------------------------------------------- | --------- | -------------------- |
| 计数（8 部分，并行）                              | 19 ms     | 带宽                 |
| 合并（8×1 M 桶求和 + 前缀 + 游标）                | **18 ms** | **串行**             |
| 散写（140 MB：positions 56 + slot 56 + avail 28） | 34 ms     | 带宽                 |
| `LongRange::push`                                 | 28 ms     | 与上面并行，但抢带宽 |
| 预表合计（两者并行后）                            | 99–105 ms |                      |

两个已验证的边界：

- **去掉 `LongRange::push` 只省 10 ms**（99 → 88–93），因为它本来就与预表并行，
  只是和散写抢内存带宽。为它引入"非固实不推送"的 API 改动收益不值得。
- 散写 140 MB / 34 ms ≈ 4.1 GB/s，已接近本机可用带宽；`slot`（56 MB）是为了避开
  每位置一次 4 MB `starts` 随机读而引入的，去掉它会省约 12 ms 散写，但要把随机读
  搬回热循环里，净收益不确定。

### 结论：固定开销的硬地板 ≈ 240 ms

启动 67 + IO/CRC/写 68 + 筛选 48 + 预表 90（= 已优化的地板值，乐观再压到 70） ≈
**240–273 ms**。而官方整次运行是 295 ms。

也就是说：**即使解析成本为零，我们这套结构的墙钟也只能勉强追平官方**（240 + 73 =
313 ms 已含走法解析）。要在 295 ms 内同时拿到官方比率，必须让 DP 的 293 ms 波次
降到 ~100 ms 以下，而那正是"变成走法"——代价是机制分解里量到的 rep 传播 1.95%
与自适应价格表约 5%。

因此本架构下的真实前沿只有两个点，二者不可同时达成：

- **官方比率**：585 ms（波次 293 + 固定 292），比率比官方好 0.14%；
- **官方速度**：走法 73 ms 波次 + 240 ms 固定 ≈ 320 ms，比率差 7%。

### 中小文件为什么慢得多（已修）

问"是不是所有情况都慢两倍"时测出的真相：慢得最多的不是最大的文件，而是中等文件。

MT 有两道门：`add.rs` 的 `MT_MIN`（4 MiB）和 `filter.rs` 的 `mt_min_len`（8
MiB）。 所以 4 MiB 的成员走顺序路径，而顺序路径要 1103 ms——比 13.9 MiB 走 MT 的
548 ms 还慢。修法是把两道门统一成 `MT_MIN_MEMBER_SIZE = 1 MiB`（可被
`RAR_RS_MT_MIN` / `RAR_RS_MT_MIN_LEN` 覆盖），1 MiB
以下仍走顺序（这时池子无活可叠）。

尺寸曲线（内核镜像前缀，`-m3 -md32m -mt24`，时间 / 大小）：

| ------- | ----------------- | --------------- | --------------- |
| 256 KiB | 207 / 115,212     | 179 / 115,212   | 160 / 107,029   |
| 512 KiB | 255 / 187,388     | 256 / 187,388   | 165 / 178,040   |
| 1 MiB   | 363 / 360,979     | 218 / 359,082   | 163 / 340,422   |
| 2 MiB   | 535 / 804,743     | 264 / 799,645   | 200 / 766,156   |
| 4 MiB   | 1,103 / 1,810,492 | 358 / 1,827,026 | 222 / 1,808,489 |

修后对照官方的倍数：256 KiB 1.16×、512 KiB 1.33×、1 MiB 1.16×、2 MiB 1.25×、 4
MiB 1.48×、5.9 MiB 源码 1.63×、13.9 MiB 2.11×。也就是说"慢两倍"只在大文件成立，
中等文件原来慢 4 倍多，现在反而更接近。

### 大文件（50 MB / 200 MB / 1 GB）的账

语料：`System32` 里 1,662 个不同 DLL 按名排序拼接成 50/200/1000 MB 三个文件，
`-m3 -md32m -mt24`，与我们自己的 `rar.exe` 和官方 `Rar.exe 7.23` 各跑一次。

| 成员     | 我们                 | 官方                 | 速度比 | 比率     |
| -------- | -------------------- | -------------------- | ------ | -------- |
| 13.9 MB  | 0.95 s / 5,878,519   | 0.46 s / 5,886,560   | 2.1×   | 好 0.14% |
| 53 MB    | 3.4 s / 12,926,745   | 1.36 s / 12,819,587  | 2.5×   | 差 0.84% |
| 202 MB   | 15.7 s / 54,473,456  | 4.66 s / 53,271,403  | 3.4×   | 差 2.26% |
| 1,000 MB | 72.9 s / 286,406,261 | 24.5 s / 293,575,884 | 3.0×   | 好 2.4%  |

按每字节 CPU 折算：13.9 MB 时我们 ≈475 ns/B、官方 ≈104；1 GB 时我们 ≈763 ns/B、
官方
≈117。也就是**我们的单位成本随成员变大而上升，官方基本持平**——慢得越来越多。

原因（实测定位）：切片尺寸 = 成员/(线程×1)，202 MB 成员每片 2.8 MB。切片一大，
候选探测就全落在 32 MB 字典窗口的 DRAM 冷区，每字节成本随窗口被用满而上涨。
内存不是瓶颈（202 MB 峰值 1,021 MB，官方 322 MB），IO 也不是（`-m0` 只要 345
ms）。

修法：给切片加上限 `MT_MAX_SLICE = 512 KiB`。

| 成员     | 无上限                 | 512 KiB 上限           |
| -------- | ---------------------- | ---------------------- |
| 53 MB    | 5,077 ms / 12,926,745  | 3,304 ms / 12,914,454  |
| 202 MB   | 21,714 ms / 54,473,456 | 17,597 ms / 54,428,923 |
| 1,000 MB | 80.1 s / 286,406,261   | 62.0 s / 286,414,589   |

256 KiB 在 1 GB 上反而更慢（64.6 s）且开始影响 13.9 MB（那边切片只有 ~580
KiB）， 所以取 512 KiB。13.9 MB 的产物仍是 5,878,519，零比率损失。 修后 1 GB
是官方的 2.5×（原 3.0×），仍是大文件最弱的一环。
