# 交接：MT 行索引（row index）+ solid 滤镜（2026-11-16）

> 接 `handoff-2026-11-15.md`。这一轮的结论一句话：**MT 的速度问题在「每个位置
> 走多少次随机访存」，比例问题在 solid 链上丢掉的 x86 滤镜。**

## 这一轮改了什么（都已进代码）

1. `RowIndex` 查询从「哈希 → 桶头 → 二分 → 倒着走」变成「`slot[pos]` 直接给出
   该位置在自己的桶里的槽位」，每位置少一次 20 位桶表随机读和一次二分。
   `crates/rar/src/codec/modern/lzss_huff/encoder/parse/optimal.rs`
   （`slot` + `starts`，`collect` 只用 `index - starts[hash]` 定长度）。
   候选集与顺序**逐字节不变**（同 hash 桶、新到旧、同样 depth 截断）。
2. `RowIndex::build` 拆成 `build_serial` / `build_split`：按**连续位置区间**分块
   统计桶计数，串行合并前缀和后给每块一个写游标，再并行填 `positions`/`slot`。
   结果与串行 build 位相同。`BUILD_MAX_PARTS = 8`、`BUILD_MIN_PART = 1 MiB`
   （实测 16 块反而更慢：合并流量压过收益）。build 155 → 82–90 ms。
3. MT 切片几何对齐官方：下限从 2 MiB 降到 **128 KiB**（官方 wave 粒度就是
   `threads × 128 KiB`），并把切片数**按整 wave 向上取整**
   （`div_cell(waves * workers)`），避免 48 片之后多出一个 16 字节的尾巴片
   独占一波（mt24：49 片 → 48 片，waves 377–400 → 290–320 ms）。
4. `LONG_RANGE_INSIDE_MEMBER`：单成员（`entry_len == 0`）不再把采样长表塞进
   row-index 解析（比例**一个字节都不变**，wall 省 10–12%）。**solid 链必须
   保留**——上一个成员的字节根本不在 `data` 里，行索引看不到，只有采样表能看
   到；早期"直接关掉长表"的写法把
   `solid_members_share_the_window_through_mt` 弄挂了。
5. **solid 成员改用非 solid 的逐 64 KiB 分块滤镜选择器**
   （`format/rar5/write/filter_policy.rs::combined_filter_specs`，被
   `format/rar5/write/add.rs::try_solid_filters` 调用，失败才回退旧的
   `solid_filter_specs` 探针选择器）。旧的整成员探针选择器在 ntoskrnl 上干脆
   不选 x86 滤镜，导致 **solid 成员白丢 600 KiB**；修好后
   ntoskrnl+ntdll solid（mt1）7,257,425 → **6,839,224**（官方 6,712,267）。

## 为什么 waves 只能到 35% 并行效率（下一轮的主战场）

每个位置的实际访存：`slot[pos]`（顺）、`starts[hash]`（4 MB 随机）、
`hash` 要读 `data[pos..pos+4]`（顺）、每候选 `positions[at]`（56 MB 随机）、
命中后再 `data[candidate+best]`（14 MB 随机）。官方每候选只有**一条**
位置索引链（`prev4[pos]` 直接是"同 hash 的上一个位置"），同样的候选走法少一次
随机流；而且他们的桶更稀疏（20 位 → 23 位量级的表 + 5 字节 hash），平均每位置
只探 1–2 个候选，我们平均 ~13（13.9 M / 2^20）。

未验证的猜想（按性价比排序，都还没做）：

- **加桶位数**：`ROW_INDEX_HASH_BITS` 20 → 21/22，平均桶 13 → 6/3。代价是
  `starts` 变大（4 → 8/16 MB，查询是随机读）和 build 计数表
  （parts × buckets × 4 B）；比例会掉（等价于降 depth：d16 = 43.14%）。
- **5 字节 hash**（官方同款）：桶内候选仍然共享 ≥4 字节前缀，但分布更均匀。
  注意：只在候选循环里加"第 5 字节过滤"是**净亏**（实测 1.56 s → 1.96 s），必须
  让 hash 本身吃掉第 5 字节。
- **官方式提前退出**：`FUN_1400468d4` 在 `best` 已经够长时直接 return
  （`if ((2<iVar17) && ((+0x300a0 * 0x4000) < uVar13) && (iVar22 < iVar17+5)) return;`），
  我们目前只有 `length == max_length` 才 break。
- **小成员切不出片**：2.5 MB 成员在 24 线程下 `by_count = len/(2T)` 太小，片数
  被封顶，mt24 与 mt8 同速（ntdll 501 vs 504 ms）。官方没有这个问题。

## 仍然开着的比例缺口

- **solid 链上 MT 仍比串行差 95 KiB**（mt8 6,934,557 vs mt1 6,839,224；官方
  mt1→mt24 只差 133 B）。原因：MT 切片对"上一个成员"只有采样长表可达，串行的
  chunk 循环有真窗口。`RAR_RS_MT_MIN_SLICE` 调大几乎无改善（2 MiB → 6,930,617），
  说明不是切片粒度而是**跨成员可达性**。
- **我们的 solid 仍比非 solid 略大**（ntoskrnl+ntdll：6,839,224 vs 6,770,399），
  官方 solid 反而小 153 KiB。同样的成员、solid 信息严格更多，却更差 ⇒ 嫌疑在
  (a) 跨成员的 `dist_cache`/价格携带（`TokenPrices` 沿用上一个成员的分布）、
  (b) 长表候选挤占近距候选的 `MAX_PARSE_STEPS_PER_POSITION` 预算。未定位。
- 单成员（非 solid）时 row index 只覆盖本成员窗口，跨成员匹配完全靠采样表。

- 计时不要信第一遍：同一条命令第二次跑常常从 1810 ms 掉到 860 ms（页缓存 + 线程
  池预热）。每个数测两遍。
- 本机没有 `python`/`python3`（Windows Store 桩），用

- 改切片几何会让 `carried_prices_beat_starting_from_the_flat_estimate` 这类

官方同等配置是 **286 ms / 5,886,560（42.30%）**。

两个结论：

1. **固定开销 ≈ 200 ms，和官方的全程一样大**。`depth 1` 时 waves 只有 170 ms、
   build 85 ms，总 460 ms ⇒ 剩下 200 ms 与解析无关（滤镜测量 110–124 + IO/CRC/
   头 ~140，部分重叠）。也就是说**哪怕解析免费，我们也还在 290 ms**，只和官方打平。
   想让"速度相近"成立，`block_stats_all` 的 11 个 delta 通道 + 2 个 x86 覆盖扫描
   是下一个必须动的固定成本（WinRAR 只发少数通道；我们逐块全通道比）。
2. **候选深度的边际很差**：depth 64 → 16 只省 50 ms 却赔 0.71 pp，depth 1 才到
   1.6x 速度但赔 4 pp。说明 collect 的成本主要是**每位置固定几条随机流**
   （`slot[pos]`、`positions[at]`、命中后的 `data[cand+best]`），不是候选条数。
   要真正砍下去，得减少**每个位置的流数**，而不是 depth。

官方同配置 277–306 ms / 5,886,560：我们 **2.1x 慢、0.20% 小**。

同轮否掉的旋钮（都有数据，别再重复试）：

- `RAR_RS_MT_MAXMATCH` 64/128/256/1024/4096：waves 305/311/307/304/305 —— **匹配
  长度上限完全不影响时间**，说明 `match_length_at` 的延长不是瓶颈（否掉了"延长太贵"
  的假设）。体积代价也只有 +0.16%（mm64）。
- `RAR_RS_DP_SKIP` 8/16/32/64/128：waves 297/327/306/424/331，体积 6,057,349 →
  5,897,372 —— 跳步阈值也不是杠杆（大匹配处的跳过已经饱和）。
- 预取：在 `collect` 里对 `data[candidate_ahead + best_length]` 做 8 步前的
  `_mm_prefetch`，collect 合计 5689–5909 对基线 5870 —— 无收益，已撤。
- 每位置 4 字节签名数组（`sig: Vec<u32>`）：walls 341 → 1900 ms（只留签名）/
  486–524（签名 + 探针），row_index 142 → 213 ms —— 索引每位置再加一条流
  反而更慢。
- 窗口 md32m/8m/4m/1m：waves 526/495/496/441 —— 距离局部性只值 16%，赔 3.9% 体积。
- ADR 0012 两段式：5,911,145 → 5,911,140（−5 B）、+130 ms，默认关闭（见 ADR 正文）。

结论没变，但更硬：**每位置固定几条随机流**（`slot[pos]`、`avail[pos]`、
`positions[at]`、命中后的 `data[cand+best]`）才是成本的形状，depth 与长度上限
都不是。下一步要动的只有两处结构：把 `slot/avail/positions` 三条流压成一两条
（例如 32 位打包 `(slot, avail)`，或直接把候选位置存进 CSR 让 `collect` 只走一条流），
以及把 `best_combined_specs` 的 50 ms 固定成本按块并行到通道粒度。

## 又一轮否证（2026-11-16 夜）：索引构建与"更省事的解析"都不是杠杆

`RowIndex` 的桶数（运行时 `RAR_RS_RI_BITS` 扫过）、构建分片数、候选停走阈值、
低步进 greedy 解析，全部实测过，结论都是"不动"或"更差"：

| 试验 | 构建 | waves | 体积 | 判定 |
| ---- | ---- | ----- | ---- | ---- |
| 20 bit 桶（现状） | 93–112 | 292–324 | 5,898,075 | 基准 |
| 18 bit | 57 | 358 | 5,902,455 | 构建省 50、解析赔 60，净亏 |
| 16 bit | 32 | 408 | 5,929,660 | 更差 |
| 22 bit | 212 | 284 | 5,897,166 | 体积 −909 B，构建 +110，净亏 |
| 24 bit | 529 | 262 | 5,896,913 | 同上，构建爆炸 |
| 构建分片 2/4/6/8/13 | 103–166 | 327–363 | 不变 | 全在噪声内 |
| `RAR_RS_RI_STOP` 8/16/32/64/128 | — | 267/303/343/323/301 | 5,979,729/5,912,557/5,899,789/5,898,668/5,898,260 | stop=8 快 60 ms 但赔 1.4%，不可用 |
| 低步进 greedy（`RAR_RS_MT_LOWSTEP=1`，走链不走索引） | — | 464–493 | 6,515,182 | 更慢且更差（每片重插链的老问题） |

两条可以写进设计前提的事实：

1. **20 bit 桶是构建/查询的联合最优**。桶数只改变两边的分配，不改总和；
   24 bit 能把体积再压 1.2 KB、waves 再省 30 ms，但计数表 64 MB，构建从
   100 ms 涨到 529 ms。
2. **构建的 100 ms 是 56 MB 随机散写的地板**：16 bit（表 256 KB，写入落点
   集中）只要 32 ms，说明成本全在"1 M 桶跨 56 MB 的散写"，不在计数。
   两级构建（先 4 K 粗桶、再在 13 KB 的粗桶内用 L1 表细分）理论上能把
   20 bit 的构建压到 ~50 ms，收益约 8% 的总时长，是本目录里唯一还剩的
   无损优化。
3. **候选停走没法和 DP 共存**：我们的 priced DP 需要"所有 improving 候选"
   才能定价，任何提前停止都直接换成比例损失（stop=16 就赔 0.25%）。

至此"在现有 DP + 行索引架构内提速"的选项已经全部试完，剩下的差距是架构性的：
官方用**受限候选的 greedy + lazy**（`FUN_1400468d4` 的 `best+5`/`best*0x4000`
早退）配合 128 KiB 子块并行，我们用的是**全候选定价 DP**。同等设置下我们只比
官方小 0.2%，却付了 2 倍时间——这 0.2% 就是 DP 的全部收益。


## greedy 层的实测否决，与"账本反转"（2026-11-16 深夜）

上一节把剩下的差距判为"架构性：官方用受限候选 greedy，我们用全候选 DP"。
按这个判断实现了 `windowed_greedy_parse`（`RAR_RS_MT_GREEDY=<depth>`，走同一
个 `RowIndex` 的 `collect`，lazy 阈 `RAR_RS_MT_GREEDY_LAZY`，最后仍交给
`convert_tokens` 复用 repeat-cache 语义），实测**否决**：

| 配置 | 体积 | 每片 parse（mt4，3.5 MB 片） |
| ---- | ---- | ---- |
| DP depth 64（现状） | 5,898,075 | 575–854 ms |
| greedy depth 4 | 6,612,844 | — |
| greedy depth 8 | 6,497,342 | 715–749 ms |
| greedy depth 16 | 6,412,192 | — |

即：**同等速度下比例差 10%**。受限候选 greedy 在我们这里不是"更快的同质量
解析"，而是"同速率的差解析"——因为它丢掉了两件 DP 免费做的事：memory/repeat
候选（`state.reps` 探测）和"短近距离 vs 长远距离"的定价。

实现过程中踩到的两个坑（后一个才是真 bug）：

1. `convert_tokens` 要求 token 流**覆盖每一个位置**，literal 必须显式写成一
   个 `(0, byte)` token。greedy 只推进 `pos` 不写 literal 时，`pos` 的推进和
   解码器的推进就错位，输出在第 2 个 match 之后整体偏位——表现是 UnRAR 报
   "checksum error"、体积比 DP 小 26%（假象）。
2. match 不能跨 slice 末尾（`limit = max_match.min(e0 - pos)`），否则会把下一
   片的字节重复吐一遍。

### 账本反转：我们的 waves 已经等于官方的全部耗时

把同一份 ntoskrnl（13.9 MB、`-m3 -md32m -mt24`）的两本账并排放：

| 阶段 | 我们 | 官方 |
| ---- | ---- | ---- |
| IO + CRC + 写盘 | ~150 ms | 含在 322 内 |
| filter 选取（`best_combined_specs`） | 46–48 ms | — |
| `LongRange::push` | 28–29 ms | — |
| `RowIndex` 构建 | 95–96 ms | — |
| **waves（并行解析+编码）** | **317–334 ms** | — |
| 合计 wall | 631 ms（第二次跑） | **322 ms** |

也就是说：**我们的解析本身（317 ms）已经和官方整包的耗时（322 ms）持平**，
2 倍的差距全部来自解析之外——IO 和三项全局开销（170 ms）以及没有与解析重叠。
比例上我们只大 0.2%（5,898,075 vs 5,886,560）。

结论修正：既然 waves 已经达标，正确的主攻方向不是"更快的解析"，而是
**把 300 ms 的固定开销拿掉或藏起来**：

1. IO/CRC 与解析重叠（读流 → 边读边 CRC → 分块喂给行索引构建），可省 ~150 ms。
2. `RowIndex` 构建（95 ms）与 IO 重叠，或改成"边读边建"的分段构建。
3. `best_combined_specs`（46 ms，213 块 × 13 通道）先用采样预筛通道，再全量确认。
4. `LongRange::push`（28 ms）可与刷盘重叠。

按 1–4 全做，wall 的理论落点是 330–380 ms，即官方的 1.05–1.2 倍，比例不变。

## 48 KiB DP 块：比例和速度同时变好（已落地）

`MT_DP_BLOCK_SIZE` 从 256 KiB 改成 48 KiB。这是本轮唯一"两边都赚"的改动，
因为块变小让价格/码长表（每块之间传递的那张）刷新更勤，同时每个 worker 的
DP 表从 8 MiB 降到 1.5 MiB：

| 语料 | 256 KiB | 48 KiB | waves |
| ---- | ---- | ---- | ----- |
| ntoskrnl 13.9 MB | 5,898,075 | **5,883,538** | 298 → 299 |
| code.bin（5.9 MB Rust 源码） | 1,125,053 | 1,119,493 | 118 → 111 |
| text.bin（7.7 MB markdown） | 1,598,504 | 1,585,410 | 174 → 171 |
| solid（三者一起） | 8,019,198 | 7,999,171 | — |

各等级同样成立：`-m1` 5,989,776 → 5,974,684、`-m2` 5,936,433 → 5,921,671、
`-m4` 5,869,710 → 5,855,069（waves 382 → 350）、`-m5` 5,848,805 → 5,834,207
（waves 473 → 452）。扫过的块大小 16/32/48/64/96/128/192/256 KiB 里 48 KiB
和 32 KiB 最好，48 KiB 在三份语料上总和最小。

顺带把 `LongRange::push`（28 ms）和 `RowIndex::build`（100 ms）放进同一个
`pool.join`：两者都只读 `data`、互不相干，串行 128 ms → 一起 106 ms。

## 现在的账（ntoskrnl 13.9 MB，`-m3 -md32m -mt24`，取两次最好值）

| 阶段 | 我们 | 官方 |

2. **砍掉波浪之外的开销**（filter 预筛 48 → ~18 ms；行索引改成"每位置存

3. **等级重映射**：给 `-m1/-m2` 一套真正的快档（depth 8 + 关掉 filter 探测），

## 选项 2（砍波浪外开销）三个方向全部否证

三轮都实测完、都回滚了，工作树干净。

### 1. 行索引改成"逐位置 prev 距离链"（否证）

链条版：`prev: Vec<u32>`，每位置存到同 4 字节哈希前一个位置的距离，
`collect` 顺着链跳；构建变成一次顺序扫描 + 4 MB head 表。

- 构建：prelude（long_range + row index 并行）106 → **30–37 ms**，内存 140 MB → 56 MB。
- 体积：**完全一致**（5,883,538，UnRAR 校验 OK），说明候选顺序等价。
- 但 waves **311 → 858–863 ms**。原因：CSR 里同一桶的候选在 `positions` 里
  是连续倒着放的，一次 miss 带回一整条 cache line；链表的每一跳都是一次对
  56 MB 数组的随机依赖读，约 13 候选 × 13.9 M 位置 ≈ 每次 48 ns。
- 结论：**查询必须连续**，构建必须散写，这两个要求在我们这里无法同时满足；
  CSR 的 ~95–100 ms 构建就是查询连续性的代价。链式索引不要重试。

### 2. filter 的 delta 通道预筛（否证）

11 个候选帧在整块 64 KiB 上排名的扫描量是 150 MB/成员。改成先在块首
8 KiB 上排名、赢家再在整块上数一遍：

- `filter_pick` 49 → 43 ms（只省 6–13 ms，说明通道扫描本来只占 ~13 ms）。
- 体积 5,883,538 → **5,892,080（+0.15%）**，滤波记录从 187 涨到 188。
- 结论：省的时间太少、比例代价明确，回滚。

### 3. 覆盖率测度的采样前缀（否证，已有开关）

`RAR_RS_HEUR_SAMPLE`：

| 前缀 | filter_pick | 体积 |
| ---- | ---- | ---- |
| 全块（默认） | 48 ms | 5,883,538 |
| 32 KiB | 48 ms | 5,888,270（+0.08%） |
| 16 KiB | 39 ms | 5,895,539（+0.2%） |
| 8 KiB | 34 ms | 5,950,393（+1.1%） |

省 9–14 ms 换来 0.08–1.1% 体积，不划算。默认保持全块。

### 结论

`-m1` 的阶段账：filter 47 + prelude 103 + waves 227 = 377 ms，加上启动 67 和
IO 68 = **512 ms**。官方 `-m1` 整包 **170 ms**——也就是说我们**光是波浪之外的
固定开销（150 ms）就接近官方整个 -m1 的运行时间**。官方没有 filter 扫描、没有
全成员行索引，它用 128 KiB 子块 + 每子块增量哈希链、流式一遍做完。

在现架构里，能砍的固定开销已经砍完了（filter 预筛、索引链、采样前缀三个方向
都实测否决），剩下的 1.8–2.0 倍差距是架构性的：要么按官方形状重写解析

## 候选走查本身：三个方向否证（2026-11-16 深夜）

上一节把波浪之外的固定开销砍完，剩下 `RowIndex::collect` 的候选走查

基线：`-m3 -md32m -mt24`，waves 284–311 ms、prelude 96–102 ms、
`member_encode` 405–427 ms、体积 **5,883,544**（成员名带 `../` 前缀的形态；
同目录跑是 5,883,538）。先跑一次丢弃、再交替 A/B，共 20 次运行。注意本机
同一时段也在漂（prelude 101 → 253 ms、waves 291 → 496 ms），所以只比同一轮里
相邻的基线值。

### 1. 桶内 4 字节整数校验 + 长度比较从第 4 字节续起（否证）

候选共享的是 4 字节 *hash*，不是 4 个字节，所以先用一次 `u32` 比较
（`quad_at`）拒绝碰撞，命中后用 `match_length_at_from(.., 4, ..)` 从第 4 字节
续。语义精确：体积 **每一次都 5,883,544**，归档逐字节相同，UnRAR `All OK`。

- waves 297 / 302 / 318 / 344 / 322 / 385 / 519，基线同期
  284 / 300 / 307 / 290 / 290 / 311 / 367 / 319 / 347 / 496
  （中位数 322 vs 309，最好值 297 vs 284）→ **不快，略慢**。
- 原因：`depth` 之所以是旋钮，是因为**重复最多的 4-gram**（零填充、重复代码）
  桶被深度截断；这些桶里候选的 4 个字节几乎总是相同，校验**几乎不拒绝**，只是
  多一次候选数据装载并把分支推迟一个 load 延迟。
- 一个实现坑：`u32::from_le_bytes([data[at], data[at+1], data[at+2], data[at+3]])`
  是 4 次独立越界检查，实测 waves 384–393（**慢 20%**）；必须走
  `data[at..at+4].try_into()`（单次边界检查、一次非对齐装载）。
- 另一个坑：**不能**据此把长度比较改到 `best_length + 4` 续起。`best_length`
  是「目前最好」的长度，不是这个候选已证的匹配长度；只有第 0 字节的探针（或第 1
  项那个偏移 0 的门）才能证明前缀。跳过前缀会**高估**长度，产出的归档被 UnRAR 报
  `checksum error`（本轮 5,627,705 的假“更好比例”就是这么来的）。

### 2. 把 `best_length` 处的探针从 1 字节加宽到 4 字节（否证）

与 1 字节探针是同一次装载（同一 cache line、同一个偏移），却多拒绝 ~4 倍的
`match_length_at`。语义有损（长度落在 `(best, best+4)` 的候选被丢掉），
归档仍 `All OK`：

- 体积 5,883,544 → **6,076,807（+193,263 B，+3.3%）**，waves 296 / 296 / 298
  对基线同期 290 / 290 / 311 → **时间一点没动**。
- 结论（这一轮最有价值的一条）：**多拒绝 4 倍的长度比较换不到任何时间**，
  说明 `match_length_at` 不是成本；成本是**每个候选的一次数据装载**，两种探针
  都要付，所以加宽探针是纯比例损失。同一结论也解释了第 1 项为何不快。

### 3. 切片局部链缓存（未做，与已否证项同机制）

"每切片预计算「到同 hash 上一位置的距离」，走查改用切片局部数组"就是上面
「行索引改成逐位置 prev 距离链」那一条（waves 311 → 858–863 ms），机制相同，
不再重跑。而且它的前提不成立：近窗要往回够 32 MB，**跨 MT 切片边界**，切片局部
的链无法复现候选集，除非每个切片先做全局播种——那正是 `build_with_threads`
现在干的事（prelude 96–102 ms）。

### 判定

走查已经到地板：每个候选至少要装载一次它的数据才能判断，候选数由 depth 与桶
分布决定，而 depth（d32 +0.65%、d16 +1.55%）和桶数（上一轮否证）都不能动。
`waves` 没有变动到值得的地步，三项全部 `git checkout` 回退，工作树停在

## 定价式跳过解析：3x 速度达标，7.5% 比例缺口没收回（2026-11-16 深夜，已回退）

上一节的判定是"候选走查已到地板，想再往下只剩官方形状重写"。官方形状的核心是
规则式解析器（`FUN_140044794`）：每个位置只提交一个匹配、并跳过它的整个长度。
此前按官方整数启发式（`dist >> 5`）实现过一版：waves 286 → 67–91 ms，但体积
5,883,544 → 6,336,096（+7.7%）。

本轮把两件事拆开测：**保留跳过循环**（速度来源），**把候选选择换成真实价格比较**
（比例来源）。假设是：那 +7.7% 是整数启发式的账，不是跳过的账。

### 实现（回退前）

- `windowed_rule_parse` 按 48 KiB 块（`MT_DP_BLOCK_SIZE`）走。每位置
  `emit(pos, &probe_cache, &mut runs)` 拿候选，逐候选用
  `SlotPricer::for_run(&state, distance, variant, prices)` 定价：长度等于
  `pricer.repeat_length` 时取 `repeat_cost`，否则 `price_of_one(length)`；
  得分 `savings = literal_price * length - cost`，取最大者（并列取更长——同价多
  提交字节；再并列取更近——候选本来就近到远）。`literal_price` 是
  `prices.literal(combined[pos])`，首块无价格时退到 `ESTIMATED_LITERAL_COST`。
- 价格按块携带：块内 token 走一次 `convert_tokens`（同时推进
  `EncoderMatchState`），再用 `prices_from_frequencies` + `TokenPrices::new`
  给下一块定价——和 DP 的携带方式一致，所以价格是真实码长，不是常数表。
- 走步状态和转换状态分两份 `EncoderMatchState`：`pick_state` 随每个提交的匹配
  `remember`，使"已在 cache 里的距离"能被定价成 cache/repeat；`state` 由
  `convert_tokens` 推进并写回 `dist_cache`/`last_length`。
- 匹配不得跨块（`cap = max_match.min(block_end - pos)`），否则相邻两块会重复
  覆盖同一段字节（`convert_tokens` 按块铺符号）。
- 开关：`RAR_RS_MT_RULE=<1..=64>` 启用、`RAR_RS_MT_RULE_LAZY`（默认 32）；
  另加诊断开关 `RAR_RS_MT_RULE_INT=1`，同一条走步改用官方整数规则，用于同进程
  A/B 隔离"决策规则"这一个变量。

### 为什么定价没收回比例：缺口不在决策规则，在跳过本身

同一条走步、同一个候选集、同一 depth/lazy，只切 `RAR_RS_MT_RULE_INT`：

| depth/lazy | 定价 | 官方整数规则 | 差 |
|---|---|---|---|
| 64 / 8 | 6,323,060 | 6,352,364 | −29,304（0.46%）|
| 32 / 8 | 6,368,620 | 6,402,017 | −33,397（0.53%）|
| 32 / 32 | 6,435,449 | 6,386,111 | +49,338（整数反而更好）|

价格比较整条规则只值 **0.5%**，缺口是 **7.5%（439,522 B）**——差一个数量级。
所以那 +7.7% 不是"用 `dist >> 5` 顶替价格"的账，是"每个位置只提交一个匹配"的账。

机制：DP 在每个位置都重新定价，所以能选一个**局部更差**的匹配去换更好的后续
路径（保住 cache、对齐 repeat 长度、不断掉已有 repeat 链），而且是在整个 48 KiB
块上对路径求最小。跳过式走步一旦提交就前进 L 字节，那 L−1 个位置再也不会被看见，
结构上只能逐位置贪心。数据上三处互相印证：

- 候选深度 8 → 64 只赚 2.98%（6,517,583 → 6,323,060），32 → 64 只赚 0.72%，
  曲线已饱和：不是"候选不够好"，是"更好的候选也用不上"。
- 单步前瞻的阈值有浅最优（lazy 8）：几乎不前瞻（lazy 2/4）和大幅前瞻
  （lazy 64+）都更差，两端都在 +7.5% 以上。能改善的只有"多定价几个位置"，
  而那正是 4x 速度的来源。
- depth 64（97–117 ms）对 depth 32（87–101 ms）只慢不到 0.5%：价格计算本身
  很便宜，贵的是 DP 对每个位置都做一遍。

结论：速度与比例是同一根开关的两端。`RAR_RS_MT_RULE` 这条路不可能同时做到
< 150 ms 和 +0.5%，除非把"整段跳过"换成"有条件地少跳"（例如只在候选唯一且长度
远超阈值时才跳过，其余位置仍交给 DP）。那个方向本轮没有数据，不猜。

## CPU 账：差距是"每字节的算法工作量"，不是并行效率（2026-11-16 深夜）

前面所有测量都只有 wall，这一轮开始量 CPU（`Start-Process` + `TotalProcessorTime`），
假设"2x 差距可能来自并行效率"当场被推翻：

| | CPU | wall | 体积 |
|---|---|---|---|
| 我们 mt24 | **6,641 ms** | 585 ms | 5,878,519 |
| 官方 mt24 | **1,453 ms** | 295 ms | 5,886,560 |
| 我们 mt1 | 4,016 ms | 4302 ms | 5,778,366 |
| 官方 mt1 | 1,312 ms | 1516 ms | 5,886,435 |

三件事同时成立：

1. **每字节工作量是官方的 4.6 倍**（6.6 s vs 1.45 s），wall 差距是它的结果。
2. **官方 MT 几乎不多花 CPU**（1453 vs 1312 ms）：并行只覆盖候选发现，裁决串行且极轻。
3. **我们的 MT 路径在两个维度上都输给自己的串行路径**：CPU 6.6 s vs 4.0 s，
   体积 5,878,519 vs 5,778,366。row-index 切片解析每个字节比串行 DP 贵 65%，
   因为每个切片都重新走一遍共享索引、没有链式复用。

并行度反而是我们占优：我们 6641/585 ≈ 11.3 核，官方 1453/295 ≈ 4.9 核。

### 据此重做的两个实验（都否证）

**A. 官方模型走步接 row index**（`windowed_index_lazy_parse`，`RAR_RS_MT_RULE2`）：
复用既有 `lazy_tokens` 的全部判定（近距优先、4 槽 rep 判定器的三条边界、可编码性
检查），只把候选来源换成 row index——这是 ADR 0011 说"lazy walk 需要一个按距离类
排序的候选集"时缺的那一半。结果 waves **73 ms**（DP 290 ms，官方整个任务 295 ms），
但体积 6,291,756（**+7.0%**）。depth 32/16/8 依次 6,327,572 / 6,377,061 / 6,445,808。

**B. DP 内部按匹配长度跳过候选收集**（`RAR_RS_DP_SKIP_INMATCH`）：只跳过"落在刚
收集到的长匹配内部"的位置，价格表与决策模型完全不动。skip=16 得 5,920,135 /
waves 246–327；skip=8 得 6,026,489 / waves 185。**时间只线性地掉一小截，比例却
涨 0.7–2.5%**。

B 的时间曲线是关键证据：跳过一半位置只省 35% 的 waves，说明 per-position 成本
不在候选收集上，而在 DP 的**表遍历本身**（48 KiB 块 × 前后两遍 × 32 B/位置）。
这也解释了此前三次失败：`RAR_RS_MT_MAXMATCH` 扫不动时间、depth 扫不动时间、
`RAR_RS_RI_STOP` 只能拿比例换时间。

## 非 DP 走法实测：更快但更差，且救不了墙钟（2026-11-16 深夜）

用户要求「做非DP」。按 ADR 0012 与 `official-parse-rules.md` 的逆向结论，实现了
WinRAR 形状的四类候选走法（`RAR_RS_MT_OFFICIAL`）：位置索引的 `prev1`/`prev2`/`prev4`
三张"上一处同前缀"距离表（12 B/位置，单趟流式构建），加上原有的 4 字节哈希链作为
第 4 类；走法本身沿用官方规则（最近优先偏好、四槽重复距离裁决器、`length_bonus`
对齐），最后仍交给 `convert_tokens` 做 rep/cache 语义。

| 配置 | 波次 | 归档大小 | 对 DP |
| --- | --- | --- | --- |
| DP 基线（d64） | 293 ms | 5,878,519 | — |
| 仅 prev 三类（无哈希链） | 33 ms | 6,936,721 | +18.0% |
| prev 三类 + 哈希链 d4 | 74 ms | 6,584,250 | +12.0% |
| prev 三类 + 哈希链 d16 | 67 ms | 6,460,807 | +9.9% |
| prev 三类 + 哈希链 d64 | 81 ms | 6,393,561 | +8.8% |
| 上述 + 一位置延迟裁决（lazy 8/16/64） | 77–88 ms | 6,393,561 | 无变化 |

三点结论：

1. **候选类不是瓶颈，决策模型是。** 把 DP 喂同一份哈希链候选时它能做到 5,878,519；
   换成"每次提交最好候选"的走法就掉 7%。四类候选补回来 1.6%，一位置延迟裁决
   一分不补。官方之所以能用走法，是因为它的判决对着自适应 Huffman 价格做
   （`FUN_140045c14` 的 `FUN_140044410` 熵编码器回喂价格），而我们的走法没有任何价格。
2. **即便把解析降到 0，墙钟也回不到官方。** 走法波次只有 81 ms，但总墙钟 477 ms：
   启动 67 + 读入/CRC/写出 68 + 筛选 48 + 预表 113 + 波次 81。**波浪外的固定开销
   合计约 296 ms，已经等于官方整次 `-m3` 运行的 295 ms。** 非 DP 只是把 293 ms 的
   波次换成 81 ms，墙钟从 585 掉到 477，离 295 还差一整个固定开销。
3. **因此下一步的杠杆是"消掉预表和筛选"，不是解析。** 官方不建成员级索引：它的
   prev1/prev2/prev4 与 5 字节链是在同一趟里增量维护的（先查后插），没有 56 MB
   的批量构建；与 MT 子块并行并不冲突，因为表是位置索引的、只读共享的。

实验全部回退（`git checkout` + 删除 `parse/official.rs`），未提交任何走法代码；
树在工作区干净状态下停在 `2714f25` 之上的文档提交。

## 消掉预表的尝试：位置索引 prev 表反而更慢（2026-11-16 深夜，第三次否证）

思路来自官方结构：`prev1/prev2/prev4` 是**上一处同前缀的距离表**，一趟前向扫描就能建，
没有桶排序的 56 MB 散写。若成立，预表 113 ms 可以掉到 ~25 ms。

实测（`RAR_RS_MT_OFFICIAL`，ntoskrnl 13.9 MB，`-m3 -md32m -mt24`）：

| 项 | 行索引（现有） | prev 表（本实验） |
| --- | --- | --- |
| 预表耗时 | 85 ms（8 分片并行） | **152–163 ms**（单趟串行） |
| 波次 | 81 ms（链走连续桶） | **291–297 ms**（链走 `prev4` 逐跳） |
| 归档大小 | 6,393,561 | 6,371,552（+8.4% vs DP） |
| 总墙钟 | 477 ms | **640–671 ms** |

三项都比现状差，原因互不相同：

1. **构建更慢。** 表是 3 × `u32` × 位置数 = 167 MB，`vec![0u32; len]` 三次零初始化加页错误
   本身就比 8 分片并行的桶排序贵。而且官方表是 **1 + 2 + 4 = 7 B/位置**（`prev1` 只存
   一个字节，距离饱和 255），比我的 12 B/位置少一半，且小表常驻缓存。
2. **不能并行。** head 表是跨位置的依赖链，无法像桶排序那样切分片各算各的；而切片
   并行要求共享只读历史，正是必须物化成员级结构的原因。
3. **链跳昂贵。** `prev4[cand]` 是 56 MB 数组上的依赖随机读，一跳一个延迟；行索引的
   桶是连续的，一跳一条缓存线。

**结论（这是本轮最后的架构结论）**：官方的"一趟流式增量维护"只在**单趟顺序**处理下成立；
我们的切片并行必须先物化一份成员级只读索引，物化成本与查询局部性不可兼得。预表这项
固定开销在我们的并行形状里消不掉，除非放弃切片并行。

## 最终前沿（ntoskrnl 13.9 MB，`-m3 -md32m`）

| 配置 | 墙钟 | 大小 | 对官方比率 |
| --- | --- | --- | --- |
| 官方 Rar 7.23 `-mt24` | 295 ms | 5,886,560 | — |
| 本项目 DP `-mt24`（默认） | 585 ms | **5,878,519** | **−0.14%（更好）** |
| 本项目 DP depth 16 | ~470 ms | 5,974,684 | +1.5% |
| 本项目 DP depth 64 + skip 16 | ~500 ms | 5,920,135 | +0.57% |
| 非 DP 走法（本实验族） | 455–671 ms | 6,371,552–6,393,561 | +8.2…8.6% |

默认配置比官方小 0.14%，慢 2.0×。所有把速度压到官方附近的走法都在 8% 量级的比率损失上，
而所有保住比率的 DP 配置都在 1.6× 以上的时间上。这是两种决策模型的交换面，不是调参缺口。
