# 交接：MT 行索引（row index）+ solid 滤镜（2026-11-16）

> 接 `handoff-2026-11-15.md`。这一轮的结论一句话：**MT 的速度问题在「每个位置
> 走多少次随机访存」，比例问题在 solid 链上丢掉的 x86 滤镜。**

## 这一轮改了什么（都已进代码）

1. `RowIndex` 查询从「哈希 → 桶头 → 二分 → 倒着走」变成「`slot[pos]` 直接给出
   该位置在自己的桶里的槽位」，每位置少一次 20 位桶表随机读和一次二分。
   `crates/rar/src/codec/modern/lzss_huff/encoder/parse/optimal.rs`
   （`slot` + `starts`，`collect` 只用 `index - starts[hash]` 定长度）。
   候选集与顺序**逐字节不变**（同 hash 桶、新到旧、同样 depth 截断）。
2. `RowIndex::build` 拆成 `build_serial` / `build_split`：按**连续位置区间**分块
   统计桶计数，串行合并前缀和后给每块一个写游标，再并行填 `positions`/`slot`。
   结果与串行 build 位相同。`BUILD_MAX_PARTS = 8`、`BUILD_MIN_PART = 1 MiB`
   （实测 16 块反而更慢：合并流量压过收益）。build 155 → 82–90 ms。
3. MT 切片几何对齐官方：下限从 2 MiB 降到 **128 KiB**（官方 wave 粒度就是
   `threads × 128 KiB`），并把切片数**按整 wave 向上取整**
   （`div_cell(waves * workers)`），避免 48 片之后多出一个 16 字节的尾巴片
   独占一波（mt24：49 片 → 48 片，waves 377–400 → 290–320 ms）。
4. `LONG_RANGE_INSIDE_MEMBER`：单成员（`entry_len == 0`）不再把采样长表塞进
   row-index 解析（比例**一个字节都不变**，wall 省 10–12%）。**solid 链必须
   保留**——上一个成员的字节根本不在 `data` 里，行索引看不到，只有采样表能看
   到；早期"直接关掉长表"的写法把
   `solid_members_share_the_window_through_mt` 弄挂了。
5. **solid 成员改用非 solid 的逐 64 KiB 分块滤镜选择器**
   （`format/rar5/write/filter_policy.rs::combined_filter_specs`，被
   `format/rar5/write/add.rs::try_solid_filters` 调用，失败才回退旧的
   `solid_filter_specs` 探针选择器）。旧的整成员探针选择器在 ntoskrnl 上干脆
   不选 x86 滤镜，导致 **solid 成员白丢 600 KiB**；修好后
   ntoskrnl+ntdll solid（mt1）7,257,425 → **6,839,224**（官方 6,712,267）。

## 为什么 waves 只能到 35% 并行效率（下一轮的主战场）

每个位置的实际访存：`slot[pos]`（顺）、`starts[hash]`（4 MB 随机）、
`hash` 要读 `data[pos..pos+4]`（顺）、每候选 `positions[at]`（56 MB 随机）、
命中后再 `data[candidate+best]`（14 MB 随机）。官方每候选只有**一条**
位置索引链（`prev4[pos]` 直接是"同 hash 的上一个位置"），同样的候选走法少一次
随机流；而且他们的桶更稀疏（20 位 → 23 位量级的表 + 5 字节 hash），平均每位置
只探 1–2 个候选，我们平均 ~13（13.9 M / 2^20）。

未验证的猜想（按性价比排序，都还没做）：

- **加桶位数**：`ROW_INDEX_HASH_BITS` 20 → 21/22，平均桶 13 → 6/3。代价是
  `starts` 变大（4 → 8/16 MB，查询是随机读）和 build 计数表
  （parts × buckets × 4 B）；比例会掉（等价于降 depth：d16 = 43.14%）。
- **5 字节 hash**（官方同款）：桶内候选仍然共享 ≥4 字节前缀，但分布更均匀。
  注意：只在候选循环里加"第 5 字节过滤"是**净亏**（实测 1.56 s → 1.96 s），必须
  让 hash 本身吃掉第 5 字节。
- **官方式提前退出**：`FUN_1400468d4` 在 `best` 已经够长时直接 return
  （`if ((2<iVar17) && ((+0x300a0 * 0x4000) < uVar13) && (iVar22 < iVar17+5)) return;`），
  我们目前只有 `length == max_length` 才 break。
- **小成员切不出片**：2.5 MB 成员在 24 线程下 `by_count = len/(2T)` 太小，片数
  被封顶，mt24 与 mt8 同速（ntdll 501 vs 504 ms）。官方没有这个问题。

## 仍然开着的比例缺口

- **solid 链上 MT 仍比串行差 95 KiB**（mt8 6,934,557 vs mt1 6,839,224；官方
  mt1→mt24 只差 133 B）。原因：MT 切片对"上一个成员"只有采样长表可达，串行的
  chunk 循环有真窗口。`RAR_RS_MT_MIN_SLICE` 调大几乎无改善（2 MiB → 6,930,617），
  说明不是切片粒度而是**跨成员可达性**。
- **我们的 solid 仍比非 solid 略大**（ntoskrnl+ntdll：6,839,224 vs 6,770,399），
  官方 solid 反而小 153 KiB。同样的成员、solid 信息严格更多，却更差 ⇒ 嫌疑在
  (a) 跨成员的 `dist_cache`/价格携带（`TokenPrices` 沿用上一个成员的分布）、
  (b) 长表候选挤占近距候选的 `MAX_PARSE_STEPS_PER_POSITION` 预算。未定位。
- 单成员（非 solid）时 row index 只覆盖本成员窗口，跨成员匹配完全靠采样表。

- 计时不要信第一遍：同一条命令第二次跑常常从 1810 ms 掉到 860 ms（页缓存 + 线程
  池预热）。每个数测两遍。
- 本机没有 `python`/`python3`（Windows Store 桩），用

- 改切片几何会让 `carried_prices_beat_starting_from_the_flat_estimate` 这类

官方同等配置是 **286 ms / 5,886,560（42.30%）**。

两个结论：

1. **固定开销 ≈ 200 ms，和官方的全程一样大**。`depth 1` 时 waves 只有 170 ms、
   build 85 ms，总 460 ms ⇒ 剩下 200 ms 与解析无关（滤镜测量 110–124 + IO/CRC/
   头 ~140，部分重叠）。也就是说**哪怕解析免费，我们也还在 290 ms**，只和官方打平。
   想让"速度相近"成立，`block_stats_all` 的 11 个 delta 通道 + 2 个 x86 覆盖扫描
   是下一个必须动的固定成本（WinRAR 只发少数通道；我们逐块全通道比）。
2. **候选深度的边际很差**：depth 64 → 16 只省 50 ms 却赔 0.71 pp，depth 1 才到
   1.6x 速度但赔 4 pp。说明 collect 的成本主要是**每位置固定几条随机流**
   （`slot[pos]`、`positions[at]`、命中后的 `data[cand+best]`），不是候选条数。
   要真正砍下去，得减少**每个位置的流数**，而不是 depth。

官方同配置 277–306 ms / 5,886,560：我们 **2.1x 慢、0.20% 小**。

同轮否掉的旋钮（都有数据，别再重复试）：

- `RAR_RS_MT_MAXMATCH` 64/128/256/1024/4096：waves 305/311/307/304/305 —— **匹配
  长度上限完全不影响时间**，说明 `match_length_at` 的延长不是瓶颈（否掉了"延长太贵"
  的假设）。体积代价也只有 +0.16%（mm64）。
- `RAR_RS_DP_SKIP` 8/16/32/64/128：waves 297/327/306/424/331，体积 6,057,349 →
  5,897,372 —— 跳步阈值也不是杠杆（大匹配处的跳过已经饱和）。
- 预取：在 `collect` 里对 `data[candidate_ahead + best_length]` 做 8 步前的
  `_mm_prefetch`，collect 合计 5689–5909 对基线 5870 —— 无收益，已撤。
- 每位置 4 字节签名数组（`sig: Vec<u32>`）：walls 341 → 1900 ms（只留签名）/
  486–524（签名 + 探针），row_index 142 → 213 ms —— 索引每位置再加一条流
  反而更慢。
- 窗口 md32m/8m/4m/1m：waves 526/495/496/441 —— 距离局部性只值 16%，赔 3.9% 体积。
- ADR 0012 两段式：5,911,145 → 5,911,140（−5 B）、+130 ms，默认关闭（见 ADR 正文）。

结论没变，但更硬：**每位置固定几条随机流**（`slot[pos]`、`avail[pos]`、
`positions[at]`、命中后的 `data[cand+best]`）才是成本的形状，depth 与长度上限
都不是。下一步要动的只有两处结构：把 `slot/avail/positions` 三条流压成一两条
（例如 32 位打包 `(slot, avail)`，或直接把候选位置存进 CSR 让 `collect` 只走一条流），
以及把 `best_combined_specs` 的 50 ms 固定成本按块并行到通道粒度。

## 又一轮否证（2026-11-16 夜）：索引构建与"更省事的解析"都不是杠杆

`RowIndex` 的桶数（运行时 `RAR_RS_RI_BITS` 扫过）、构建分片数、候选停走阈值、
低步进 greedy 解析，全部实测过，结论都是"不动"或"更差"：

| 试验 | 构建 | waves | 体积 | 判定 |
| ---- | ---- | ----- | ---- | ---- |
| 20 bit 桶（现状） | 93–112 | 292–324 | 5,898,075 | 基准 |
| 18 bit | 57 | 358 | 5,902,455 | 构建省 50、解析赔 60，净亏 |
| 16 bit | 32 | 408 | 5,929,660 | 更差 |
| 22 bit | 212 | 284 | 5,897,166 | 体积 −909 B，构建 +110，净亏 |
| 24 bit | 529 | 262 | 5,896,913 | 同上，构建爆炸 |
| 构建分片 2/4/6/8/13 | 103–166 | 327–363 | 不变 | 全在噪声内 |
| `RAR_RS_RI_STOP` 8/16/32/64/128 | — | 267/303/343/323/301 | 5,979,729/5,912,557/5,899,789/5,898,668/5,898,260 | stop=8 快 60 ms 但赔 1.4%，不可用 |
| 低步进 greedy（`RAR_RS_MT_LOWSTEP=1`，走链不走索引） | — | 464–493 | 6,515,182 | 更慢且更差（每片重插链的老问题） |

两条可以写进设计前提的事实：

1. **20 bit 桶是构建/查询的联合最优**。桶数只改变两边的分配，不改总和；
   24 bit 能把体积再压 1.2 KB、waves 再省 30 ms，但计数表 64 MB，构建从
   100 ms 涨到 529 ms。
2. **构建的 100 ms 是 56 MB 随机散写的地板**：16 bit（表 256 KB，写入落点
   集中）只要 32 ms，说明成本全在"1 M 桶跨 56 MB 的散写"，不在计数。
   两级构建（先 4 K 粗桶、再在 13 KB 的粗桶内用 L1 表细分）理论上能把
   20 bit 的构建压到 ~50 ms，收益约 8% 的总时长，是本目录里唯一还剩的
   无损优化。
3. **候选停走没法和 DP 共存**：我们的 priced DP 需要"所有 improving 候选"
   才能定价，任何提前停止都直接换成比例损失（stop=16 就赔 0.25%）。

至此"在现有 DP + 行索引架构内提速"的选项已经全部试完，剩下的差距是架构性的：
官方用**受限候选的 greedy + lazy**（`FUN_1400468d4` 的 `best+5`/`best*0x4000`
早退）配合 128 KiB 子块并行，我们用的是**全候选定价 DP**。同等设置下我们只比
官方小 0.2%，却付了 2 倍时间——这 0.2% 就是 DP 的全部收益。


## greedy 层的实测否决，与"账本反转"（2026-11-16 深夜）

上一节把剩下的差距判为"架构性：官方用受限候选 greedy，我们用全候选 DP"。
按这个判断实现了 `windowed_greedy_parse`（`RAR_RS_MT_GREEDY=<depth>`，走同一
个 `RowIndex` 的 `collect`，lazy 阈 `RAR_RS_MT_GREEDY_LAZY`，最后仍交给
`convert_tokens` 复用 repeat-cache 语义），实测**否决**：

| 配置 | 体积 | 每片 parse（mt4，3.5 MB 片） |
| ---- | ---- | ---- |
| DP depth 64（现状） | 5,898,075 | 575–854 ms |
| greedy depth 4 | 6,612,844 | — |
| greedy depth 8 | 6,497,342 | 715–749 ms |
| greedy depth 16 | 6,412,192 | — |

即：**同等速度下比例差 10%**。受限候选 greedy 在我们这里不是"更快的同质量
解析"，而是"同速率的差解析"——因为它丢掉了两件 DP 免费做的事：memory/repeat
候选（`state.reps` 探测）和"短近距离 vs 长远距离"的定价。

实现过程中踩到的两个坑（后一个才是真 bug）：

1. `convert_tokens` 要求 token 流**覆盖每一个位置**，literal 必须显式写成一
   个 `(0, byte)` token。greedy 只推进 `pos` 不写 literal 时，`pos` 的推进和
   解码器的推进就错位，输出在第 2 个 match 之后整体偏位——表现是 UnRAR 报
   "checksum error"、体积比 DP 小 26%（假象）。
2. match 不能跨 slice 末尾（`limit = max_match.min(e0 - pos)`），否则会把下一
   片的字节重复吐一遍。

### 账本反转：我们的 waves 已经等于官方的全部耗时

把同一份 ntoskrnl（13.9 MB、`-m3 -md32m -mt24`）的两本账并排放：

| 阶段 | 我们 | 官方 |
| ---- | ---- | ---- |
| IO + CRC + 写盘 | ~150 ms | 含在 322 内 |
| filter 选取（`best_combined_specs`） | 46–48 ms | — |
| `LongRange::push` | 28–29 ms | — |
| `RowIndex` 构建 | 95–96 ms | — |
| **waves（并行解析+编码）** | **317–334 ms** | — |
| 合计 wall | 631 ms（第二次跑） | **322 ms** |

也就是说：**我们的解析本身（317 ms）已经和官方整包的耗时（322 ms）持平**，
2 倍的差距全部来自解析之外——IO 和三项全局开销（170 ms）以及没有与解析重叠。
比例上我们只大 0.2%（5,898,075 vs 5,886,560）。

结论修正：既然 waves 已经达标，正确的主攻方向不是"更快的解析"，而是
**把 300 ms 的固定开销拿掉或藏起来**：

1. IO/CRC 与解析重叠（读流 → 边读边 CRC → 分块喂给行索引构建），可省 ~150 ms。
2. `RowIndex` 构建（95 ms）与 IO 重叠，或改成"边读边建"的分段构建。
3. `best_combined_specs`（46 ms，213 块 × 13 通道）先用采样预筛通道，再全量确认。
4. `LongRange::push`（28 ms）可与刷盘重叠。

按 1–4 全做，wall 的理论落点是 330–380 ms，即官方的 1.05–1.2 倍，比例不变。

## 48 KiB DP 块：比例和速度同时变好（已落地）

`MT_DP_BLOCK_SIZE` 从 256 KiB 改成 48 KiB。这是本轮唯一"两边都赚"的改动，
因为块变小让价格/码长表（每块之间传递的那张）刷新更勤，同时每个 worker 的
DP 表从 8 MiB 降到 1.5 MiB：

| 语料 | 256 KiB | 48 KiB | waves |
| ---- | ---- | ---- | ----- |
| ntoskrnl 13.9 MB | 5,898,075 | **5,883,538** | 298 → 299 |
| code.bin（5.9 MB Rust 源码） | 1,125,053 | 1,119,493 | 118 → 111 |
| text.bin（7.7 MB markdown） | 1,598,504 | 1,585,410 | 174 → 171 |
| solid（三者一起） | 8,019,198 | 7,999,171 | — |

各等级同样成立：`-m1` 5,989,776 → 5,974,684、`-m2` 5,936,433 → 5,921,671、
`-m4` 5,869,710 → 5,855,069（waves 382 → 350）、`-m5` 5,848,805 → 5,834,207
（waves 473 → 452）。扫过的块大小 16/32/48/64/96/128/192/256 KiB 里 48 KiB
和 32 KiB 最好，48 KiB 在三份语料上总和最小。

顺带把 `LongRange::push`（28 ms）和 `RowIndex::build`（100 ms）放进同一个
`pool.join`：两者都只读 `data`、互不相干，串行 128 ms → 一起 106 ms。

## 现在的账（ntoskrnl 13.9 MB，`-m3 -md32m -mt24`，取两次最好值）

| 阶段 | 我们 | 官方 |
| ---- | ---- | ---- |
| 进程启动（空跑） | 67 ms | 90 ms |
| 读 + CRC + 写盘 | ~68 ms | ~60 ms |
| filter 选取 | 48 ms | 0 |
| 长距表 + 行索引 | 106 ms | 0 |
| waves | 311 ms | ~100–120 |
| **合计** | **547 ms** | **274 ms** |

体积我们 5,883,538，官方 5,886,560——**我们小 0.05%**。等级曲线：

| 等级 | 我们 | 官方 |
| ---- | ---- | ---- |
| -m1 | 501 ms / 5,974,684 | 170 ms / 7,562,367 |
| -m2 | 511 ms / 5,921,671 | 237 ms / 6,483,724 |

注意低等级：官方 `-m1/-m2` 是"快速预览"档（体积差得多），我们的 `-m1` 已经
达到他们 `-m3` 的体积。所以"速度相近"在低等级其实是指他们的 170–237 ms。

### 剩下的 2 倍在哪里

解析 CPU：我们 311 ms × ~16 核 ≈ 5 s；官方整包 274 ms，扣掉启动/IO 后解析
只有 ~100–120 ms 墙钟。即同样（略好）的比例下，我们的每字节 CPU 是他们
的 3.5 倍。原因是结构：官方是 3 类 prev 距离的受限候选 + 槽位定价 + rep 优先，
我们是 ~64 候选的全量定价 DP 加 rep 探测。depth 也降不动（d32 +1.5%、
d16 +2.6%），块大小已经最优，索引/候选侧的所有 shortcut 都试过。

结论：想再往下走只有三条路，且都要动结构：

1. **把解析换成官方形状**（受限候选 + 槽位定价 + rep 优先），唯一能到 1.0–1.2×
   的路，工作量以天计，比例有风险。
2. **砍掉波浪之外的开销**（filter 预筛 48 → ~18 ms；行索引改成"每位置存
   prev 距离链" 106 → ~50 ms），wall 到 ~420 ms（1.5×），比例不变。
3. **等级重映射**：给 `-m1/-m2` 一套真正的快档（depth 8 + 关掉 filter 探测），
   落点 ~300 ms / 6.5 MB，仍然远好于官方 `-m1` 的 7.56 MB。
