# RAR5 解码路径与官方对拍（未关闭）

> 目标：`Rar723.exe`（WinRAR 7.23 随包的那个 `Rar.exe`），工具 ghlab，项目
> `~/re/proj/ghlab`（该二进制的分析已入库，含 `rar5-filter` / `rar5-decode`
> 两条笔记）。本文件只留结论与锚点，取证过程在提交信息里。

## 已关闭：x86 滤镜（E8/E8E9）

`FUN_140042ce8` 是逆变换，由解码端的「应用已完整滤镜」循环 `FUN_140040f10`
逐条调用（该循环遍历 `ctx+0x8190` 计数的数组，每条 0x20 字节，带
start/length）。 它的语义与 `crates/rar/src/codec/common/filters.rs` 的
`e8_encode` / `e8_decode_in_place` 逐条等价：

| 项         | 官方                                | 我们                         |
| ---------- | ----------------------------------- | ---------------------------- |
| 操作码     | `0xE8`；`!e8_only` 时再加 `0xE9`    | `cmp_mask` = 0xFF / 0xFE     |
| 操作数位置 | `(CurPos + FileOffset) % 0x1000000` | 同（`X86_FILTER_FILE_SIZE`） |
| 步进       | 命中 +5，否则 +1                    | 同                           |
| 下界       | `i < len - 4`（需 5 字节）          | `n < 5` 直接返回             |
| 减法       | 回绕，**无守卫**（见下）            | 回绕（`wrapping_sub`）       |

编码侧是 `FUN_14004ac5c`，由写侧 `FUN_140048930` 调用，并顺带写出滤镜记录
（`type` 1=E8 / 2=E8E9、码表 `DAT_1400bb000` / `DAT_1400bb038`、长度字段）。
两个函数共用同一套「虚拟 16 MiB 地址空间」算术，方向只由调用者传入的基址符号
决定（mod 2^32 下加法即减法），所以函数本身与方向无关。

长期规则已并入 [`PITFALLS.md`](../../PITFALLS.md)
的「字节对齐」段（减法必须回绕、滤镜是纯函数因而区域可任意重切）。

### 踩过的坑：给减法加守卫

`FUN_140042ce8` 里有 `cand >= 0` 的把关，一度被读成「逆变换的减法需要
`addr >= offset`」，于是加了守卫。**错的**：官方流里确实存在操作数小于 `offset`
的情况，加守卫后那些字节被原样留下，**解坏真实归档**——实测官方 7.23 `-m3` 压 80
MiB 的 `MRT.exe`，回环 CRC 报错（`0x775C0113` vs `0xC449A434`），去掉守卫
立刻恢复（同一份矩阵 18 个用例全过）。

教训：单看一个函数的把关不足以判定方向（encode/decode 共用同一套虚拟地址算术），
**必须用官方产的档做回环**才能定案。

## 已定位：4 槽距离缓存

官方解码是**两段式**：

- `FUN_14007ab9c` 解符号，写成 16 字节记录（`+0` 类型、`+2` u16 长度、`+8` u64
  距离；数组在 `ctx+0x2ce0`，计数在 `ctx+0x2ce8`）。
- `FUN_140074aec` 回放记录产出明文（按 `x` 采样时最热的函数）。
- `FUN_1400444a4` 窗口驱动：`ctx+0xe8` 窗口缓冲、`+0x158` 窗口大小、`+0x178`
  位置、`+0x8190` 待应用滤镜计数、`+0xb1d8` 解码状态、`+0xb1c8`/`+0xb1c9` 标志。
- `FUN_140040c8c` 滤镜记录解析：0x20 字节/条，落在 `ctx+0x198`，容量 0x400。
- `FUN_140040f10` 应用已完整滤镜（见上）。

**四槽缓存 = 回放函数的 `param_1[0x16..0x19]`**（4 × u64），规则与我们逐条一致：

| 记录类型     | 官方                                | 我们                       |
| ------------ | ----------------------------------- | -------------------------- |
| 1 = 新距离   | 四槽整体下移，新值进 `[0]`          | `dist_cache_push`          |
| 2 = 重复     | 读 `[0]`，**不轮转**                | `Repeat` → `dist_cache[0]` |
| 3 = 缓存引用 | `[0] = 记录里的距离`，不碰 `[1..3]` | `dist_cache_touch`（前移） |
| 0 / 4        | 字面量串 / 未读                     | —                          |

类型 3 不碰 `[1..3]` 是自洽的：回放只读
`[0]`，其余三槽没有读者。所以**槽位选择与 轮转发生在 phase
1**（`FUN_14007ab9c`），那一步还没读。

未读的那一步不影响正确性：我们的编码器**确实**会发 index 1..3 的 `CacheRef`
（`parse/optimal.rs` 里 `state.reps.iter().position(..)`），而官方 UnRAR
能把这些流 逐字节还原，说明 phase 1 的规则与我们的 LRU 前移在实践上一致。

## 怎么找到的

穷举函数名不行就**采样**：仓库自带的
[`scripts/winrar-profile/`](../../../scripts/winrar-profile/)
（无管理员权限的穷人版采样器）在 `Rar.exe x` 解压一个 89 MB 的 RAR5 时采样，2240
次采样落到 252 个地址，最热的那簇就是解码路径。

- 必须 `-ExecutionPolicy Bypass`，否则脚本被策略拦下。
- 样本里混有其它模块的 RVA（减基址后是巨大值）；`Rar.exe` 自己的 RVA 落在
  `0x74xxx` 一簇，热函数即 `FUN_140074aec`。
