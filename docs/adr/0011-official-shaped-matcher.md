# ADR 0011：按官方形状重做匹配器（立项）

- 状态：**已否决**（2026-11-15；三种形态实测均不敌现状——8 棵类树、共享 `son` + 类表头、官方哈希链。本 ADR 现在的作用是记录逆向结论、三次否证的实测数据，以及这里留下并已落地的四项收益：末端封口删复核、表头按窗口定尺寸、停滞降档、下降步预取）
- 关联：[ADR 0009](0009-match-finder-kernel.md)（BT4 内核）、[ADR 0010](0010-hash-ring-finder.md)（哈希环重写，已否决）；`docs/PITFALLS.md`「压缩内核」；`PLAN.md`「性能」

## 背景

当前主路径是「BT4 树收候选 + 融合单遍 DP 定价」。在 ntoskrnl.exe（13.9 MB，`-md32m`）上的定论：

| 方案 | 时间 | 体积 |
|---|---|---|
| 现状（树 + DP，m3） | 4329 ms | 5,828,867（41.88%） |
| 树 + 贪婪早退（m3 临时改路由） | 3459 ms | 6,656,044（47.83%） |
| 官方 WinRAR 7.23（m3） | 1466 ms | 5,886,469（42.30%） |

价格分解（m3，总 4329 ms）：`collect` 2913、`dp` 978、`prep` ~110、`emit` 111、`convert` 29。其中 `collect` 里 60 ns/位置是地板（`RAR_RS_SEQ_PRICE_TIER=1` 实测 2302 ms），其余 ~150 ns 是"为 DP 多给候选"付出的树深。

已排除的旋钮（都有实测）：树预算 ≥24 不再咬合；近窗口大小是工作集代价（10% 换 0.3pp）；`OPT_BLOCK_SIZE`/DP 状态带宽无影响（32 KiB 与 64 KiB 同速）；校验上限收紧只是比例换时间；每个候选的单价由「越界检查的 `son` 索引 + 8 字节比较 + `match_length_at` 验证」决定。

官方之所以既贪婪又深还快：**每个候选只花一次字节比较**——每块预计算哈希、8 个距离类近距优先、子节点数组按位置索引，工作集全在热内存；代价是比例低 0.42pp。

## 决策

新开一条匹配器实现，形状照官方：`collect` 阶段不再走 BT4，而是

1. **每块预计算哈希**：进入 64 KiB 解析块时先扫一遍，把该块每个位置的 4/5 字节哈希与长哈希写进紧凑数组（`u32`/位置），后续下降只读该数组。
2. **按位置索引的子节点**：`son: Vec<[u32; 2]>` 之类的平铺数组，用位置而非内容键定位，避免 BT4 桶的随机访问；插入位置与查询位置都在同一块内，命中集中在最近写入的行。
3. **8 个距离类**：把窗口按 `hash / (window / classes)` 分桶，近距类优先搜索、远距类给独立预算（官方 `+0x188 = budget >> 2` 就是远距预算），使"就近优先"直接体现在搜索顺序上，而不是靠距离约束事后过滤。
4. **预算 + 早退**：沿用官方量级（m3 ≈ 100 候选/位置），找到 `NICE_MATCH_LENGTH` 以上即停；候选以 `(len, dist)` 递增形式交给现有定价层。

不变的部分：`parse/pricing.rs`（`EncoderMatchState`/`TokenPrices`/`SlotPricer`/`convert_tokens`）、`parse/block.rs` 的发射块策略、`LongRange`、`ShortFinder`、DP 本身。新匹配器只替换 `collect_block_matches` 的候选来源。

## 验收门槛

按块回归优先（比整体百分比更能定位退化）：

- 逐块 `tokens`/`literals` 对照现状实现，任何一块退化 >2% 视为回归（工具：`RAR_RS_PROFILE` 分相 + `RAR_RS_DEBUG_PRICES` 逐块计数）。
- 整体：ntoskrnl m3 ≤ **2200 ms** 且 ≤ 42.5%（现 4329/41.88%）；d2d1 m3 不变慢且不变大；text/xml 保持 16.5%/10.0%；mt8 不退化。
- 不达标就整体回退到 `781afa0`（本 ADR 只记录方向与实测，不预设保留）。

## 分期

1. **P1 骨架**：块内哈希预计算 + 位置索引子节点 + 预算早退，接现有 `collect_block_matches` 接口，先只保证正确（606 测试 + 忽略的字节回归矩阵）。
2. **P2 距离类**：8 类分桶与远距预算，量时间/比例曲线，定 m1–m5 的候选数与类数。**已否决（两种形态），见文末 P2 与 P2' 两节。**
3. **P3 与 DP 合流**：候选递增序、`ShortFinder` 合流、逐块回归门槛跑通。
4. **P4 并行**：MT 切片带块内预计算（每 worker 自建索引即可，无需共享）。

## 风险

- 预计算哈希的前置扫描本身是 13.9 M 次读，若不能与下降共用缓存行，会变成纯亏损（P1 必须先量这一项）。
- 位置索引子节点在**跨块**匹配上不如树：块边界的历史只能靠 `LongRange` 与短表，需在 P1 就用 `mixed`/`sparse` 语料验证。
- 这是新增实现，不是改动主路径：P1 起就放在 `parse/hashmatcher.rs`，用环境变量接入 `BlockSearch`，默认关闭，达标后再切默认。（P2 实测否决该形态后，这条路径已整体删除，见文末「决定」。）

## P1 前置测量（2026-11-15）

先量「预计算那一趟」的净成本（`crates/rar/examples/hashprobe.rs`，两表各 `u32`/位置）：

```
precompute 13917560 positions: 10 ms (2 tables, 108730 KiB written)
```

即 13.9 M 位置铺两张哈希表只要 **10 ms**，占 `collect`(2913 ms) 的 0.3%、整档的 0.2%——纯流式写、预取友好。**P1 的第一个风险（预扫描本身亏损）不成立，继续做骨架。**

仍待验证的是第二个风险：108 MB 的哈希流在下降读回时是否还在缓存里。按 64 KiB 解析块算，单块的哈希切片是 512 KiB，能落在 L2/L3；跨块下降则要重读。P1 的骨架必须按块分配/按块读，而不是整文件一张表。

## P1 第二个测量：读回是否热

同一探针加了读路径对照（1M 次伪随机查表）：

```
reads: 1.2 ns/lookup inside a 64 KiB block slice, 6.2 ns/lookup across the whole member
```

块内哈希切片（512 KiB，两表）**1.2 ns/次**，整成员表（108 MB）**6.2 ns/次**，差 5×。结论：

- 9 个候选/位置的哈希读 ≈ 11 ns，100 个候选 ≈ 120 ns —— 与官方 105 ns/位置同量级，说明**哈希读就是他们的主要成本项**，布局比算术重要；
- 因此候选链**必须留在块内**：块内下降走 1.2 ns 的路径，跨块候选交给 `LongRange` 与 `ShortFinder`，不要沿着块内子节点走进更早的块（那一步就是 6.2 ns）。
- P2 的 8 个距离类必须按块内偏移分层，而不是按整个窗口分层，否则类内索引会跨块。

## P1.3 结果：块内候选密度不够——「块内」前提不成立

`hashmatcher::tests::reports_candidate_density_and_cost`（1 MiB 文本，64 KiB 块，`head` 1<<14、8 字节键、预算 32）：

```
hashmatcher: 109852 candidates over 983040 positions (0.11/pos), 4.5% reach 16 bytes, 39.0 ns/pos
```

BT4 在同一份数据上是 ~1.1 候选/位置、且 20.8 M 次校验/13.6 M 次下降。块内链只有 0.11/位置，低一个数量级：64 KiB 块里每个哈希槽平均只落 ~4 个位置，去掉哈希碰撞后同键命中极少，只能看到很靠近的重复。

**结论：候选表不能按块截断。** 官方之所以只花 105 ns/位置，靠的不是"块内"，而是**子节点按位置索引**带来的空间局部性（最近写入的子节点在相邻行，8 个距离类把窗口切成多段，近段总在热区）。这与我们此前那版「位置索引 `chain8`」形态一致，但那次是把它挂在一个 8 字节单键上、逐候选付 `verify`，所以只有哈希环的水平（48.18%）。

P2 必须同时满足三点才有希望：全窗口覆盖（回比例）、按位置索引的子节点（局部性）、每步只做一次字节比较（单价，靠树形生长而非逐候选 `verify`）。三者的共同点就是 BT4 本身——差别只在 BT4 的 `son` 是内容键定位的树、按窗口复制，而官方是位置索引 + 距离类分层。

下一节 P2 的实测把这条假设否掉了。

## P2 结果：8 个距离类方案否决（2026-11-15）

### 实现形态

`parse/hashmatcher.rs` 里 `ClassMatchFinder`，`RAR_RS_CLASSES`（1..=8，缺省关）选中，`RAR_RS_CLASS_FAR` 给远距预算的右移（缺省 2）。三条机制：

- **位置索引子节点**：`son` 槽位是 `class*block_len*2 + (pos - base[class])*2`，块内相对索引而非 `pos & mask`。这是与 BT4 唯一的实质差别：帧滑动时只要平移 `base[]`（O(classes)），子节点一个字节都不用重写；BT4 每次 `rebase` 都要重排整个 ring。
- **类环**：每类一棵 BT4 形态的树，覆盖一段连续的 `block_len`（2 的幂）块，8 类轮转；近类吃满预算，远类共享 `budget >> 2`。整环宽 `classes * block_len`，按窗口一次分配（改名即失效，不能像 BT4 那样原地长大）。
- **类不是「距离带」**：环可以比窗口宽，两块可能落在同一带上；早期版本用 `band -> class` 下标表，同带冲突直接丢掉一整块。现在按块龄从近到远逐个走。

另有一条正确性前提：`len_limit` 被输入尾部截断时，**不允许**「整段前缀相同 → 收养子树」。BT4 那条捷径只在限长是真实上界时成立；截断的限长证明不了后面的字节，收养之后树的序就被破坏，之后每次走行都会虚报长度（实测在 5 万位置处虚报 16 字节对 7 字节）。截断时改为封口，两端都不认。

保真性有测试钉住：`stream_equals_bt4_when_one_class_covers_the_window`——单块覆盖整帧时，1/2 类给出的候选流与 BT4 **逐条相同**（5 万位置零差异），所以下面的差距不是实现跑偏，而是「把一棵树切成多棵」本身的代价。

### 测量

ntoskrnl.exe 13.9 MB、`-m3`、`DICT=8`（32 MiB），本机。比例可复现，墙钟有噪声，故同时列 `RAR_RS_PROFILE` 相位：

| 方案 | 比例 | collect | dp | 说明 |
|---|---|---|---|---|
| BT4（现行） | **44.61%** | 3067 ms | 928 ms | 基线，220 ns/位置 |
| 8 类，远预算 `cut>>2` | 45.17% | 3633 ms | 887 ms | +18% collect，-0.56pp |
| 8 类，`RAR_RS_NEAR=32 MiB`（不发生 rebase） | 45.07% | — | — | 排除 rebase 丢块的影响 |
| 8 类，远预算 `cut>>0`、`>>1`（同上） | 45.06% / 45.06% | — | — | 远预算给到 96 也不回比例 |
| 4 类 / 2 类 | 45.21% / 44.85% | | | 都劣于基线 |

旁证：
- ntoskrnl 前 4 MiB（单块覆盖整帧）三种类数比例都**与 BT4 完全相等**（45.77%），印证上面那条保真测试。
- `verify` 计数 4 285 758 对 BT4 的 4 525 053：类方案给的候选更少，比例还更差。
- 64 MiB 文本 m3：28.28% → 28.92%（+0.64pp），33.5 s → 43.7 s。

### 为什么切分必然亏

BT4 的一次 96 步下降，是在**按内容排序**的一棵树里走：命中哪个年龄段由内容决定，各年龄段的候选在同一次下降里就能走到。按年龄切树之后，每个年龄段要单独付一次下降预算，等于把「96 步覆盖全窗口」换成「96 步覆盖最新一段 + 24 步覆盖其余各段」。把远预算从 24 提到 96（`RAR_RS_CLASS_FAR=0`）比例一点不回来，说明卡点不是预算不够，而是**分层后每棵树的形状更碎**：96 步在新树里走不到 BT4 同一步数下能到的深层节点。再加预算就是纯亏时间。

P1.3 末尾那条假设——「官方赢在位置索引 + 距离类带来的空间局部性」——因此不成立：类树更小更热，但主导项是步数，不是缓存。位置索引带来的那一点局部性（`rebase` 免重写）省下的是每帧 O(窗口) 的一次性开销，摊到 13.9 M 位置上不够看。

## P2'：改成官方的真形态（共享 `son` + 8 份类表头）——同样否决（2026-11-15）

「8 棵树」被否决后还剩一种读法：官方并没有 8 棵树，它只有**一份**按位置索引的子节点数组（`min(dict, 1 GiB) × 4B` 两份，见 ADR 0010），距离类只是 8 个**入口**（`+0x48`/`+0x68` 的链表头尾），预算 100 由近类吃满、远类吃 `budget >> 2`。照这个形态重写：一份 `son`（`(pos & mask) << 1`，与 BT4 同布局）+ `classes` 份 head 快照，每写满 `block_len` 就把当前快照轮转到下一格并清空；近快照插入并吃满预算，老快照只搜不插，所有老快照**共享**一份远预算。单快照覆盖整帧时，候选流与 BT4 逐条相同（有测试钉住），所以下面的差距不是实现跑偏。

ntoskrnl.exe `-m3`、32 MiB 窗口：

| 方案 | 比例 | collect |
|---|---|---|
| BT4（现行） | **44.61%** | 2704–2729 ms |
| 8 类共享树，远预算 1 步/类（`FAR=8`） | 45.54% | 2640 ms |
| 8 类共享树，6 步/类（`FAR=4`） | 45.01% | 4985 ms |
| 8 类共享树，24 步共享（`FAR=2`） | 44.63% | 7917 ms |
| 8 类共享树，96 步共享（`FAR=0`） | 44.61% | 7848 ms |
| 2 类共享树（`FAR=2`） | 44.61% | 3498 ms |

读法：`FAR=8` 时每个老快照只走 1 步，等于只用最新一块（32 MiB / 8 = 4 MiB）——45.54%，比 BT4 差 0.93pp，时间还略快。往后每加一段远走行，比例就回到 44.61%，正好把那 0.93pp 补回来，代价是 +5.3 s。也就是说**距离类买到的候选，BT4 在同一次按内容排序的下降里本来就能走到**，而它为此要多付一次随机访存。

代价不在入口，在远走行：入口查表几乎免费（`FAR=8` 比 BT4 还快 64 ms，head 缩到 2^17 后更好命中），付费的是远走的每一步——入口点在窗口末尾往回 `block_len` 处，每一步都是一次 DRAM 缺页，约 16 ns/步；24 步 × 13.9 M 位置就是 5.3 s。

顺带钉住两个事实：

- **BT4 的预算根本不咬合**：`chain_len` 96 / 256 / 1024（m3/m4/m5）的 collect 分别是 2728.5 / 2727.7 / 2772.0 ms，比例 44.61 / 44.52 / 44.50%。树先走空了，所以「官方 100 步、我们 96 步」不是差距来源。
- 位置索引那条理论收益（`rebase` 免重写整个 ring）摊到 13.9 M 位置上不足 1%：把「每帧一次 O(窗口) 重排」省掉，救不了每候选的单价。

结论：距离类在两种形态下都被**严格支配**——切树是 +18% 时间 / -0.56pp，共享树是 +193% 时间 / 比例持平。P1.3 末尾那条「官方赢在位置索引 + 距离类」的假设，至此彻底否掉。

## 决定

- **否决距离类方案（两种形态都否决）**，默认路径继续是 BT4。相关代码已整体删除：`parse/hashmatcher.rs`、`parse::Finder` 枚举、`collect::BlockFinder` trait、`EncoderState::class`、`profile::BAND` 一并移除；`RAR_RS_CLASSES` / `RAR_RS_CLASS_FAR` 不再存在。留着的只有两条与它无关的正确性/性能收益（见下条）。
- 保留下来的那次改动是 `9cbb354`：**下降在输入末端封口**（截断的 `len_limit` 不再收养子树，树的序不再被破坏），因此 `collect` 里那趟 `match_length_at` 复核可以整趟删掉——release 里只剩 `debug_assert`。ntoskrnl m3 collect 2838.5 → 2745.6 ms（-3.3%），比例 44.61% 不变。
- 验收线（≤ 2200 ms 且 ≤ 42.5%）在距离类形态下无望：需要同时 -47% 时间与 -0.2pp 比例，实测是 +18% 时间与 +0.56pp。
- 缺口仍然是**每候选单价**（ADR 0009 的复述）：官方整档 105 ns/位置，我们光 `collect` 就 212 ns/位置。这一步的常数已经量到底：一步 32.8 ns 里只有约 4 ns 是访存缺失（树整体进 L2 后仍要 28.4 ns），预取两个子节点只拿到 3.3%，无分支侧向选择毫无变化（见下节「下降步的单价」）。两位置交错下降的上限是藏掉那 4 ns，代价是把循环改成两宽流水并放弃候选流不变的验证手段，按数据否决。P3/P4 在当前形态下没有意义，暂缓。

## P3 之前的收益：树表头按窗口定尺寸（-14%，比例零代价）

P2 反复测到的一件事：**BT4 的步数是自己造出来的**。`TreeMatchFinder` 的表头固定
`HASH_BITS = 20`（2^20 桶、4 MB），与窗口无关；32 MiB 的 dict 下平均每桶 32 个位置，
桶深直接变成下降步数。固定位宽扫描（ntoskrnl m3，交替 A/B）很干净地证明了这点：

| 表头位宽 | collect | 步数 | 比例 |
|---|---|---|---|
| 2^20（改前） | 3380.8 / 3283.8 ms | 80.65 M | 44.61% |
| 2^22 | 2824.3 / 2889.6 ms | 74.76 M | 44.61% |
| 2^24 | **2677.4 / 2765.7 ms** | 72.80 M | 44.61% |
| 2^26 | 3008.7 / 3205.7 ms | 72.27 M | 44.61% |

位宽只花步数、**一个 pp 也不影响候选质量**（44.61% 在四种位宽下完全一致——树是内容
排序的，桶深浅只决定从哪儿开始走，不决定能走到哪儿），所以这是纯收益项。落地形态：

- `head_bits_for(window) = window.trailing_zeros().clamp(23, 24)`，`new()` 用窗口算初始桶数；
  `grow_to()` **只增不减**，增时才清表（帧会从 64 KiB 爬到 `keep + chunk`，事后加宽等于
  rehash 丢历史）。
- 表头改成 `0 = 空、值存 pos + 1`，于是 `vec![0; 1 << bits]` 走 calloc、只在实际哈希到的
  桶上缺页——小文件不必为 32 MB 表付 memset。`head_link()` 负责解回 `NO_LINK`。
- 建表尺寸取 `window.min(near_window_max() + chunk.len()).min(combined.len() * 4)`，既不让
  小文件建出大表，也保证帧爬升时不会触发重建。

实测（交替 A/B，baseline = `f1c9b4c` + 步数计数器、2^20 表头）：

| 语料 | 级别 | 改前 | 改后 | 比例 |
|---|---|---|---|---|
| ntoskrnl.exe 13.3 MiB | m3 | 4623 ms | **3961 ms（-14.3%）** | 44.61% → 44.61% |
| d2d1.dll 6.3 MiB | m2 | 1250 ms | **1152 ms（-7.8%）** | 38.13% → 38.12% |
| d2d1.dll 6.3 MiB | m3 | 1272 ms | **1165 ms（-8.4%）** | 38.03% → 38.03% |
| `perf/text.bin` 64 MiB | m3 | 31433 ms | 30290 ms（-3.7%） | 28.28% → 28.28% |
| 256 KiB / 512 KiB / 1 MiB 切片 | m3 | 36 / 70 / 156 ms | 35 / 71 / 156 ms | 全同 |

位宽下限为什么是 23 而不是 21：把初始桶数压到 2^21 时
`encoder::tests::long_range_matches_compress_distant_repeats`（2 MiB 随机 + 2 MiB 精确副本）
会红——同一位置上树几乎不工作（75 步）、长距探针反而更多（49024 次）却抓不到 2 MiB 外的
副本。机制没有完全查清（长距探针的门是 `longest < 64`，合理的怀疑是浅树给不出足够长的
`offered`，探针虽然跑了但被 `ll > offered` 之外的条件吃掉），因此下限钉在 23，并让那条
测试继续看守它。表头因此多占 28 MB（32 MB vs 4 MB），与 dict 同量级，可以接受。

## P2 之后：每候选单价已到地板（2026-11-15）

两条与结构无关的收益落地之后（`9cbb354` 下降末端封口、`fcd8a60` 表头按窗口定尺寸），
m3 的 ntoskrnl 是 collect 2455 ms + dp 890 ms，比例 44.61%。这一段把剩下的钱花在哪儿
逐个消融了一遍，结论是**没有白干的活**——每一处能砍的工作都带比例价格。

单次下降的步数（72.80 M 步 / 13.1 M 次下降 = 5.6 步）已经咬不到预算：`chain_len`
96 / 256 / 1024 三档的 collect 只差 40 ms。所以时间都在「每步 34 ns」上，而它随工作集
单调上升，与结构无关：

| 语料 | 步数 | ns/步 |
|---|---|---|
| 1 MiB 切片（全在 cache） | 4.09 M | 21.8 |
| 4 MiB 切片 | 15.50 M | 28.9 |
| ntoskrnl 13.3 MiB | 72.80 M | 34.4 |

把树本身缩小（`RAR_RS_NEAR` 8192 / 2048 / 512 KiB）只把 41.8 → 34.0 → 31.5 ns/步拉回来，
比例却 44.61 → 44.96 → 45.29%：5.6 次依赖访存的位置，只能在「少走几步」和「少拿候选」
之间二选一。

DP 的分解（m3，13.9 M 位置，dp ≈ 917 ms = 66 ns/位置）：

| 消融 | dp | 比例 | 差额 |
|---|---|---|---|
| 基线（12 步上限、2 个 rep 探针） | 917 ms | 44.61% | — |
| 只剩字面量松弛 | 104 ms | — | 循环骨架 + 字面量定价 = 7.5 ns/位置 |
| 关掉 rep 探针 | 633 ms | 45.32% | 探针 284 ms（20 ns/位置） |
| 步数上限 12 → 1 | 742 ms | 45.20% | 多步定价 175 ms（12 ns/位置） |
| 只探 `reps[0]` | 779 ms | 44.69% | −138 ms / +0.08pp |
| 步数上限 8 / 6 / 4 | 866 / 826 / 907 ms | 44.64 / 44.69 / 44.82% | 同上，全是比例杠杆 |
| `RAR_RS_COMMIT` = 32 / 16 | −44 / −197 ms | 44.70 / 45.14% | collect 同步 −174 / −433 ms |

剩下 ~350 ms 是 reaches 构建、每个 run 的 `SlotPricer::for_run`（`EncoderMatchState::plan`
的槽位分类）和四个数组的写回（`arrive_reps` 每位置 16 B 就是 222 MB），一份都不是余量。
顺带否掉两个假设：`NICE_MATCH_LENGTH` 64 → 32 对 collect、dp、比例**三项全无影响**
（早退本来就不咬合）；把两次 rep 探针的 `pos` 八字节装载合并成一个 head word（写过
`repeat_reach`）也在噪声内——LLVM 早已把那个字留在寄存器里。

结论：**在这个候选生成形态下，每位置 ~205 ns（collect 190 + dp 66 里可归因到 collect 的部分）
就是地板**。要往验收线 2200 ms 走，缺口的 1.2 s 只能来自「每位置依赖访存的次数」这个
形态本身，而不是常数。ADR 0009 里那条用体积换速度的多槽链是唯一还没试过的方向。

## 官方形态的哈希链：第三种形态，同样否决（2026-11-15）

前两节否决的都是「树 + 距离类」，但官方的真实形态一直只有 ADR 0010 的静态线索。这一段把
`Rar723.exe`（x64，835,792 B，md5 `c7b8d0c2b6a3851291fd446113cbfc5d`）的候选搜索整个逆了
一遍，按官方形状重建，再在同一套 collect + 定价 + 发射路径上对拍。结论：**形状照搬也拿不到
官方的速度，而且比例更差**。

### 官方到底怎么走（`FUN_1400468d4`，1217 B）

- 链头**不查哈希桶表**：直接读 `chain[pos % window]`（`finder+0x120`，每位置一个 `u32`，
  内容是「上一个同哈希位置的距离」）。哈希在每块预计算阶段（`FUN_14004115c`）就算好写进数组了。
- 每步的检查顺序：`budget == 0` → 距离上界 `min(window, pos - cur)` → 单调性
  （`uVar11 <= seen` 即 return）→ **首字节与哈希双发散即 return** → 只有
  `input[cur + best_len] == input[pos + best_len]` 才做全长比较（逐字节，无字对齐）。
- 命中后不是简单继续走链，而是**look-ahead**：读 `chain[cur + 1 .. cur + len - 5]` 这些
  相邻槽（顺序访存），跳到其中距离最近的那个节点继续。`len - 5` 个节点只花一次迭代。
- 剪枝 `best_len > 2 && best_dist * 0x4000 < dist && len < best_len + 5` → 放弃该位置；
  记候选 `len > 4 && (best_len + 1 < len || dist >> 5 <= best_dist)`（16 B/项、上限 0x1000）；
  `len > 0xb` 且非快速模式 → 立即返回。
- 预算 `+0x184` = `{2, 18, 45, 100, 150}` 按等级（m3 = 100），快速模式 `>> 2`。
- 预计算阶段的「8 个距离类」其实是**哈希域分类**（`class = min(7, hash / (space / 8))`，
  头 `+0x48`、尾 `+0x68`、链 `+0xb478`），不是距离分桶；另有一套长哈希分类。

### 实测（ntoskrnl 13.3 MiB，m3，32 MiB dict，同一次构建对拍）

| 形态 | collect | dp | 比例 | steps | 步/位置 |
|---|---|---|---|---|---|
| BT4（现状） | 2423.0 ms | 891.8 ms | **44.61%** | 72.80 M | 5.2 |
| 链，预算 150，look-ahead 全开 | 2802.8 ms | 719.4 ms | 46.22% | 108.99 M | 7.8 |
| 链，预算 24，look-ahead 仅 `len ≥ 32` | 2739.7 ms | — | 45.45% | 111.07 M | 8.0 |
| 链，预算 150，look-ahead 仅 `len ≥ 32` | 5384.3 ms | — | 45.19% | 309.91 M | 22 |
| 链，预算 150，无 look-ahead | 5765.8 ms | — | 45.39% | 341.11 M | 25 |

链长实测（4 MiB、16 MiB 窗口、5 字节哈希）：median 3、p90 85、p99 353、平均 24，访问到的
节点全部同哈希（链接本身是对的）；桶平均间距 25581。也就是说链本身没问题，是**遍历顺序**
决定了一切。

### 为什么照抄形状还输

1. **每步的信息量不同**。BT4 的下降是内容序的：一次 `son` 访问加一次 8 字节比较就把候选空间
   砍掉一半，5.2 步就摸到长匹配。官方的链是距离序的：每步只排除一个候选，8–25 步才能达到
   同样的深度，而每步照样一次随机访存。
2. **距离序 + 只记变长 = 候选集偏近偏短**。链先给出「近而短」的匹配，之后更远的候选必须
   *严格更长* 才会被记录，长候选常常在预算耗尽前没轮到；BT4 先给长匹配，短的就不必记了。
   这直接换算成 0.6–1.6pp 的比例。
3. look-ahead 能救命也能要命：全开把 collect 拉到 2803 ms，但比例掉到 46.22%（跳过了真能
   变长的节点）；只在 `len ≥ 32` 时跳，比例回到 45.19%，collect 却回到 5384 ms。这条曲线
   上没有比 BT4 更好的点。

官方 1466 ms / 42.30% 与我们 3695 ms / 44.61% 的差距，因此**不是候选结构能解释的**。剩下的
怀疑对象是「搜索多少个位置」：官方 `+0x300b8`/`+0x300bc` 两个计数器驱动的快速模式会让大量
位置根本不进搜索，而我们的 `searches` 是 13.1 M / 13.9 M 位置，几乎每个位置都在搜。

### 决定

- 原型（`parse/chainfinder.rs` + `Finder` 枚举 + `BlockFinder` trait）**删除**，理由与前两节
  相同：一条默认关闭、实测严格更差的路径是纯维护成本。默认仍是 BT4。
- 保留的资产是**这份逆向结论**：官方候选生成的每个启发式、每条常量、每步的检查顺序都记在
  这里，下一次要试「少搜一些位置」时不必再从机器码重来。
- 下一步（若继续）：先做官方那个「计数器驱动的快速模式」的等价物——它砍的是位置数而不是
  每步成本，是唯一还没被否掉的方向。

## 「少搜一些」的最后一条旋钮：停滞降档（2026-11-15）

三次形态否决之后，唯一还没被检验的官方机制是**计数器驱动的快速模式**：`Rar.exe` 在
miss 计数跑起来之后把预算降到 `>>2`。它不是跳过位置（我们的 `fast_tree` 才是），而是
在同一批位置上**少走几步**。把它做成可测的档位：

- `RAR_RS_STALL` = 连续多少个「一无所获」的位置之后进入降档（0 或缺省 = 关闭，即现状）；
- `RAR_RS_STALL_CUT` = 降档期间的步数上限（缺省 8）；
- 实现：`parse/collect.rs` 的 `SearchState.stall` 计数，`stall_cut()` 决定本次下降的
  `cut`；任何候选（`offered >= 4`）立刻复位。

### 曲线（ntoskrnl 13.3 MiB，m3，`collect` 取自 `RAR_RS_PROFILE`）

| 档位 | collect | 比例 | steps |
|---|---|---|---|
| 关闭（现状） | 2384 ms | **44.61%** | 72.80 M |
| 8 / 4 | 2324 ms | 44.67% | 70.82 M |
| 2 / 4 | 2155 ms | 44.92% | 66.33 M |
| 4 / 2 | 2120 ms | 45.00% | 64.86 M |
| 1 / 4 | 2157 ms | 45.01% | 64.99 M |
| 2 / 2 | 2047 ms | 45.17% | 62.19 M |
| 1 / 2 | 1948 ms | 45.31% | 60.11 M |
| 1 / 1 | 1798 ms | 45.62% | 56.18 M |
| `RAR_RS_COMMIT=32`（既有旋钮） | 2271 ms | 44.70% | 64.90 M |
| `COMMIT=32` + `STALL=1/4` | 1980 ms | 45.12% | 57.38 M |

d2d1.dll（6.3 MiB，m3）：关闭 1036 ms / 38.03%；2/4 → 983 ms / 38.20%；1/2 → 950 ms / 38.39%。

### 读法

- **步数只降 2.5%**（8/4 档）说明「一无所获」的位置本来也没走满预算——步数集中在**有产出**
  的位置上，那里缩短下降直接用候选换时间。所以这条曲线的斜率就是比例价格，没有白捡的部分：
  从 44.61% 走到 45.62% 换来 25% 的 `collect`。
- 温和段（8/4、2/4）被既有的 `RAR_RS_COMMIT` 支配：后者用 +0.09pp 换 218 ms。
- 激进段（1/1、1/2）是目前**最便宜的速度**：+1.0pp 换 −25% collect，比 `COMMIT=16`
  （+0.53pp 换 −17%）更划算；两者可叠加（`COMMIT=32` + `1/4` = +0.51pp 换 −17%）。
- 默认仍**关闭**：这是一条「按需换取速度」的档位，不是无代价收益。要用时打开
  `RAR_RS_STALL`，比例预算按上表挑档。

### 验收线现状（真实归档路径，`-m3 -md32m -mt1`，ntoskrnl.exe 13.9 MB）

`crates/rar/examples/collectbench.rs` 走的是未过 x86 滤镜的 `encode()`，验收线却在归档路径上，
所以这里用 `rar a -m3 -md32m -mt1` 直接量：

| 配置 | 时间 | 体积 |
|---|---|---|
| 现状（默认） | 3769 ms | 5,828,867（41.89%） |
| `STALL=1/4` | 3581 ms | 5,885,076（42.30%） |
| `STALL=2/2` | 3450 ms | 5,906,469（42.45%） |
| `STALL=1/1` | 3245 ms | 5,970,031（42.88%） |
| 官方 WinRAR 7.23 | 1466 ms | 5,886,469（42.30%） |

两件事同时成立：(1) 四处落地（`9cbb354` 封口删复核、`fcd8a60` 表头定尺寸、停滞降档关闭、
下降步预取两子节点）之后，同一份输出比 ADR 立项时的 4329 ms 快了 14.0%，比例一字未变；(2) **在官方那个输出尺寸上
（42.30%）我们仍要 3581 ms，是它的 2.44 倍**。验收线的 2200 ms 还没到，`STALL=2/2` 能过
42.5% 的比例门（42.45%）但时间是 3450 ms。

## 下降步的单价：预取与分支都试过，只剩 3%（2026-11-15）

前面的「每候选单价已到地板」留下一个未验证的猜测：一步 34 ns 里有多少是**访存延迟**。
访存延迟能靠重叠掩盖（两位置交错下降、沿路径预取），指令吞吐不能。这一节把它分开了。

### 先量清楚「一步」里有什么

`descent` 每步两次**串行**依赖访存：先读节点的子链接对 `son[pair]`，拿到 `current` 之后
再读 `input[current + len]` 比较。串行是因为后者的地址由前者的内容决定。

把 `RAR_RS_NEAR` 压到 256 KiB（整棵树立在 L2 里）再量：

| 工作集 | steps | collect | ns/步 |
|---|---|---|---|
| 13.3 MiB 窗口 | 72,804,754 | 2391.4 ms | 32.8 |
| 256 KiB 窗口 | 60,902,754 | 1732.7 ms | 28.4 |

**整棵树进 cache 也只从 32.8 降到 28.4 ns/步**。也就是说这只步的 87% 不是 `son` 数组的缺失，
而是这条指令路径本身（约 100 个周期：两次地址计算、`resolve` 的环绕减法、8 字节比较、
`trailing_zeros`、两个不可预测分支）。访存能占的部分只有 4 ns 左右。

### 于是三种「重叠」手段的实测（ntoskrnl m3，交替 A/B 各三轮）

| 手段 | collect | seq 总时 | 比例 |
|---|---|---|---|
| 无 | 2394.4 ms | 3488 ms | 44.61% |
| 预取两个子节点的**链接对**（各 1 行） | — | 3473 ms（−2.2%） | 44.61% |
| 预取两个子节点的**输入字节** | — | 3740 ms（**+5.3%**） | 44.61% |
| 两者都预取 | 2314.8 ms（−3.3%） | 3373 ms（−3.3%） | 44.61% |
| 侧向选择改成无分支（`cmov` + 索引写） | — | 3397 ms（噪声内） | 44.61% |

读法：提前一拍把**下一跳的链接对**拉进来有用（两处都能用上，因为命令当拍就知道两个候选地址）；
只预取输入字节反而更慢（多了两条永远有一半用不上的加载，把 LSU 占满）；把「往左还是往右」写成
无分支也没有任何变化，说明这个分支本来就没在误预测上花时间。

落地的是「两者都预取」，`steps` 与候选流不变、比例一字不变，实测：
collect −3.3%，ntoskrnl m3 3488 → 3373 ms，1 MiB 前缀 164 → 156 ms，64 MiB 文本 27812 → 26752 ms，
d2d1 m3 1020 → 1014 ms。

### 结论

**两位置交错下降（2-way ILP）不再值得做**：它的上限就是「把剩下的 4 ns 访存完全藏掉」，
即使全拿到也只有约 12%；而它要在 `collect_block_matches` 里把逐位置循环改成两宽流水，
还要让第二个位置在 `committed_through` 尚未更新时先猜着搜（约 6% 的位置会被追认成已提交，
多插入一个节点，候选流与比例都随之漂移）。用 300 行改造去换一个 12% 的上限、并且放弃
「候选流逐字节不变」这个验证手段，不划算——这条按数据否决。

真正剩下的差距不在这一步的单价，而在**每位置要做多少步**（我们 5.2 步、官方个位数下的
总预算 105 ns/位置），而这一点已经被三种形态（8 树、共享树 + 类表头、官方哈希链）逐一证实
在这批数据上无解。验收线的 2200 ms 因此不是靠优化这一层能到的。

## 官方的时间到底花在哪：采样剖析（2026-11-15）

前面所有「官方为什么快」的判断都是靠反汇编读出来的，这一节换成实测：自建采样器（`scripts/winrar-profile/sample.ps1`，
`OpenThread` + `SuspendThread` + `GetThreadContext`，取 `Rip` 减模块基址，~1 ms 一轮），再用
`scripts/winrar-profile/profile.py`（PE 头 + capstone）把采样归到具体函数与指令。`-m3 -md32m -mt1`，ntoskrnl.exe
13.9 MB，官方 1216 ms，5888 个样本：

| 函数 | 占比 | 是什么 |
|---|---|---|
| `FUN_1400468d4` | **57.7 %** | 每位置的链搜索（`ADR 0010`） |
| `FUN_1400413dc` | 10.5 % | 逐字节建 256 桶直方图（`local_438[256]` 递增） |
| `FUN_14004600c` | 9.9 % | rep 距离 / 最佳匹配结算（先比 `+0x300e0…+0x300f8` 四个 rep） |
| `FUN_140044794` | 5.1 % | 每位置包装：塞入 1/2/3 字节短匹配后调搜索 |
| `FUN_1400421cc` | 2.9 % | 15 位滚动哈希的「近期出现过」检测 |
| `FUN_1400433bc` | 2.2 % | 建 Huffman 树 |
| `FUN_1400478e0` + `FUN_140047698` | 2.3 % | **候选的消费者**（见下） |

指令级（`FUN_1400468d4`）：`cmp byte ptr [r10+0x168], sil` 41.3%、`movsxd rax, ebx` 32.7%
——就是链上那两次串行依赖访存（取链接、取输入字节）。也就是说官方的 58 % 花在**它自己也有**的
每步单价上，和我们测出的 15.8 ns/步 是同一件事。

**关键发现：官方没有代价 DP**。`+0x20058`（候选计数）在整个程序里只有一个读者 `FUN_1400478e0`，
它把上一位置的 `(0x300c0 距离, 0x300c8 长度)` 与当前位置对调、交换候选数组 `0x20048↔0x20050`，
再调 `FUN_140047de0` 输出——这是**一步惰性匹配**。判据在 `FUN_140047698`：遍历 4 个 rep 距离，
接受条件 `len > 1 && (best_len-3 <= len || best_len*3 <= len*4) && (len+1 != best_len || best_dist > 0xff)
&& (len+2 != best_len || best_dist > 0x7ff) && (len+3 != best_len || best_dist > 0x7fff)`。

## 把惰性解析和早停也实现出来（2026-11-15，默认关闭）

按上面的形态实现 `RAR_RS_LAZY`（`parse/optimal.rs` 的 `lazy_tokens`，3 个单测）与 `RAR_RS_STOP`
（`match_finder::descent` 里「够长就封口收工」）。ntoskrnl 13.9 MB，m3，32 MiB：

| 配置 | collect | dp | 总时 | steps | 比例 |
|---|---|---|---|---|---|
| tree + DP（默认） | 2318 ms | 897 ms | 3469 ms | 72.8 M（5.2/位置） | **44.61 %** |
| tree + DP + `STOP=12` | 1500 ms | — | 2638 ms | 39.8 M | 45.90 % |
| tree + 惰性解析 | 2231 ms | **91 ms** | 2627 ms | 72.8 M | 48.15 % |
| tree + `STOP=12` + 惰性 | 1500 ms | 94 ms | 1996 ms | 39.8 M | 49.27 % |
| 官方哈希链 + `STOP=12` | 4593 ms | — | 5644 ms | 224.4 M（17.1/位置） | 45.39 % |

归档路径（`rar a -m3 -md32m -mt1`，两轮）：默认 3804–4559 ms / 5,828,867（41.89 %）；
`STOP=12` 2881–2895 ms / 6,034,037（43.36 %，破验收线 0.86 pp）。

### 读法

1. **惰性解析确实便宜**：dp 897 → 91 ms（6.5 ns/位置），与官方 2.3 % 的解析开销同量级。
   这条反向印证了剖析结论——官方省时间的第二块就是「不做 DP」。
2. **但它吃掉 3.5 pp 比例**。原因在我们的候选形态：collector 给出的是**一列按长度递增的最长匹配**
   （每个报告都必须比前面的长），惰性判据只能在这列上做「近者优先」，实测再掉 1.2 pp（49.35 %）。
   官方能在 42.30 % 上用惰性解析，是因为价格判据在**搜索函数内部**就执行了
   （`best_dist*0x4000 < dist && len < best+5`、`dist >> 5 <= best_dist`），每位置的候选天然是
   「各距离类的最佳」，而不是一列最长匹配。
3. **链式即便早停也不敌树**：`STOP=12` 下 17.1 步/位置（树 5.2），collect 4593 ms。
   近→远序遍历时近处候选只有 4–8 字节，要凑到 12 字节得穿很远。

### 决定

两条便宜路径都留下（默认关，各有单测/开关）：`RAR_RS_LAZY` 是官方解析的等价物，
`RAR_RS_STOP` 是「少搜一些」的最后一条旋钮，两者的代价曲线已记在上表。要同时满足
2200 ms 与 42.5 %，缺的不是单价也不是解析算法，而是**候选集的组织方式**：让 collector 按距离类
产出「每类最佳」，惰性判据才有东西可挑。这是下一步，也是唯一还没试过的形态。

## 按距离类产出候选：走的还是同一批节点（2026-11-15，否决）

上一节留下的下一步是「让 collector 按距离类产出每类最佳」。已实现并实测：`descent` 里对
每个命中改判 `len > class_best[class]` 就报告（8 类，边界 64/256/1024/4096/16384/65536/262144），
collector 端把该位置的报告按 `(长度, 距离)` 排回长度序（DP 依赖「后一个比前一个长」），开关
`RAR_RS_CLASS_CAND`。ntoskrnl m3：

| 配置 | 总时 | 比例 |
|---|---|---|
| `STOP=12` + DP | 2638 ms | 45.90 % |
| `STOP=12` + DP + 距离类候选 | 2883 ms（+9 %） | 45.90 % |
| `STOP=12` + 惰性 | 1996 ms | 49.27 % |
| `STOP=12` + 惰性 + 距离类候选 | 2055 ms | 49.27 % |
| `STOP=12` + 惰性 + 距离类候选 + 近者优先 | 2097 ms | 50.70 % |

64 MiB 文本上同样只多出 0.01 pp（29.42 → 29.43 %）而慢 6 %。**否决，代码已删除**。

机理：树的一次下降只会走进**一个**内容子树，它沿途遇到的节点几乎都落在同一个距离类里
（同一个四字节前缀的最近一次出现就在那附近）。真正「近而短」的那批候选，树走不到——它们
属于另一棵子树，要拿到就得给每个距离类一个独立入口，而那正是 P2 试过的两种形态（8 棵树、
共享树 + 8 份类表头），分别付出 +18 % 与 +193 % 的 collect。换句话说：**从树里拿类候选要付
入口的钱，从入口拿又要付每步漂移的钱**，两头都测过了。

至此四种形态全部实测（8 树、共享树 + 类表头、官方哈希链、类候选）都不敌 BT4；BT4 + DP 的
44.61 %／3469 ms 是这批数据上的帕累托点，想再快到 2200 ms 必须付 1.3 pp 以上比例（`STOP=12`
的 45.90 %／2638 ms 是最便宜的一档），而 42.5 % 的验收线在这个形态下没有可达点。

## 官方主循环逐条落地：速度拿得到，比例拿不到（2026-11-15）

采样剖析给出的分布（`scripts/winrar-profile/`，ntoskrnl m3，1216 ms）是搜索 57.7 %、直方图
10.5 %、rep 与最佳裁决 9.9 %、每位置包装 5.1 %、Huffman 2.2 %、**解析只有 2.3 %**。于是把
`FUN_140044794`（主循环）、`FUN_1400478e0`（一步惰性）、`FUN_140047698`（rep 判价）三支
读完，按原样写进 `interleaved_tokens`：

- 每 `0x1000` 位置一个格子；`+0x300ac` 是格内剩余长度，`+0x300b0` 是距离上限；
- 1/2/4 字节三张表各取一个候选（距离分别限 `0x100`／`0x2000`／`0x40000`，且要求
  `dist < best_dist << 7`／`<< 6`）；
- `FUN_1400468d4` 链搜索，`best_len` 从 1 起算；
- `FUN_140047698`：四个 rep 距离，长度满足 `len + 3 >= best_len` 或 `len * 4 >= best_len * 3`，
  若只短 1/2/3 字节则要求备选距离超过 `0xff`／`0x7ff`／`0x7fff`；
- `best_len < 2` 发字面量，否则 `pos += best_len` 跳过整段（`FUN_1400478e0` 之后）；
- 预算 `+0x300b8` 每发一个字面量衰减 `-= v >> 5`，与 `+0x300bc`（150）比较决定用 100 还是 25
  步；`local_res8` 是「2 字节候选信用」，命中 `+= 0x80`、`best_len != 2` 时 `-= 1`。

预计算 `FUN_14004115c` 的真相（这一轮读清的）：每位置算 4 个哈希（2/3/4/5 字节，掩码
`0x3fff`/`0x3ffff`/`0x3ffff`/`+0x148`），按 `h5 / (window / classes)` 分 8 组挂链——**分组键是
哈希域，不是距离**，所以「距离类」这个说法从此作废；短匹配那三张表 `+0xb1e8`（字节）、
`+0xb1f0`（u16）、`+0xb1f8`（u32）是**按位置索引**的（`pos - +0xb208`），一次装载就是候选，
不是哈希桶。我们的实现用哈希桶（`prev2`/`prev3`/`prev4`），4 字节表 4 MB、随机写，「实测吃掉
4 % 时间只换来 0.29 pp」——已删掉该表（`ShortTables` 现在只剩 2/3 字节两张）。

实现开关 `RAR_RS_INTERLEAVE`（默认关）。ntoskrnl 13.9 MB／m3／32 MiB：

| 配置 | seq | 归档 `-m3 -md32m -mt1` | 体积比 |
|---|---|---|---|
| 树 + DP（现状） | 3476 ms | 3840 ms | **41.89 %** |
| 融合（三表 + rep 规则 + 一步惰性 + 按长度跳） | **2151 ms** | **2421 ms** | 44.82 % |
| 官方 `Rar723.exe` | — | 1216 ms | 42.30 % |

第一版更慢，是因为三张表在**每个 64 KiB 块**里新建（1<<20 的 `prev4` 就是 4 MB memset，
213 个块），提到 `ParseBuffers` 由整段解析共享后 `2287 → 2151 ms`、归档 `3476 → 2421 ms`。

结论：**官方那 3 倍速度来自「按匹配长度跳过位置」这一行**，实测复现后我们拿到 −37 % 时间，
代价是 +2.9 pp 体积；而官方只付 0.4 pp，因为它那三张表是**为每个位置**预计算的（`FUN_14004115c`），
跳过的位置照样有短匹配可用。还没抄的三处是 `FUN_14004600c`（在 `pos+1` 上重搜链、判是否
推迟）、`FUN_140046424`／`FUN_140045b7c` 两条旁路、以及链搜索的 `dist >> 5 <= best_dist` 准入；
按缺失面估计能再收 1–1.5 pp，仍到不了 42.5 % 与 2200 ms。所以融合路径保留为**标尺**（它给出
「官方形态在我们数据上的上限」），默认关闭，不作为默认档。

### 预计算阶段的真相（同轮读清）：分组键是哈希域，短表按位置索引

`FUN_14004115c` 每位置算 4 个哈希（2/3/4/5 字节，掩码 `0x3fff`／`0x3ffff`／`0x3ffff`／
`+0x148`），然后按 `h5 / (window / classes)` 分 8 组挂链（头 `+0x48`、尾 `+0x68`、链在
`+0xb478`）——**分组键是哈希域，不是距离**，所以「8 个距离类」这个说法从此刻起作废；另有一组
`+0xb480`/`+0x88`/`+0xa8` 由 12 字节哈希键控、每 16 个位置采样一次（`+0x18e` 打开时）。
短匹配那三张表 `+0xb1e8`（字节）／`+0xb1f0`（u16）／`+0xb1f8`（u32）是**按位置索引**的
（`pos - +0xb208`）：一次装载就是候选，写入是顺序的；我们的实现用哈希桶（`prev2`／`prev3`／
`prev4`），4 字节表 4 MB、写入随机。

照此实测：删掉 `prev4` 后 `2151 → 2065 ms`、比例 47.55 → 47.87 %（那 4 MB 表只换 0.29 pp
却要 4 % 时间）；`RAR_RS_NOREP` 关掉 rep 规则是 `−4.5 %／+0.38 pp`；`RAR_RS_NOTABLES` 关掉两张
短表是 `1910 ms／49.04 %`（即两张表花 0.4 s 换 1.46 pp）。融合路径最终：seq 2065 ms、归档
2186 ms、体积 45.16 %。每搜索位置 5.76 M 次、16.5 M 步，折合 ~365 ns/位置，而官方约 200 ns——
剩下的差距在每位置的簿记（三张表的探测、`length_bonus`、候选入栈），不在下降本身（只有 2.9 步）。

### 再把两张短表改成按位置索引（同轮落地）

照 `+0xb1e8`／`+0xb1f0` 的存法重写：`ShortTables` 现在持两个区块长度的**距离数组**
`prev2`／`prev3`（`prev2[offset]` = 回到上一个同 2 字节对／同 3 字节哈希位置的距离），
以及跨区块保留的两张 `last` 映射（`1<<16` 项，常驻 L2）。每个区块开头跑一遍 `prepare()`
顺序写两张表，循环里一次装载就得候选，不再做哈希乘与随机桶写。

| 配置 | seq | 归档 | 体积 |
|---|---|---|---|
| 哈希桶两表 + rep（上一步） | 2065 ms | 2186 ms | 47.87 % ／ 45.16 % |
| 按位置索引两表 + rep | **2031 ms** | **2164 ms** | 47.87 % ／ 45.22 % |
| 同上 + rep 只在 `best_len < 12` 时跑（官方 `FUN_14004600c` 的分界） | **2039 ms** | — | 47.93 % |

结论：位置索引只值 1.6 %（两张 `last` 映射本来就在 L2，随机写不像 4 字节表那样摊到 4 MB），
但方向和官方一致、内存从 4.5 MB 降到两张区块数组。每搜索位置仍是 ~350 ns 对官方 200 ns，
差的那部分不在下降（2.9 步/次）也不在这两张表，而在每位置的其余簿记与 `finder.matches`
的调用开销上。

### 融合路径的大头其实是树搜索：一次预取拿回 16 %

消融 `RAR_RS_NOTREE`（只留两张短表 + rep 规则，完全不搜树）：792 ms / 54.94 %；带树
2192 ms / 47.93 % ⇒ 树花掉 1.4 s、买回 7 pp。5.76 M 次搜索、2.9 步/次，折合每次 243 ns，
远高于 `walkbench` 里 15.8 ns/步——因为融合循环同时压着两张短表、候选与 token，树的两级
访存（桶头、`son` 对）都掉到 DRAM。

照串行 collector 的做法，在 `pos + 16` 处预取桶头（`finder.prefetch_head_for`）：

| 配置 | seq | 归档 | 体积 |
|---|---|---|---|
| 无预取 | 2192 ms | 2164 ms | 47.93 % ／ 45.22 % |
| 预取距离 8 | 1864 ms | — | 47.93 % |
| **预取距离 16** | **1847 ms** | **1984 ms** | 47.93 % ／ 45.22 % |
| 预取距离 32 | 1855 ms | — | 47.93 % |

预取不改候选流（比例一位不变），纯拿回 16 %。融合路径因此到 1847 ms（seq）／1984 ms（归档），
是这批形态里最快的合法点，代价仍是 +3.3 pp 体积。

### 两级预取：桶头提前 32 位、节点提前 16 位

一级预取只藏住桶头，节点那对 `son` 与输入字节仍然是冷缺失（每次搜索 2.9 步却要 183 ns）。
再加一级：`pos` 处读 `head[hash(pos + 16)]`（该桶在 `pos - 16` 时已被一级预取，命中），
解出 `current` 后预取 `son[(current & mask) << 1]` 与该节点的输入字节
（`TreeMatchFinder::prefetch_node_for`），同时把一级预取推到 `pos + 32`。

| 配置 | seq | 体积 |
|---|---|---|
| 无预取 | 2192 ms | 47.93 % |
| 一级（`pos + 16` 桶头） | 1847 ms | 47.93 % |
| **两级（桶头 +32、节点 +16）** | **1734–1784 ms** | 47.93 % |
| 两级但都推远（桶头 +48、节点 +32） | 1883 ms | 47.93 % |

归档 1984 → 1979 ms（两轮 1979/1993，体积 45.22 % 不变）。管线不能推太深：推到 +48/+32 反而退回
1883 ms，因为提前读的桶头在真正用到前已被刷掉。融合路径至此 1750 ms（seq）／1980 ms（归档）。

### 深度曲线：每多走一步的代价与收益（`RAR_RS_FUSED_CUT`）

融合路径的 `cut` 现在可用 `RAR_RS_FUSED_CUT` 覆盖（默认取档位的 `chain_len`）。ntoskrnl m3：

| cut | seq | 体积 | 说明 |
|---|---|---|---|
| 1 | 1208 ms | 50.64 % | 只走一步（含桶头与首节点） |
| 2 | 1293 ms | 49.77 % | 第二步 +85 ms（15 ns/搜索） |
| 96（默认） | 1731 ms | 47.93 % | 2.9 步/搜索、更深每步 ~84 ns |

把 950 ms 的树成本拆开：第一步 416 ms（72 ns/搜索，桶头与首节点各一次缺失），第二步便宜，
再往深每步 ~84 ns（冷缺失，预取只覆盖得到前两级）。桶表大小不是杠杆：`HASH_BITS` 21 →
1811 ms、22 → 1756 ms、23/24 → 1731–1784 ms（同一噪声带），体积一位不变。

给出这条曲线的用处是选点：`cut = 2` 是 1293 ms / 49.77 %，`cut = 96` 是 1731 ms / 47.93 %——
**每放弃 0.5–0.9 pp 体积，换 100–400 ms**，比早停（`RAR_RS_STOP`）的斜率略好。

### 信用计数节流：实现了，在二进制数据上是惰性的（已回退）

照 `FUN_140044794` 的 `+0x300b8`（发出的匹配字节充值、字面量扣减）对 `+0x300bc = 150`
实现了一版：信用低于阈值时把预算砍到四分之一，并且**在已有短候选时连搜索一起跳过**
（这正是 72 ns/搜索的第一步成本所在）。实测（ntoskrnl m3，交替两轮）：无节流 1764/1738 ms、
节流 1738/1757 ms，比例 47.93 → 47.94 %——**几乎不动**。

原因：融合路径在发出长匹配后整段跳过，字面量位置本来就少，信用计数长期贴着上限，
节流条件基本不成立。官方的计数器咬合在它们更稠密的短匹配路径上（它们不跳过位置，
每个位置都发短匹配或字面量）。代码已 `git checkout` 回退，只留这条记录。
