# ADR 0011：按官方形状重做匹配器（立项）

- 状态：**提案**（2026-11-15）
- 关联：[ADR 0009](0009-match-finder-kernel.md)（BT4 内核）、[ADR 0010](0010-hash-ring-finder.md)（哈希环重写，已否决）；`docs/PITFALLS.md`「压缩内核」；`PLAN.md`「性能」

## 背景

当前主路径是「BT4 树收候选 + 融合单遍 DP 定价」。在 ntoskrnl.exe（13.9 MB，`-md32m`）上的定论：

| 方案 | 时间 | 体积 |
|---|---|---|
| 现状（树 + DP，m3） | 4329 ms | 5,828,867（41.88%） |
| 树 + 贪婪早退（m3 临时改路由） | 3459 ms | 6,656,044（47.83%） |
| 官方 WinRAR 7.23（m3） | 1466 ms | 5,886,469（42.30%） |

价格分解（m3，总 4329 ms）：`collect` 2913、`dp` 978、`prep` ~110、`emit` 111、`convert` 29。其中 `collect` 里 60 ns/位置是地板（`RAR_RS_SEQ_PRICE_TIER=1` 实测 2302 ms），其余 ~150 ns 是"为 DP 多给候选"付出的树深。

已排除的旋钮（都有实测）：树预算 ≥24 不再咬合；近窗口大小是工作集代价（10% 换 0.3pp）；`OPT_BLOCK_SIZE`/DP 状态带宽无影响（32 KiB 与 64 KiB 同速）；校验上限收紧只是比例换时间；每个候选的单价由「越界检查的 `son` 索引 + 8 字节比较 + `match_length_at` 验证」决定。

官方之所以既贪婪又深还快：**每个候选只花一次字节比较**——每块预计算哈希、8 个距离类近距优先、子节点数组按位置索引，工作集全在热内存；代价是比例低 0.42pp。

## 决策

新开一条匹配器实现，形状照官方：`collect` 阶段不再走 BT4，而是

1. **每块预计算哈希**：进入 64 KiB 解析块时先扫一遍，把该块每个位置的 4/5 字节哈希与长哈希写进紧凑数组（`u32`/位置），后续下降只读该数组。
2. **按位置索引的子节点**：`son: Vec<[u32; 2]>` 之类的平铺数组，用位置而非内容键定位，避免 BT4 桶的随机访问；插入位置与查询位置都在同一块内，命中集中在最近写入的行。
3. **8 个距离类**：把窗口按 `hash / (window / classes)` 分桶，近距类优先搜索、远距类给独立预算（官方 `+0x188 = budget >> 2` 就是远距预算），使"就近优先"直接体现在搜索顺序上，而不是靠距离约束事后过滤。
4. **预算 + 早退**：沿用官方量级（m3 ≈ 100 候选/位置），找到 `NICE_MATCH_LENGTH` 以上即停；候选以 `(len, dist)` 递增形式交给现有定价层。

不变的部分：`parse/pricing.rs`（`EncoderMatchState`/`TokenPrices`/`SlotPricer`/`convert_tokens`）、`parse/block.rs` 的发射块策略、`LongRange`、`ShortFinder`、DP 本身。新匹配器只替换 `collect_block_matches` 的候选来源。

## 验收门槛

按块回归优先（比整体百分比更能定位退化）：

- 逐块 `tokens`/`literals` 对照现状实现，任何一块退化 >2% 视为回归（工具：`RAR_RS_PROFILE` 分相 + `RAR_RS_DEBUG_PRICES` 逐块计数）。
- 整体：ntoskrnl m3 ≤ **2200 ms** 且 ≤ 42.5%（现 4329/41.88%）；d2d1 m3 不变慢且不变大；text/xml 保持 16.5%/10.0%；mt8 不退化。
- 不达标就整体回退到 `781afa0`（本 ADR 只记录方向与实测，不预设保留）。

## 分期

1. **P1 骨架**：块内哈希预计算 + 位置索引子节点 + 预算早退，接现有 `collect_block_matches` 接口，先只保证正确（606 测试 + 忽略的字节回归矩阵）。
2. **P2 距离类**：8 类分桶与远距预算，量时间/比例曲线，定 m1–m5 的候选数与类数。**已否决（两种形态），见文末 P2 与 P2' 两节。**
3. **P3 与 DP 合流**：候选递增序、`ShortFinder` 合流、逐块回归门槛跑通。
4. **P4 并行**：MT 切片带块内预计算（每 worker 自建索引即可，无需共享）。

## 风险

- 预计算哈希的前置扫描本身是 13.9 M 次读，若不能与下降共用缓存行，会变成纯亏损（P1 必须先量这一项）。
- 位置索引子节点在**跨块**匹配上不如树：块边界的历史只能靠 `LongRange` 与短表，需在 P1 就用 `mixed`/`sparse` 语料验证。
- 这是新增实现，不是改动主路径：P1 起就放在 `parse/hashmatcher.rs`，用环境变量接入 `BlockSearch`，默认关闭，达标后再切默认。（P2 实测否决该形态后，这条路径已整体删除，见文末「决定」。）

## P1 前置测量（2026-11-15）

先量「预计算那一趟」的净成本（`crates/rar/examples/hashprobe.rs`，两表各 `u32`/位置）：

```
precompute 13917560 positions: 10 ms (2 tables, 108730 KiB written)
```

即 13.9 M 位置铺两张哈希表只要 **10 ms**，占 `collect`(2913 ms) 的 0.3%、整档的 0.2%——纯流式写、预取友好。**P1 的第一个风险（预扫描本身亏损）不成立，继续做骨架。**

仍待验证的是第二个风险：108 MB 的哈希流在下降读回时是否还在缓存里。按 64 KiB 解析块算，单块的哈希切片是 512 KiB，能落在 L2/L3；跨块下降则要重读。P1 的骨架必须按块分配/按块读，而不是整文件一张表。

## P1 第二个测量：读回是否热

同一探针加了读路径对照（1M 次伪随机查表）：

```
reads: 1.2 ns/lookup inside a 64 KiB block slice, 6.2 ns/lookup across the whole member
```

块内哈希切片（512 KiB，两表）**1.2 ns/次**，整成员表（108 MB）**6.2 ns/次**，差 5×。结论：

- 9 个候选/位置的哈希读 ≈ 11 ns，100 个候选 ≈ 120 ns —— 与官方 105 ns/位置同量级，说明**哈希读就是他们的主要成本项**，布局比算术重要；
- 因此候选链**必须留在块内**：块内下降走 1.2 ns 的路径，跨块候选交给 `LongRange` 与 `ShortFinder`，不要沿着块内子节点走进更早的块（那一步就是 6.2 ns）。
- P2 的 8 个距离类必须按块内偏移分层，而不是按整个窗口分层，否则类内索引会跨块。

## P1.3 结果：块内候选密度不够——「块内」前提不成立

`hashmatcher::tests::reports_candidate_density_and_cost`（1 MiB 文本，64 KiB 块，`head` 1<<14、8 字节键、预算 32）：

```
hashmatcher: 109852 candidates over 983040 positions (0.11/pos), 4.5% reach 16 bytes, 39.0 ns/pos
```

BT4 在同一份数据上是 ~1.1 候选/位置、且 20.8 M 次校验/13.6 M 次下降。块内链只有 0.11/位置，低一个数量级：64 KiB 块里每个哈希槽平均只落 ~4 个位置，去掉哈希碰撞后同键命中极少，只能看到很靠近的重复。

**结论：候选表不能按块截断。** 官方之所以只花 105 ns/位置，靠的不是"块内"，而是**子节点按位置索引**带来的空间局部性（最近写入的子节点在相邻行，8 个距离类把窗口切成多段，近段总在热区）。这与我们此前那版「位置索引 `chain8`」形态一致，但那次是把它挂在一个 8 字节单键上、逐候选付 `verify`，所以只有哈希环的水平（48.18%）。

P2 必须同时满足三点才有希望：全窗口覆盖（回比例）、按位置索引的子节点（局部性）、每步只做一次字节比较（单价，靠树形生长而非逐候选 `verify`）。三者的共同点就是 BT4 本身——差别只在 BT4 的 `son` 是内容键定位的树、按窗口复制，而官方是位置索引 + 距离类分层。

下一节 P2 的实测把这条假设否掉了。

## P2 结果：8 个距离类方案否决（2026-11-15）

### 实现形态

`parse/hashmatcher.rs` 里 `ClassMatchFinder`，`RAR_RS_CLASSES`（1..=8，缺省关）选中，`RAR_RS_CLASS_FAR` 给远距预算的右移（缺省 2）。三条机制：

- **位置索引子节点**：`son` 槽位是 `class*block_len*2 + (pos - base[class])*2`，块内相对索引而非 `pos & mask`。这是与 BT4 唯一的实质差别：帧滑动时只要平移 `base[]`（O(classes)），子节点一个字节都不用重写；BT4 每次 `rebase` 都要重排整个 ring。
- **类环**：每类一棵 BT4 形态的树，覆盖一段连续的 `block_len`（2 的幂）块，8 类轮转；近类吃满预算，远类共享 `budget >> 2`。整环宽 `classes * block_len`，按窗口一次分配（改名即失效，不能像 BT4 那样原地长大）。
- **类不是「距离带」**：环可以比窗口宽，两块可能落在同一带上；早期版本用 `band -> class` 下标表，同带冲突直接丢掉一整块。现在按块龄从近到远逐个走。

另有一条正确性前提：`len_limit` 被输入尾部截断时，**不允许**「整段前缀相同 → 收养子树」。BT4 那条捷径只在限长是真实上界时成立；截断的限长证明不了后面的字节，收养之后树的序就被破坏，之后每次走行都会虚报长度（实测在 5 万位置处虚报 16 字节对 7 字节）。截断时改为封口，两端都不认。

保真性有测试钉住：`stream_equals_bt4_when_one_class_covers_the_window`——单块覆盖整帧时，1/2 类给出的候选流与 BT4 **逐条相同**（5 万位置零差异），所以下面的差距不是实现跑偏，而是「把一棵树切成多棵」本身的代价。

### 测量

ntoskrnl.exe 13.9 MB、`-m3`、`DICT=8`（32 MiB），本机。比例可复现，墙钟有噪声，故同时列 `RAR_RS_PROFILE` 相位：

| 方案 | 比例 | collect | dp | 说明 |
|---|---|---|---|---|
| BT4（现行） | **44.61%** | 3067 ms | 928 ms | 基线，220 ns/位置 |
| 8 类，远预算 `cut>>2` | 45.17% | 3633 ms | 887 ms | +18% collect，-0.56pp |
| 8 类，`RAR_RS_NEAR=32 MiB`（不发生 rebase） | 45.07% | — | — | 排除 rebase 丢块的影响 |
| 8 类，远预算 `cut>>0`、`>>1`（同上） | 45.06% / 45.06% | — | — | 远预算给到 96 也不回比例 |
| 4 类 / 2 类 | 45.21% / 44.85% | | | 都劣于基线 |

旁证：
- ntoskrnl 前 4 MiB（单块覆盖整帧）三种类数比例都**与 BT4 完全相等**（45.77%），印证上面那条保真测试。
- `verify` 计数 4 285 758 对 BT4 的 4 525 053：类方案给的候选更少，比例还更差。
- 64 MiB 文本 m3：28.28% → 28.92%（+0.64pp），33.5 s → 43.7 s。

### 为什么切分必然亏

BT4 的一次 96 步下降，是在**按内容排序**的一棵树里走：命中哪个年龄段由内容决定，各年龄段的候选在同一次下降里就能走到。按年龄切树之后，每个年龄段要单独付一次下降预算，等于把「96 步覆盖全窗口」换成「96 步覆盖最新一段 + 24 步覆盖其余各段」。把远预算从 24 提到 96（`RAR_RS_CLASS_FAR=0`）比例一点不回来，说明卡点不是预算不够，而是**分层后每棵树的形状更碎**：96 步在新树里走不到 BT4 同一步数下能到的深层节点。再加预算就是纯亏时间。

P1.3 末尾那条假设——「官方赢在位置索引 + 距离类带来的空间局部性」——因此不成立：类树更小更热，但主导项是步数，不是缓存。位置索引带来的那一点局部性（`rebase` 免重写）省下的是每帧 O(窗口) 的一次性开销，摊到 13.9 M 位置上不够看。

## P2'：改成官方的真形态（共享 `son` + 8 份类表头）——同样否决（2026-11-15）

「8 棵树」被否决后还剩一种读法：官方并没有 8 棵树，它只有**一份**按位置索引的子节点数组（`min(dict, 1 GiB) × 4B` 两份，见 ADR 0010），距离类只是 8 个**入口**（`+0x48`/`+0x68` 的链表头尾），预算 100 由近类吃满、远类吃 `budget >> 2`。照这个形态重写：一份 `son`（`(pos & mask) << 1`，与 BT4 同布局）+ `classes` 份 head 快照，每写满 `block_len` 就把当前快照轮转到下一格并清空；近快照插入并吃满预算，老快照只搜不插，所有老快照**共享**一份远预算。单快照覆盖整帧时，候选流与 BT4 逐条相同（有测试钉住），所以下面的差距不是实现跑偏。

ntoskrnl.exe `-m3`、32 MiB 窗口：

| 方案 | 比例 | collect |
|---|---|---|
| BT4（现行） | **44.61%** | 2704–2729 ms |
| 8 类共享树，远预算 1 步/类（`FAR=8`） | 45.54% | 2640 ms |
| 8 类共享树，6 步/类（`FAR=4`） | 45.01% | 4985 ms |
| 8 类共享树，24 步共享（`FAR=2`） | 44.63% | 7917 ms |
| 8 类共享树，96 步共享（`FAR=0`） | 44.61% | 7848 ms |
| 2 类共享树（`FAR=2`） | 44.61% | 3498 ms |

读法：`FAR=8` 时每个老快照只走 1 步，等于只用最新一块（32 MiB / 8 = 4 MiB）——45.54%，比 BT4 差 0.93pp，时间还略快。往后每加一段远走行，比例就回到 44.61%，正好把那 0.93pp 补回来，代价是 +5.3 s。也就是说**距离类买到的候选，BT4 在同一次按内容排序的下降里本来就能走到**，而它为此要多付一次随机访存。

代价不在入口，在远走行：入口查表几乎免费（`FAR=8` 比 BT4 还快 64 ms，head 缩到 2^17 后更好命中），付费的是远走的每一步——入口点在窗口末尾往回 `block_len` 处，每一步都是一次 DRAM 缺页，约 16 ns/步；24 步 × 13.9 M 位置就是 5.3 s。

顺带钉住两个事实：

- **BT4 的预算根本不咬合**：`chain_len` 96 / 256 / 1024（m3/m4/m5）的 collect 分别是 2728.5 / 2727.7 / 2772.0 ms，比例 44.61 / 44.52 / 44.50%。树先走空了，所以「官方 100 步、我们 96 步」不是差距来源。
- 位置索引那条理论收益（`rebase` 免重写整个 ring）摊到 13.9 M 位置上不足 1%：把「每帧一次 O(窗口) 重排」省掉，救不了每候选的单价。

结论：距离类在两种形态下都被**严格支配**——切树是 +18% 时间 / -0.56pp，共享树是 +193% 时间 / 比例持平。P1.3 末尾那条「官方赢在位置索引 + 距离类」的假设，至此彻底否掉。

## 决定

- **否决距离类方案（两种形态都否决）**，默认路径继续是 BT4。相关代码已整体删除：`parse/hashmatcher.rs`、`parse::Finder` 枚举、`collect::BlockFinder` trait、`EncoderState::class`、`profile::BAND` 一并移除；`RAR_RS_CLASSES` / `RAR_RS_CLASS_FAR` 不再存在。留着的只有两条与它无关的正确性/性能收益（见下条）。
- 保留下来的那次改动是 `9cbb354`：**下降在输入末端封口**（截断的 `len_limit` 不再收养子树，树的序不再被破坏），因此 `collect` 里那趟 `match_length_at` 复核可以整趟删掉——release 里只剩 `debug_assert`。ntoskrnl m3 collect 2838.5 → 2745.6 ms（-3.3%），比例 44.61% 不变。
- 验收线（≤ 2200 ms 且 ≤ 42.5%）在距离类形态下无望：需要同时 -47% 时间与 -0.2pp 比例，实测是 +18% 时间与 +0.56pp。
- 缺口仍然是**每候选单价**（ADR 0009 的复述）：官方整档 105 ns/位置，我们光 `collect` 就 212 ns/位置。下一步要攻的是每次下降的常数（子节点行内布局、一次字节比较、取指与分支），而不是候选结构的分层——分层已经用三种形态证否过了。P3/P4 在当前形态下没有意义，暂缓。
