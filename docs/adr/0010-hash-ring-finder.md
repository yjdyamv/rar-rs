## 背景

ADR 0009 的结论是「差距在每位置常数，不在解析模型」，并提出了平表单探测
（`head[hash]` 只存最新位置）的假设。按这条假设把匹配器与解析器整体重写后，
得到的是**每位置常数降下来、但候选质量下降**的结构性取舍。本 ADR 记录实际
落地的结构、实测数字与被否决的替代方案。

## 决策

1. **匹配器换成多级哈希表 + 环**（`parse/finder.rs`）：`head4` 是 2^17 桶 ×
   `depth4` 个位置的环（插入 O(1)，用 age 字节轮转，不再整体搬移）， `head8`
   同形；另有 `head16`/`head32` 两张 2^18 槽的**单槽表**，给出 「16/32
   字节前缀的最近一次出现」。候选按「比已见候选更长才报告」压成
   严格递增的梯子。**键长度比桶深度重要**（见下文实测）。
2. **删除 BT4**（`TreeMatchFinder`）与 `parse/collect.rs`：BT4 的 per-prefix
   最近邻是它唯一的优势，但每位置几十次随机节点访问是主要成本。
3. **删除 row-index 与 MT 的预建索引**（`RowIndex`、`MT_ROW_INDEX_*`）。
4. **解析器融合成单遍 DP**（`parse/dp.rs`）：匹配搜索、定价、回溯在一次
   位置扫描里完成，不再「先 collect 全块候选、再走一遍 DP」。窗口内候选由
   环给出，窗口外由共享 `LongRange` 表给出（`LR_MIN_DIST = 1`，见下）。
5. **定价逻辑整体搬进 `parse/pricing.rs`**（`EncoderMatchState`/`TokenPrices`/
   `SlotPricer`/`convert_tokens`），语义与旧实现逐行一致，块间继续顺延码长表。
6. **放弃多 pass 重定价**：`find_matches_optimal` 每块只解析一次。

## 实测（字典 32 MiB，`collectbench`，真实文件）

| 语料              | level | 旧 seq            | 新 seq           | 旧 `-mt8`        | 新 `-mt8`            |
| ----------------- | ----- | ----------------- | ---------------- | ---------------- | -------------------- |
| ntoskrnl 13.3 MiB | m3    | 46.69% / 1431 ms  | —                | 46.69% / 1431 ms | **48.53% / 1083 ms** |
| ntoskrnl 13.3 MiB | m5    | 43.77% / 15300 ms | 47.43% / 6736 ms | —                | —                    |
| d2d1.dll 6.3 MiB  | m3    | 38.79% / 2397 ms  | 38.67% / 1712 ms | 38.41% / 752 ms  | 38.86% / **732 ms**  |

| ------------- | ------------------- | ------------------- | ------------------- |
| text          | 18.36% → **16.34%** | 17.63% → **16.34%** | 16.79% → **16.20%** |
| mixed         | 48.56% → 50.88%     | 48.41% → 50.88%     | 48.27% → 50.86%     |

结论：二进制面（ntoskrnl、d2d1）同体积附近快 1.1–1.4×（m5 快 2.3×）， 文本/XML
面**体积好 1–1.8pp**、耗时持平到 +30%；`mixed` 与 `sparse-copies` 仍差
0.9–2.4pp。耗时随匹配密度增长（每位置的候选验证数随可压性上升），
所以高可压语料上的速度优势最小。

## 为什么环拿不回 BT4 的比例（实测结论）

13.9 M 个位置灌进 2^17 个桶 ≈ 每桶 106 个候选，桶里留下的是**流的随机采样**，
不是「我们这个键的上一次出现」；只有 4/8 字节键复现足够密，最近才等于最近邻。
因此：加深桶（depth 48/64 → 47.3%）、加长键梯子（12/16/…/48 七个长度表）、
桶外多级旧样本、提高表宽（H8 17→18）**全部**在 47.3–48.9% 饱和，与 `(2,2)` 到
`(32,16)` 的深度无关。这是结构上限，不是参数没调好。

### 但「每个长度的最近邻」可以用单槽表买回来

真正有用的不是更深的桶，而是**多几个键长度**：`head16`、`head32` 各一张 2^18
槽的单槽表（各 1 MiB，每位置两次哈希 + 两次写，命中时多一次候选
验证）把最近邻从「8 字节前缀」抬到「16/32 字节前缀」——同一段 12 字节匹配 在 8
字节键下的最近出现可能在几 MB 外，在 16 字节键下往往只有几十字节。
实测（`ratiocheck`）：text l2 17.37% → **16.34%**、xml l3 11.36% →
**10.04%**、mixed 50.95% → 50.88%、ntoskrnl 47.77% → 47.72%。 代价是每位置约
+10–15% 时间（xml 这类高命中语料更贵），所以只在 `avail >= 16/32` 时探测，且用
`verify` 的 soft-limit 两段式测量。 **结论：环的深度是错的旋钮，键长度才是。**

## 遗留与后续方向

- 若要把 `mixed`/`sparse-copies` 的 0.9–2.4pp 拿回来，还得继续补「中间
  长度」的最近邻（16/32 两张表已验证方向有效，但 9–15 字节这一段仍只有 8
  字节键的最近邻）。可加 `head12`，或把 8 字节环换成长度分层的单槽表。
- 多 pass 重定价在融合解析器上不可行：环只保留最新 N 次出现，第二遍扫描时
  那些位置已在查询点之后被跳过，重定价会把解析退化成全字面量（实测 +5pp）。
  旧实现能做重定价，是因为它把候选一次性 collect 进了 `BlockMatches`。

## 教训（已进 `docs/PITFALLS.md`）

- `LongRange::find_from` 曾拒绝 `cand_abs >= anchor` 的候选。锚点是帧的起点，
  于是**尾部之内的候选全被丢掉**，而尾部正是哈希环淘汰掉的那些位置 ——
  顺序流里它表现为「远端复制完全匹配不到」，MT 里表现为整段字面量。 修正后
  `LR_MIN_DIST = 1` 才真正生效。
- MT 的 `Finder` 深度变化必须重新 seed：帧不是 fresh 但表被替换时若不清表
  重建，整个携带窗口会变得不可匹配（`Frame::arm` 现在显式处理）。

## 附：官方实现（WinRAR 7.23 `Rar.exe`）的逆向结论

2026-11-14 用 `ghlab`（Ghidra 12 headless）导入 `Rar.exe`（x64，835,792 B， md5
`c7b8d0c2b6a3851291fd446113cbfc5d`，2316 个函数）后的实测结论。目的不是
抄算法，而是回答「为什么它每位置约 105 ns，而我们约 334 ns」。

### 结构

- **初始化** `FUN_140043670`：字典按体量折半（>4 MiB 取一半，>64 MiB
  取四分之一，
  > 1 GiB 取十六分之一，存 `+0x150`）；分配 **两块 `min(dict, 1 GiB) × 4 B` 的
  > int 数组**（`+0x120`/`+0x128`，二叉树的左右子节点），加一张 **2 的幂大小的
  > 哈希头表**（`1<<ceil(log2(min(dict/4, 8 MiB)))`，下限 2^18，掩码在
  > `+0x148`）。 即**它仍然是「哈希头 + 二叉树」**，不是纯哈希表。
- **每块一次哈希预计算** `FUN_14004115c`：对整块逐位置算出 4 个哈希 （乘子
  `0x2773`）：2 字节（`&0x3fff`）、3 字节（`&0x3ffff`）、 4/5
  字节（`&0x3ffff`）以及一个被 `+0x148` 掩码的长哈希；同时按
  `hash / (dict/桶数)` 把每个位置分进 8 个「距离类」（`+0x48`/`+0x68`
  两组链表头尾）。
  匹配阶段**不再计算哈希**，只读这些数组——这是可向量化的紧凑循环。
- **搜索** `FUN_1400468d4`：从哈希头取出候选，沿子节点逐字节比较，一次一步、
  每步同时更新当前最佳长度；预算来自 `+0x184`，远距离时用 `+0x188 = 预算 >> 2`。
- **预算表** `DAT_1400baf58` = `{2, 18, 45, 100, 150}`（m0..m4，m5 复用末项）：
  **m3 每位置最多走 100 个候选，m4 走 150 个**。驱动里还有 `0x1000` 的子块
  切分与 `0x96`（150）的 nice-length 常量。

### 对我们的含义

1. 我们 m3 的环深度只有 `(4, 8)`，候选数远少于官方的 100，**却比它慢 3 倍**。
   所以瓶颈不是「找得太多」，而是**每候选的成本**：我们的候选来自 2^17 个
   哈希桶，读取位置在 1 MiB 表里随机散布（基本每次都缺页级 cache miss），
   而官方的子节点数组**按位置索引**，遍历到的位置通常集中在最近窗口内，
   相邻节点往往落在同一两个 cache 行里。
2. 官方把哈希提前成一次顺序扫描（每位置 4 个），搜索循环里只剩「读指针 +
   比较字节」；我们在搜索里做 2 次哈希（4/8 字节）+ 2 次长表单槽探测，
   哈希本身也要吃一次随机写。
3. 结论：环的方向没错（它把常数降下来了），但**丢掉了「按位置索引 → 局部性」
   这一条**。下一步应该回到「按位置索引的链/树」，但保留环的 O(1) 插入与
   预计算哈希——即 `head[hash]` 一张小表 + `prev[pos & mask]` 一条按位置索引
   的链，链上比较用已经算好的哈希做预过滤。
