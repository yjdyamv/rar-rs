# ADR 0009: 匹配器内核替换（压缩速度）

- Status: proposed (2026-11)
- Date: 2026-11-14
- Related: [ADR 0008](0008-one-way-family-layering.md)（编码侧分层）、
  `crates/rar/src/codec/modern/lzss_huff/encoder/`（匹配器与解析器）

## 背景

压缩速度整体落后官方 WinRAR 7.30 约 3–6×（同机、release、`-ma5`）：

| 场景 | 我们 | 官方 |
|---|---|---|
| 87 MB DLL，m3 非固实 | 4.0 s | 1.18 s |
| 87 MB DLL，m5 非固实 | 5.8 s | 2.10 s |
| 6.6 MB 单文件，m3 `-mc-` | 487 ms | 164 ms |
| 6.6 MB 单文件，m3 `-mc-` 净编码（减启动） | ≈390 ms | ≈65 ms |

已经做过的、可提交的优化只有 `a459853`（`-m1` 贪婪匹配上限 4097 → 128，
单文件 3.2–3.9×，体积 +0.12%）与 `a2ec2e9`（编码块 4 MiB → 1 MiB）。

## 诊断（实测）

6.6 MB DLL、m3、`-mc-`、MT 路径，插桩累计：

```
syms=2238852  parse=918ms  huffman=44ms
```

- Huffman 只占 ~5%，**parse 占 95%**
- 每输入位置（6.6 M 个）≈ 139 ns；官方整条链 ≈ 10 ns/位置
- 全零 6 MB 输入 131 ms（≈启动开销）→ 成本随候选密度增长，不是线性每字节

已排除：`max_match`（4097/1024/256 无差别）、DP 块大小（256K/128K/64K
无差别）、long-range 探测（关掉只省 5%）、DP 临时数组、深度 64→16（−13%，
+1% 体积）。

已排除的解析模型改造（都在单文件上实测）：

| 模型 | 体积 | 时间 |
|---|---|---|
| row-index + priced DP（现状） | 2,549,783 | 487 ms |
| greedy chain16，无 lazy | 2,860,158 (+12%) | 358 ms |
| greedy chain4，无 lazy | 2,919,287 (+14.5%) | 285 ms |
| 官方 | 2,505,931 | 164 ms |

结论：差距不在「用哪种 parse」，而在**每个位置的匹配器常数**（随机内存访问
为主）。解析模型的两条路都已到帕累托前沿。

## 决策

替换匹配器内核，而不是继续调解析器参数：

1. **紧凑 BT4**（每节点只存 2 个子指针 + 位置，32 位下标，节点池按 2×窗口
   预分配），插入与下降都用 8 字节比较、16 字节成对比较；候选仍按「距离升序、
   仅报告刷新最长」交给现有 DP。
2. **每 worker 一份本地 BT4**，只覆盖 slice 的“tail + 本 slice”，tail 只插入
   不下降（与现状 `mt_slice_symbols_low_step` 的框架一致），远端匹配继续走
   共享 `LongRange`。
3. **每位置随机访问 ≤ 2 次**：BT4 下降从根开始，用 4 字节哈希定位首节点后
   逐层比较，命中即停；不做 bucket 的二分（现状 `partition_point` 每位置
   一次）。
4. **可选 SIMD**：`std::arch` 的 SSE2/AVX2 16/32 字节比较（x86_64 默认可用，
   其余平台退回 8 字节循环），只在长匹配（≥16 字节）时启用。
5. 解析器接口不变：`windowed_priced_parse` 的 `emit` 闭包换成 BT4 查询，
   DP/定价/符号输出全部复用，避免两套语义。

## 目标与验收

- m3 单文件净编码 ≤ 180 ms（现状 390 ms），体积 ≤ 2,560,000（现状
  2,549,783，允许 +0.4%）
- 87 MB 语料 m3 ≤ 2.0 s（现状 4.0 s），m5 ≤ 3.2 s（现状 5.8 s）
- 输出必须能被官方 UnRAR 解压；`cargo test -p rar-rs --lib codec::` 全绿；
  decode 侧完全不动
- 基准方法：`target/perf/` 固定语料 + `scripts/bench.sh`（m1/m3/m5 ×
  固实/非固实 × 单文件/目录），记录体积与 wall time

## 风险

- BT4 每 worker 的内存 ≈ 8–12 B/字节（6 MiB slice → ~70 MiB），需要沿用
  `MT_ROW_INDEX` 的内存预算逻辑并纳入 `PARALLEL_*` 限制
- 下降路径的 `unsafe` 索引必须用 debug 断言兜住；先做安全版本，压测后再考虑
  SIMD
- 与固实链的衔接：BT4 只覆盖当前窗口，跨窗口历史仍靠 `LongRange`，比例可能
  回退 0.3–0.8%，以验收线为准

## 备选（未采纳）

- 继续调 row-index 深度/DP 块：收益 <15%，已到顶
- 移植顺序路径 BT4：顺序路径自身 1.7 s，更慢
- 只用 greedy：快 1.7×，但体积 +14%
